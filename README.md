# my_dev_method — AI 협업 개발방법론

**이미 있는 계획 문서를 받아, 구현 중에 문서가 서로 어긋나서 생기는 오류와 일탈을 막는 방법론**입니다.

계획을 뽑아내는 좋은 도구는 이미 많습니다. 이 키트는 그 **다음**을 맡습니다 — 계획을 받아 요구사항에 ID를 붙이고,
문서 간 정합성을 **스크립트가 기계로** 지키고, 코드리뷰는 **구현과 분리된 서브에이전트가** 합니다.

**어떤 계획 도구도 전제하지 않습니다.** `/adopt`가 저장소 안을 먼저 뒤지고, 없으면 밖에 있는지 묻고,
그래도 없으면 `/plan`이 직접 만듭니다 — 특정 SaaS가 있어야 돌아가는 방법론은 그게 없는 사람에게는 없는 것과 같습니다.

제품 저장소에 복사해 넣는 파일 한 벌(`templates/dev-kit`)로 배포되며, 규칙은 산문이 아니라 **훅·스크립트·서브에이전트로 강제**됩니다.

이 저장소에는 제품 코드가 없습니다. 제품별 PRD, 코드, 비밀값, 실행 로그는 각 제품의 로컬 저장소가 소유합니다.

## 무엇을 해결하나

| 문제 | 이 키트의 장치 | 강제 방식 |
|---|---|---|
| **계획 문서 여러 장이 서로 어긋난 채 구현이 시작된다** | S0 도입의 교차 대조 — 도입 시점에 한 번에 판정 | 절차 |
| **유저플로우를 상태 전이표로 착각한다** → 에이전트가 상태를 지어낸다 | S0 계약 확인 — 전이표는 어느 계획 도구도 담지 않는 별도 항목 | 절차 |
| **어느 요구사항 근거로 만드는지 추적이 안 된다** | 요구사항 ID·화면 ID 추적표 (`docs/spec/source-map.md`) | **스크립트** |
| **검증 조건 5개짜리 요구사항이 테스트 1개로 완료된다** | 매핑표 `조건 수` 칸 — 조건 하나당 테스트 하나를 기계가 요구 | **스크립트** |
| **답이 없는 칸을 남긴 채 구현을 시작한다** → 에이전트가 지어낸다 | `/ready` — Story 슬롯 12칸을 AI가 채우고 **갈리는 것만** 질문 | **절차** (12칸을 읽는 검사는 없다) |
| 그 판정을 안 하고 사이클을 연다 | 매핑표 `준비` 칸이 미달(빈 칸·`❌`·재판정)이면 사이클을 못 엽니다 | **스크립트** (칸의 값만 본다 — 12칸 자체는 안 읽는다) |
| **Story가 커서 한 에이전트가 감당 못 한다** → 영향 범위가 번진다 | `/ready` 2단계 크기 판정 — 한 문장에 트리거 하나·종료 상태 하나가 될 때까지 나눕니다 | 절차 |
| **"거부하면 어디까지 막나" 같은 도메인 규칙이 어디에도 안 적힌다** | `domain.md` 5절 비즈니스 규칙 표 — 규칙마다 "어기면 무슨 일이" | 절차 |
| **md를 사람이 읽기 어려워 판정을 미룬다** | 판정할 것이 많은 4시점에 HTML 한 장 (`docs/reports/`) | 절차 |
| **계획 도구가 없어서 시작을 못 한다** | `/plan` — 압박 → 묶어 묻기 → 작성 → 검증. 외부 의존 0 | 절차 |
| **같은 것이 상류와 저장소에 두 벌로 생겨 갈라진다** | S0 계약 확인이 소유권을 판정 — 상류가 담았으면 베끼지 않고 인용 | 절차 |
| **구현 중 문서와 코드의 정합이 조용히 깨진다** | 고아 인용·미커버 요구사항·화면 불일치·참조 깨짐 검사 | **스크립트** (`/review` 1단계) |
| **상류가 바뀐 것을 모른 채 계속 짓는다** | `/adopt --sync` → 재검토 표시 → 처리 전까지 검사 실패 | **스크립트** |
| 막히면 **검증을 약화시켜 초록불을 만든다** — 테스트 삭제, 단언 완화, 타입 무시, 예외 삼킴 | 절대 규칙 11 + 금지된 우회 표 + `/review` | **서브에이전트** (구현과 분리된 컨텍스트) |
| **보안 구멍과 부작용이 정상 경로만 통과한 채 지나간다** — 남의 것 접근, 클라이언트 값 신뢰, 범위 없는 삭제, 실패 시 열리는 권한 | 리뷰 4축 17검사 — 규칙 위반 · 보안 · 의도치 않은 동작 · 검증. 기준은 `architecture.md` 3·4절과 `domain.md` 4·5절이 이미 적어 둔 대비 | **서브에이전트** |
| 세션이 끊기면 **맥락을 잃는다** | `docs/status/STATUS.md` 스냅샷 1장 | **훅** (미갱신 시 세션 종료 차단) |
| **같은 실수를 반복한다** | 이슈 기록 → 2회차 규칙 승격 → 다음 사이클에서 걸림 | **서브에이전트** (`/ingest-errors`) |
| 기술을 임의로 고른다 | `docs/spec/stack.md` 사전 확정 | **훅** (설치 명령·매니페스트 편집 차단) |
| 비밀값이 저장소에 들어간다 | 커밋·파일 쓰기 시점 검사 | **훅** |

**훅은 산문이 아니라 실제로 막습니다.** 규칙과 훅이 어긋나면 규칙이 아니라 훅이 실제 동작입니다.
**정합성은 사람도 서브에이전트도 아니라 스크립트가 지킵니다** — 기계가 확정할 수 있는 것을 판단에 맡기지 않습니다.

## 요구사항

| | 무엇 | 없으면 |
|---|---|---|
| 필수 | **Claude Code** | 훅·커맨드·서브에이전트가 동작하지 않습니다. Codex 등 다른 에이전트는 `AGENTS.md`로 같은 규칙을 읽지만 **기계적 강제는 없습니다** |
| 필수 | **git 저장소** | 비밀값·STATUS 훅이 git을 근거로 판단하므로 검사를 건너뜁니다 |
| 권장 | **jq** (`brew install jq`) | guard 훅 2개가 경고만 남기고 통과합니다 (차단하지 않음) |
| 권장 | **python3** | HTML 리포트(`report.py`)를 못 만듭니다. **강제 장치는 전부 순수 bash라 그대로 동작합니다** |
| 선택 | **계획 도구의 MCP** (있다면) | `/adopt`가 자동 수집·`--sync` diff를 못 합니다. 파일 경로나 붙여넣기로 대신할 수 있고, 계획이 아예 없으면 `/plan`이 만듭니다 |

정합성 검사(`.claude/scripts/check-consistency.sh`)는 **MCP를 부르지 않습니다** — 저장소 안 스냅샷만 봅니다.
그래서 상류가 죽어도, CI에서도 그대로 돕니다.

개발 지식이 깊지 않아도 됩니다. 설계 단계(S1~S4)는 AI가 **사용자를 인터뷰**해서 채우는 구조입니다.

## 설치

### 1. 이 저장소를 클론합니다

```bash
git clone https://github.com/JIM00N/my_dev_method.git
```

### 2. 대상 제품 저장소에 설치합니다

```bash
my_dev_method/scripts/install-kit.sh <제품 저장소 경로>
```

출력 예시 — 무엇이 생겼는지와 이어서 할 일을 알려줍니다:

```text
dev-kit v0.6.0 → /path/to/제품저장소 (install)

  생성: CLAUDE.md
  생성: AGENTS.md
  생성: docs/ 전체
  생성: .claude/ 전체

설치 완료. 이어서 할 일:
  1. CLAUDE.md 상단 첫 두 줄(제목·한 줄 설명)을 프로젝트 것으로 바꾼다
  2. docs/status/STATUS.md에 시작 시점 기록
  ...
  5. /adopt 를 실행한다 (현재 단계 S0) — 진입점은 하나다.
       저장소 안의 계획 문서를 먼저 찾고, 없으면 밖에 있는지 묻고,
       그래도 없으면 /plan 으로 보내 키트가 직접 만든다.
```

스크립트는 **덮어쓰기 사고를 막도록** 설계되어 있습니다.

- 대상이 git 저장소가 아니거나, 작업 트리가 더럽거나, `jq`가 없으면 **경고**합니다.
- `CLAUDE.md`나 `docs/`가 이미 있으면 **중단**합니다 (이미 키트를 쓰는 저장소면 `--upgrade`를 쓰라고 안내).
- 기존 `.claude/`가 있으면 **통째로 덮지 않고 파일 단위로 병합**합니다.

### 3. 기존 `.claude/`가 있는 저장소라면

훅·커맨드·서브에이전트는 자동으로 병합되지만, **`settings.json`은 덮어쓰지 않고** 키트 판을 `.claude/settings.json.dev-kit`으로 따로 둡니다. 이 명령으로 병합하세요 (기존 항목과 자체 훅을 보존하면서 키트 훅을 더합니다):

```bash
cd <제품 저장소>/.claude
jq -s '.[0] as $a | .[1] as $b | $a * $b | .hooks = (
  ($a.hooks // {}) as $ah | ($b.hooks // {}) as $bh |
  reduce ((($ah|keys) + ($bh|keys)) | unique)[] as $k
    ({}; .[$k] = (($ah[$k] // []) + ($bh[$k] // []))))' \
  settings.json settings.json.dev-kit > merged.json \
  && mv merged.json settings.json && rm settings.json.dev-kit
```

### 4. 손으로 설치하려면

```bash
cd <제품 저장소>
cp /경로/my_dev_method/templates/dev-kit/CLAUDE.md .
cp /경로/my_dev_method/templates/dev-kit/AGENTS.md .
cp -R /경로/my_dev_method/templates/dev-kit/docs .
cp -R /경로/my_dev_method/templates/dev-kit/.claude .      # 기존 .claude/가 있으면 이 줄은 쓰지 않는다
```

`cp -R`은 동명 파일(특히 `settings.json`)을 말없이 덮어씁니다. 기존 `.claude/`가 있으면 하위 폴더만 복사하고 위 3번의 병합을 하세요. 훅 실행 권한(755)은 커밋되어 있어 `chmod`가 필요 없습니다.

### 5. 설치 후 할 일

1. `CLAUDE.md` 상단 첫 두 줄(제목·한 줄 설명)을 프로젝트 것으로 바꿉니다.
2. `docs/status/STATUS.md`에 시작 시점을 기록하고 현재 단계를 `S1`로 둡니다.
3. Claude Code를 열고 `/hooks`로 훅 3개가 등록됐는지 확인합니다.
4. **`/adopt`로 시작합니다.** 계획 문서가 있든 없든 진입점은 이것 하나입니다.

## 처음 한 바퀴 — `/adopt` 하나로 시작합니다

**계획 문서가 있든 없든 진입점은 `/adopt` 하나입니다.** 특정 계획 도구를 전제하지 않습니다.

| 단계 | AI가 하는 일 | **사람이 하는 일** |
|---|---|---|
| S0-1 **찾기** | **저장소 안을 먼저 뒤진다** (`docs/`·`doc/`·`spec/`·루트 `*.md`). 없으면 밖에 있는지 묻고, 그래도 없으면 `/plan`으로 | **찾은 목록에서 고른다** |
| S0-2 수집 | `docs/upstream/`에 스냅샷·출처·해시 기록 | — |
| S0-3 **교차 대조** | 문서가 여럿이면 서로 어긋난 곳을 목록으로 뽑는다 | **어느 쪽이 맞는지 판정한다** |
| S0-4 ID 정리 | **상류가 붙인 ID를 그대로 옮긴다.** 없는 것(화면 등)만 부여 | — |
| S0-5 조건 수 세기 | 요구사항마다 검증 조건 개수를 세어 매핑표에 적는다 | — |
| S0-6 **계약 확인** | 항목마다 상류를 뒤져 `상류 보유 / 갭 / 해당 없음` 판정 | 확인 |
| S0-7 **갭만 인터뷰** | `❌ 갭`인 것만 묻는다 (대개 상태 전이표·스택·검사 명령) | 답한다 (S1~S5 전체가 아니라 이것만) |
| S6 구축·검수 | TDD 구현 → `/review` → 수정 | **검수 시나리오를 직접 누른다**, 리뷰 반영을 판정한다 |

**S0-1이 사용자에게 묻기 전에 저장소를 뒤지는 이유**: 사실은 에이전트가 찾습니다.
저장소에 이미 PRD가 있는데 "계획 있으세요?"부터 물으면 같은 것을 또 만들게 됩니다.

**S0-3이 가장 큰 이득입니다.** 계획 문서가 따로 생성됐다면 서로 안 맞는 곳이 반드시 있고,
그걸 도입 시점에 정리하지 않으면 구현 중에 *"어느 문서가 맞나"*로 매번 멈춥니다.

**S0-6이 "확인"인 이유**: 상류가 무엇을 담는지는 도구마다 다릅니다. 기능마다 권한·데이터 정의를
채워 주는 도구도 있습니다. 그걸 모른 채 저장소에 또 쓰면 **같은 것이 두 벌**이 되고,
상류가 바뀌는 순간 갈라집니다 — 갈라짐을 막으려던 표가 갈라짐을 만듭니다.
그래서 단정하지 않고 확인하고, **그 판정이 정본 소유권까지 정합니다.**

그리고 **유저플로우는 상태 전이표가 아닙니다.** 화면 이동(A → B)이지 데이터 상태 전이(접수 → 진행중)가 아닙니다.
전이표가 없으면 *"결제 화면에서 뒤로 가면 주문 데이터는 무슨 상태가 되나"*에 답이 없고,
답이 없으면 에이전트는 멈추지 않고 그 자리에서 지어냅니다. 그게 일탈의 진원지라서
**어느 계획 도구도 담지 않는 이 항목만은 거의 항상 갭으로 나옵니다.**

## 계획 문서가 없을 때 — `/plan`이 만듭니다

`/adopt`가 아무것도 못 찾으면 `/plan`으로 보냅니다. **외부 도구가 없어도 여기서 막히지 않습니다.**

| 단계 | 하는 일 | 왜 |
|---|---|---|
| P1 **압박** | 동의도 칭찬도 하지 않고 아이디어를 친다. 끝에 **강해졌다 / 기각 / 이해만 깊어졌다** 중 하나를 명시 | 안 버티는 아이디어를 잘 정리해 봐야 잘 정리된 채로 실패한다 |
| P2 **묶어 묻기** | 지금 답할 수 있는 질문을 한꺼번에, 각각 추천안과 함께 | 하나씩 던지면 왕복이 열 번 넘게 늘고 사용자가 지친다 |
| P3 작성 | `docs/upstream/plan.md` — 요구사항 + **검증 조건 목록** + 화면 + 비목표 + 부작용 지표 | 이 다섯이 하류(구현·검사)의 연료다 |
| P4 검증 | 7가지를 `튼튼함/쓸 만함/얇음/깨짐`으로 판정. **깨짐이 남으면 못 끝낸다** | 칸 채우기로는 쓸 수 없는 계획이 통과한다 |
| P5 넘기기 | `/adopt`로 넘어가 매핑표를 만든다 | 키트가 만들었어도 "요구사항이 태어난 곳"의 자리는 같다 |

**`/plan`이 외부 도구와 다른 점**: 산문으로 잘 쓰인 계획서가 아니라 **기계가 셀 수 있는 형태**로 만듭니다 —
요구사항마다 ID가 붙고, 검증 조건이 목록으로 쪼개져 있어야 검사기가 "조건 5개인데 테스트 1개"를 잡습니다.

그다음 나머지 단계는 갭이 가리키는 것만 폅니다. 전체를 처음부터 밟고 싶으면 `/stage 1`부터 시작할 수도 있습니다 —
AI가 `docs/status/STATUS.md`를 읽고 현재 단계 가이드 하나만 읽은 뒤 인터뷰를 시작합니다.

| 단계 | AI가 하는 일 | **사람이 하는 일** |
|---|---|---|
| S1 문제·범위 | 인터뷰 질문, `docs/spec/product.md` 작성 | 답한다. **"만들지 않을 것"을 정한다** |
| (프로파일 판정) | 난이도 사분면으로 Lite/Standard/Full 판정 | 확인 — 개인 도구면 절차가 자동으로 줄어든다 |
| S2 도메인·상태 | 데이터·상태 전이표 설계 | 업무가 실제로 어떻게 흐르는지 답한다 |
| S3 인터페이스 | 화면·API·CLI 표면 설계 | 뭐가 보여야 하는지 답한다 |
| S4 구조·스택 | 기술 선택지를 장단점과 함께 제시 | **고른다** (모르면 추천안 채택) |
| S5 시각 설계 | 목업 생성 (화면 없으면 스킵) | 눌러 보고 어색한 곳을 지적한다 |
| S6 구축·검수 | TDD 구현 → `/review` → 수정 | **검수 시나리오를 직접 누른다**, 리뷰 반영을 판정한다 |

역할 분담은 하나입니다 — **문서는 에이전트가 쓰고, 사람은 답하고 누르고 판정합니다.** 문서 정합성(정본·경로·양식·아카이브)은 구조와 훅이 지키므로 사람이 신경 쓸 일이 아닙니다.

S1~S4는 설계이므로 추론을 가장 높게 씁니다(Claude Code `ultrathink`). 여기 품질이 전체 결과를 결정합니다. S5~S6에서는 "구현 → 검수 요청 → 피드백 → 수정" 루프로 모드가 바뀝니다.

## 매일 쓰는 법

| 커맨드 | 언제 | 하는 일 |
|---|---|---|
| `/adopt` | **프로젝트 시작 (계획 문서 유무와 무관)** | 찾기 · 수집 · 교차 대조 · ID 정리 · 조건 수 세기 · 계약 확인 |
| `/plan` | `/adopt`가 계획 문서를 못 찾았을 때 | 압박 → 묶어 묻기 → 작성 → 검증 → `/adopt`로 넘김 |
| `/ready` | **Story를 열기 직전** | 슬롯 12칸을 AI가 채움 → **크기 판정** → 갈리는 것만 질문 → 정본에 반영 |
| `/adopt --sync` | **사이클을 시작할 때마다** | 상류를 다시 받아 바뀐 요구사항을 재검토로 표시 |
| `/stage [n]` | 세션 시작 · 단계 진입 | STATUS를 읽고 현재 가이드 하나만 읽은 뒤 모드를 맞춘다 |
| `/review` | **구현 한 덩어리가 끝날 때마다** | 1단계 정합성 기계 검사 → 2단계 `code-review` 서브에이전트 |
| `/ingest-errors` | 에러 기록이 쌓였을 때 | `error-learning` 서브에이전트가 2회차 문제를 규칙으로 승격 |
| `/cycle-close` | 사이클 종료 | DoD 대조·리뷰·검사 실행·드리프트 대조·학습 인제스트·아카이브를 순서대로 |

세션의 리듬:

```text
사이클 시작  /adopt --sync — 상류가 바뀐 걸 모른 채 지으면 다 지은 뒤에 뜯는다
세션 시작   /stage        — 어제 어디까지 했는지 설명할 필요가 없다
구현 덩어리  /review       — 검사 명령이 초록이어도 리뷰 전에는 끝난 게 아니다
세션 끝     STATUS 갱신    — 잊으면 훅이 종료를 막으며 갱신할 목록을 알려준다
사이클 끝   /cycle-close  — 종료 점검을 순서대로 (개수는 커맨드가 정본이다)
```

역할 분담이 핵심입니다. **문서 정합성은 스크립트가** 확정적으로 잡고(고아 인용·미커버 요구사항·참조 깨짐),
**판단이 필요한 것만 서브에이전트가** 봅니다(검증 우회·스펙 드리프트·권한 경로). 그리고 리뷰와 에러 학습을
**구현한 에이전트가 직접 하지 않는 것** — 구현한 컨텍스트는 자기 우회를 보지 못합니다.

## 훅이 막았을 때

**우회하지 않습니다.** 막힌 데는 이유가 있고, 우회 금지가 이 방법론의 존재 이유입니다.

| 막힌 것 | 왜 | 무엇을 하면 되나 |
|---|---|---|
| 패키지 설치 · 매니페스트 편집 | `docs/spec/stack.md` 결정 표에 없는 기술 | 사용자에게 선택지·근거를 제시해 승인받고, 결정 표에 추가한 뒤 다시 시도 |
| `git commit` · 파일 쓰기 | 비밀값 형태 문자열 또는 비밀 파일 감지 | 값을 환경 변수로 옮기고 `.gitignore` 확인. 이미 푸시됐으면 **키를 폐기·재발급** |
| 세션 종료 | 변경이 있는데 STATUS의 "최종 갱신"이 오늘이 아님 | STATUS의 최종 갱신·지금 하는 일·다음 3가지를 채우고 다시 종료 |

훅은 **판단하지 못하면 통과시키되 침묵하지 않습니다**(도구 없음·git 아님·파싱 실패 시 stderr 경고). 진짜 오탐이면 훅을 끄지 말고 좁히세요 — 끄면 규칙이 산문으로 되돌아갑니다. 한 건짜리 예외는 `docs/spec/code-conventions.md` 5-1의 예외 표에 기록하고 진행합니다.

## 정합성 검사가 실패했을 때

| 실패 | 무슨 뜻인가 | 무엇을 하면 되나 |
|---|---|---|
| `스냅샷이 수집 이후 변경됨` | `docs/upstream/`의 상류 사본을 손으로 고쳤습니다 | 상류에서 고치고 `/adopt --sync`로 다시 받습니다. 사본을 고치면 다음 동기화에서 조용히 사라집니다 |
| `완료인데 테스트가 없다` | 요구사항을 ✅로 올렸는데 검증하는 테스트 이름이 없습니다 | 테스트를 추가하거나, 완료가 아니면 상태를 되돌립니다 |
| `상류 변경 재검토가 남아 있다` | `--sync`가 표시한 것을 아직 판정하지 않았습니다 | 딸린 전이표·권한 행·테스트를 갱신한 뒤 재검토 칸을 비웁니다 |
| `고아 인용: R-0xx` | 사이클·테스트·코드가 인용한 ID가 매핑표에 없습니다 | 오타면 고치고, 새 요구사항이면 상류에 넣고 `--sync` |
| `SC-0xx … interface.md에 없다` | 화면 매핑표와 표면 목록이 어긋났습니다 | 둘 중 맞는 쪽으로 맞춥니다 |

**검사를 약화시켜 통과시키지 않습니다.** 오탐이면 스크립트의 조건을 좁히고, 끄지 않습니다 — 끄는 순간 정합성이 다시 사람 몫이 됩니다.

## 절차량 조절 — 프로파일

개인 도구 하나에 20개 문서와 6단계 DoD를 요구하면 방법론은 **일부만 지켜지는 게 아니라 통째로 버려집니다.** S1의 난이도 사분면이 절차량을 정합니다.

| 사분면 | 프로파일 |
|---|---|
| 나만 쓴다 × 내 컴퓨터에서만 | **Lite** — 설계 문서 축약 |
| 나만 쓴다 × 원격에서도 / 남도 쓴다 × 내 컴퓨터에서만 | **Standard** |
| 남도 쓴다 × 원격에서도 | **Full** — 줄이지 않는다 |

민감정보를 다루면 사분면과 무관하게 Full입니다. 축약은 각 가이드 **DoD의 프로파일 표식**(`(Standard+)`·`(Full)`)으로만 존재합니다.

**Lite에서도 줄이지 않는 것**: 비목표 · 상태 전이표 · `stack.md` · 자동 테스트 · 이슈 기록과 2회차 규칙 승격 · STATUS 갱신 · 검증 우회 금지. Lite는 **설계 문서를 줄이는 것**이지 검증과 학습을 줄이는 것이 아닙니다.

## 업그레이드

배포본의 버전은 `CLAUDE.md` 첫 줄의 `<!-- dev-kit v… -->` 스탬프로 확인합니다.

```bash
my_dev_method/scripts/install-kit.sh <제품 저장소 경로> --upgrade
```

**키트 소유 파일만** 교체되고, 프로젝트가 채운 spec 내용·사이클·이슈·STATUS·ADR은 건드리지 않습니다. `CLAUDE.md`는 프로젝트명과 §6 고유 규칙이 있어 자동 교체하지 않고 `CLAUDE.md.dev-kit-new`로 두므로, diff로 비교해 규칙 부분만 옮기고 지우세요.

`cp -R docs .`를 다시 실행하면 **프로젝트가 쌓아온 증거가 전부 파괴됩니다.** 소유권 구분표는 [templates/dev-kit/README.md](templates/dev-kit/README.md)에 있습니다.

## 문제가 생기면

| 증상 | 원인·조치 |
|---|---|
| 훅이 전혀 동작하지 않는다 | Claude Code에서 `/hooks`로 등록 확인. 기존 `.claude/settings.json`에 병합하지 않았을 가능성이 큽니다 |
| `jq가 없어 …검사를 건너뛴다` 경고 | `brew install jq`. 없으면 guard 훅 2개가 통과만 합니다 |
| 훅이 정상 작업을 막는다 | 오탐이면 `code-conventions.md` 5-1 예외 표에 한 건 기록 후 진행. 반복되면 훅을 끄지 말고 조건을 좁히세요 |
| STATUS 훅이 계속 막는다 | 같은 세션에서 두 번 연속 막지 않습니다. `**최종 갱신**`을 오늘 날짜로 고치면 통과합니다 |
| 절차가 무겁게 느껴진다 | 프로파일을 낮추지 말고 `docs/guides/profiles.md`로 **확인**하세요. 표식 없는 DoD 항목은 모든 프로파일이 봅니다 |
| `/adopt`가 상류를 못 가져온다 | MCP 인증을 확인하세요 (`claude mcp login <이름>`). 안 되면 파일 경로나 붙여넣기로 진행해도 됩니다 — 스냅샷만 저장소에 남으면 검사는 그대로 돕니다 |
| 정합성 검사가 `도입 전`이라고만 한다 | `docs/spec/source-map.md`에 요구사항 행이 없습니다. `/adopt`를 먼저 실행하세요 |

## 적용 원칙

- 목적·범위·권한·중요 위험을 바꾸지 않는 질문은 하지 않습니다.
- 새롭고 되돌리기 어려운 결정은 학습 모드로, 이미 배운 기본값은 실행 모드로 진행합니다.
- **초록불을 만들기 위해 검증을 약화시키지 않습니다.** 테스트 삭제·단언 완화·타입 무시·예외 삼킴은 통과가 아닙니다.
- 서비스 페르소나의 권한과 개발 에이전트의 작업 권한을 분리합니다. Story 문서가 그 계약입니다.
- 병렬 구현은 데이터·권한·API·코드 컨벤션·파일 소유권이 확정된 뒤에만 합니다.
- 산문 규칙은 드리프트하므로, 지킬 수 있는 것은 **훅으로 강제**하고, 문서 정합성은 **스크립트가 기계로** 확정하고, 그래도 남는 판단은 **별도 서브에이전트 컨텍스트**가 잡습니다.
- 계획을 뽑아내는 일은 **상류 도구에 맡깁니다.** 이 키트는 상류 산출물을 받아 구현·정합·리뷰를 맡습니다.
- 상류와 저장소가 둘 다 갱신되더라도 **항목 단위로 정본이 하나**이면 갈라지지 않습니다 (`docs/spec/source-map.md` 1절).
- 제품 코드·테스트·서비스 실행은 제품의 **로컬 개발 환경**에서만 합니다.

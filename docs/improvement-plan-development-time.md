# 개발 시간 단축을 위한 방법론 개선 설계

작성일: 2026-09-08

상태: **상세 개선 계획. 이 문서의 제안은 아직 운영 규칙이나 검사기에 반영되지 않았다.**

대상: 이 저장소가 배포하는 dev-kit의 계획·설계·질문·진행 보고·구현 준비·검증 절차

## 1. 목적과 사용자 요구

가장 중요한 목표는 **기능 요청부터 사용자가 검수할 수 있는 결과까지 걸리는 시간을 줄이는 것**이다.
계획서를 빨리 쓰거나 코드 작성을 빨리 끝내는 것만으로 달성했다고 보지 않는다.
계획, 질문 읽기와 답변, 대기, 구현, 검증, 수정, 재검수에 드는 시간을 함께 본다.

이번 대화에서 사용자가 요구한 방향은 다음과 같다.

1. 개발에는 스프린트 배치 외에도 기능별 권한·예외·데이터 등 다양한 결정이 필요하다.
2. 기존에 참고하던 Manyfast처럼 기능을 세분화하고 실제 동작까지 고려할 수 있어야 한다.
3. 가장 중요한 판단 기준은 개발 시간 단축이다.
4. 질문 대기는 구현 중 다른 일을 하는 방식뿐 아니라 **계획 단계에서 질문을 구성하는 방식 자체로 줄여야 한다.**
5. 질문이나 보고를 `D-10` 같은 내부 ID로 전달하면 사용자가 의미를 다시 찾아야 한다. 이 이해 비용을 줄여야 한다.
6. 구현에 앞서 개선 방법을 충분히 구체화한 문서로 남긴다.

이 문서는 위 요구를 실현하기 위한 제안이다. 모든 세부 정책이 사용자에게 개별 승인된 것으로 해석하지 않는다.
특히 제품의 권한·삭제·외부 행동 정책은 이 문서의 사례를 실제 제품 기본값으로 자동 채택하지 않는다.

- 위험·미결정 사항·완료 조건: 20~22절

## 3. 현재 구조에서 확인한 사실

2026-09-08 작업 트리의 문서와 코드를 기준으로 확인했다. 작업 트리에는 기존의 미커밋 보완이 있다.
현재 제공되는 기능과 이번에 제안하는 기능을 구분하며, 아래 비용 후보가 실제 시간을 얼마나 쓰는지는 아직 측정하지 않았다.

| 현재 구조 | 이미 갖춘 점 | 시간 관점의 보완 지점 |
|---|---|---|
| 자체 계획의 요구사항 → 기능 → 사양 | 기능 목록만 쓰고 구현으로 넘어가는 것을 줄인다 | 모든 후속 기능까지 상세 작성하면 계획 비용이 커진다. 현재 범위와 공통 결정에 집중해야 한다 |
| 역할별 권한 표 | 허용·금지·거부 동작을 초기 계획에서 다룬다 | 기능·소유권·상태별 실제 사례가 충분한지는 별도 판단이다 |
| Story의 준비 슬롯 12개 | 권한·데이터·예외·규칙과 실행 준비를 함께 확인한다 | 같은 판단을 표·권한 계약·비교 JSON·검증 표에 반복 기록할 수 있다 |
| 기존 자료 탐색과 결정 재사용 | 이미 있는 답을 다시 묻지 않도록 한다 | 실제 질문·리포트가 기존 결정과 새 결정을 구분해 보여주도록 구체화할 필요가 있다 |
| 의존 질문을 다음 라운드로 미루는 규칙 | 무의미한 조건부 질문을 줄인다 | 함께 제안할 수 있는 동작도 직렬 질문으로 나누면 왕복이 늘어난다 |
| 단계별 사용자 확인 | AI가 임의로 제품 결정을 확정하는 것을 줄인다 | 같은 내용에 대한 진행 확인·계획 승인·준비 승인 등이 반복될 수 있다 |
| 영향 분류에 따른 문서 선택 | 변경과 무관한 설계 문서를 매번 다시 쓰지 않는다 | 초기 계획의 검토 대상 선정과 사용자 설명에도 연결해야 한다 |
| 파일 전체 해시에 따른 준비 판정 | 변경 후 오래된 판정을 그대로 쓰는 것을 줄인다 | 공백·진행 상태·무관한 계약 변경에도 재판정 범위가 커질 수 있다 |
| HTML 리포트 | 많은 내용을 한 화면에서 확인할 수 있다 | 문서를 펼쳐 보여주는 것만으로 사용자의 이해 부담이 줄었다고 볼 수 없다 |
| 파일럿 지표 | 재작업·질문·오탐·검사 시간을 기록할 수 있다 | 계획 확정 시간·전체 경과 시간·설명 재요청·반복 질문을 더해야 한다 |

## 4. 성공 기준과 시간의 정의

### 4.1. 최적화할 시간

**주지표: 현재 범위가 주어진 시점부터 검수 가능한 결과가 나온 시점까지의 경과 시간.**
검수에서 수정이 필요했다면 최종 검수 완료까지의 시간도 별도로 기록한다.

그 안에서 먼저 줄일 것은 다음 두 가지다.

1. 계획 시작 → 구현 가능한 계획 확정까지의 경과 시간.
2. 사용자가 질문을 이해하고 판단하고 답하는 데 쓰는 실제 작업 시간.

구현·검증·재작업 시간은 질문을 줄인 부작용이 뒤로 옮겨가지 않았는지 확인하는 지표다.
미리 계획 가능한 질문을 구현 후에 하는 방식으로 계획 시간만 줄이지 않는다.

### 4.2. 합산할 수 있는 것과 없는 것

- 계획 작성·문서 관리·구현·검증·재작업에 실제로 쓴 작업 시간은 겹치지 않는 구간으로 분류한다.
- 사람과 AI의 동시 작업 시간은 각각 기록할 수 있지만 그대로 합쳐 전체 경과 시간이라 하지 않는다.
- 응답 대기 중 독립 작업을 진행한 시간은 전체 대기 시간과 겹칠 수 있다.
- 질문 발송부터 답변까지의 시간과, 답을 기다리느라 실제 작업이 멈춘 시간은 구분한다.
- 휴식·야간·사용자 부재가 포함된 경과 시간과 실제 작업 시간은 둘 다 보존한다.

### 4.3. 성공이라고 보지 않는 것

- 질문을 한 메시지에 스무 개 넣고 왕복이 한 번이라고만 보고하는 것.
- 내용을 설명하지 않고 추천안으로 자동 확정하여 질문 수를 줄이는 것.
- 검증을 생략하거나 미결정 요구사항을 누락하여 빨리 끝내는 것.
- 문서와 보고를 더 많이 만들고 체계가 좋아졌다는 이유만으로 개선을 선언하는 것.
- 합성 리허설 결과로 실제 제품의 개발 시간 절감률을 주장하는 것.

## 5. 설계 원칙

1. **질문 전에 AI가 일을 한다.** 사실 조사, 기존 결정 대조, 동작 초안 작성, 충돌 탐색을 먼저 수행한다.
2. **사용자가 기억해야 할 것을 줄인다.** 질문과 보고는 그 메시지만으로 이해할 수 있어야 한다.
3. **연결된 결정을 함께 제안한다.** 간단한 후속 분기는 완성된 동작 제안 안에 포함한다.
4. **결정을 한 번 기록하고 재사용한다.** 적용 범위가 같고 근거가 변하지 않았으면 재승인하지 않는다.
5. **현재 범위를 깊게, 후속 범위를 얕게 계획한다.** 여러 기능에 영향을 주는 공통 결정은 먼저 한다.
6. **제품 동작의 정본은 한 곳에 둔다.** 사람용 리포트와 기계용 연결 정보를 독립 사본으로 관리하지 않는다.
7. **수량보다 충분함을 본다.** 12칸을 채웠거나 질문이 적다는 사실만으로 준비됐다고 판정하지 않는다.
8. **검사가 실제로 보장하는 범위를 적는다.** 구조 검사는 구조를, 의미 검토는 판단을 맡는다.
9. **이 문서의 개선도 비용을 낸다.** 큰 엔진 개편은 관측된 비용과 구현·유지 비용을 비교한 뒤 진행한다.

## 6. 개선 후 전체 흐름

| 순서 | AI가 하는 일 | 사용자가 보는 것 | 다음으로 넘기는 조건 |
|---|---|---|---|
| 자료 확인 | 계획·코드·기존 정책·사용자 결정을 조사 | 필요하면 현재 이해와 핵심 공백 요약 | 이미 있는 답과 새 결정이 구분됨 |
| 범위와 공통 정책 초안 | 이번 결과, 비목표, 역할·소유권·핵심 데이터·상태를 초안으로 연결 | 사용 가능한 제품 동작 중심의 제안 | 현재 범위와 공통 경계가 설명 가능함 |
| 기능 흐름 예행 검토 | 정상·거부·취소·실패를 따라가며 미정을 찾음 | 아직 모든 내부 검토를 보여주지 않음 | 뒤에서 나올 질문 후보가 모임 |
| 질문 정리 | 기존 답 적용, 중복 제거, 동작별 결정 묶음 작성 | 추천 구성과 실제 선택 차이 | 사용자가 판단할 내용만 남음 |
| 결정과 수정 | 답을 관련 정책·사례 전체에 반영 | 수정된 내용과 파급 효과 | 미결정이 현재 범위를 막지 않음 |
| 계획 확정 | 구체적인 초안·잔여 가정·비목표를 함께 제시 | 무엇을 만들지와 바꿀 부분 | 새 제품 결정에 대한 확인이 확보됨 |
| 구현 준비 확인 | 기존 결정의 반영, 사례·테스트·의존 연결 검증 | 새 충돌이 있을 때만 결정 요청 | 현재 범위의 구현 근거가 충분함 |
| 구현·검수 | 사례에 따라 구현·검증, 결과 보고 | 실제 동작·확인 결과·남은 일 | 검수 가능한 결과와 증거가 있음 |

단계 이름이 다르다는 이유로 사용자 대화를 매번 끊지 않는다.
문서의 소유 위치와 인터뷰 순서는 별개다. 예를 들어 데이터 삭제 정책은 도메인 문서가 소유하더라도,
계획 초안에서 사용자에게 미리 제안하고 그 결정이 맞는 위치에 기록되도록 할 수 있다.

## 7. 계획 단계에서 구현 중 질문을 미리 찾는 방법

### 7.1. 대상 범위

- 이번에 실제로 만들 기능의 사용자 결과를 끝까지 따라간다.
- 후속 기능 전체를 미리 구현 수준으로 설계하지 않는다.
- 여러 기능을 관통하는 권한, 데이터 관계, 상태, 외부 연동 경계는 현재 범위에서 필요한 만큼 먼저 정한다.
- 기존 프로젝트는 승인된 현재 동작에서 무엇이 달라지는지를 먼저 확인한다.

### 7.2. 기능별 검토 대상 선정

각 기능에 대해 아래 항목의 적용 여부와 근거를 확인한다. 질문 목록이 아니라 AI가 사용하는 검토 기준이다.
기존 영향 분류를 재사용하고, 이 목록을 기능마다 사용자에게 그대로 답하게 하지 않는다.

| 조건 | 검토할 결정 | 완료 근거 예 |
|---|---|---|
| 사용자·조직 데이터 접근 | 본인·타인·타 조직, 조회·수정·공유, 검사 위치 | 적용 정책과 허용·거부 사례 |
| 장치 권한이나 데이터 처리 동의 | 요청 시점, 거부·철회 후 동작, 처리 범위 | 접근 권한과 처리 동의가 구분된 흐름 |
| 데이터 생성·수정·삭제 | 필수값, 동일성, 관계, 동시 수정, 보관·복구 | 데이터 정의와 실패·중복 사례 |
| 상태를 가진 작업 | 시작·종료, 금지 전이, 취소, 재시도, 되돌림 | 상태 전이와 사례 연결 |
| 외부 API·결제·발송 | 실패·시간 초과, 중복 방지, 부분 성공, 재시도 | 외부 경계별 결과와 확인 방법 |
| 화면·입력 | 빈 상태, 로딩, 오류, 권한 없음, 입력 오류 | 사용자가 보게 될 결과 |
| 대량 데이터·파일·반복 처리 | 예상 규모, 처리 시간·용량·비용 한도 | 수치 또는 실험으로 확인할 조건 |
| 기존 사용자·데이터에 변경 | 호환성, 이관, 이전 데이터 처리, 되돌림 | 변경 전후 동작과 이관 검증 |
| 민감 데이터 | 접근·저장·보관·삭제·외부 전달 범위 | 제품에 필요한 정책과 검증 대상 |
| 다국어·여러 시간대·접근성 요구 | 해당 사용자와 환경, 표시·입력·조작 조건 | 적용 범위와 대표 검수 사례 |
| 운영 중 지속 실행 | 관측, 알림, 백업, 복구, 운영 주체 | 실패를 알아내고 복구하는 방법 |

위 표는 최소 검토 후보이며 모든 도메인을 완전히 포괄한다고 주장하지 않는다.
조건이 불확실하면 곧바로 해당 없음으로 처리하지 않고 자료 확인·실험·질문 중 하나로 보낸다.
제품에 특수한 결정이 있으면 기존 항목에 억지로 끼우지 말고 추가한다.

### 7.3. 흐름을 따라 던지는 내부 질문

1. 누가 어떤 조건에서 시작하는가?
2. 입력이나 권한이 부족하면 어디까지 진행하는가?
3. 중간에 취소·종료·연결 끊김이 발생하면 무엇이 남는가?
4. 같은 동작이 반복되거나 동시에 실행되면 무엇이 달라지는가?
5. 성공·거부·실패 후 데이터와 화면은 각각 어떤 상태인가?
6. 사용자는 결과를 어떻게 확인하는가?
7. 개발자는 어떤 테스트나 실행 실험으로 결정이 지켜졌음을 확인하는가?

이 질문들에 대한 초안이 기존 자료에서 나오면 사용자에게 다시 묻지 않는다.
합리적인 선택이 여럿 남고 선택에 따라 제품 동작이 바뀌면 질문 후보로 올린다.

### 7.4. 기술적 미정은 짧은 실험으로 해소

외부 API의 실제 응답, 파일 형식 지원, 기존 코드의 동작처럼 확인 가능한 것은 실험한다.
실험에는 확인할 가설·최소 방법·종료 조건을 먼저 둔다. 무기한 조사로 계획 시간을 늘리지 않는다.
제품 정책이나 사용자 선호를 기술 실험으로 대신 결정하지 않는다.

## 8. 질문 후보를 줄이고 묶는 규칙

### 8.1. 질문 후보의 처리 순서

| 분류 | 처리 | 사용자에게 묻는 조건 |
|---|---|---|
| 자료로 확인할 사실 | 파일·코드·실행 결과에서 확인 | 접근 불가 등으로 필요한 사실을 얻을 수 없을 때 |
| 기존 결정이 적용됨 | 결정의 적용 범위와 재검토 조건을 확인한 뒤 재사용 | 새로운 예외나 충돌이 있을 때 |
| 위임된 구현 선택 | 기존 제약 안에서 선택하고 필요할 때 짧게 보고 | 위임 범위를 벗어나거나 제품 정책을 바꿀 때 |
| 새로운 제품 결정 | 추천안과 대안을 구체적인 동작으로 제시 | 현재 범위를 구현하려면 결정이 필요할 때 |
| 후속 범위의 미정 | 결정이 필요한 시점과 이유를 남김 | 현재 구조나 구현에 영향을 주기 시작할 때 |

승인되지 않은 가정을 기존 결정으로 승격하지 않는다. 사용자 답이 모호하면 영향을 받는 부분만 확인한다.

### 8.2. 함께 제안할 수 있는 조건부 결정

기존의 “앞선 답에 의존하면 다음 라운드” 규칙을 다음처럼 바꾸는 것이 제안이다.

> 후속 분기가 단순하고 사용자가 한 동작 구성으로 이해할 수 있으면 추천 구성에 포함한다.
> 설명이 복잡해지거나 독립적인 중요한 선택을 감추게 되면 나누어 묻는다.

예를 들어 여러 파일 선택·파일별 진행률·일부 실패 시 계속 처리·실패 파일만 재시도는 한 사용자 행동으로 제안할 수 있다.
권한 확대·외부 공유·유료 결제를 묶어서 한 번의 포괄 승인으로 처리하는 것은 피한다.

### 8.3. 질문 작성 형식

질문 하나는 다음 요소를 짧게 갖는다.

1. 사용자가 이해할 수 있는 결정 제목.
2. 결정이 필요한 상황과 현재 동작.
3. 추천하는 구체적인 동작.
4. 선택을 바꿀 만한 중요한 차이: 범위·사용 경험·비용·권한 등.
5. 답변 방법: 제안 수용, 다른 선택, 일부 수정.

정보가 많으면 요약을 먼저 보여주고 상세 근거는 펼쳐볼 수 있게 한다.
질문 메시지가 독립적으로 이해된다면 앞선 긴 대화나 ID 목록을 다시 읽게 하지 않는다.

### 8.4. 질문 묶음 크기

권장 시작값은 한 번에 서로 독립적인 결정 묶음 1~3개다. 강제 상한이나 성공 지표로 쓰지 않는다.
세 개라도 설명이 길면 줄이고, 매우 단순한 확인들은 함께 제시할 수 있다.
판단 기준은 메시지 개수보다 사용자가 한 번에 정확하게 결정할 수 있는지다.

### 8.5. 답변을 받은 뒤

- 사용자가 바꾼 부분과 유지한 부분을 구분한다.
- 답이 권한·데이터·상태·표시·테스트 중 어디에 영향을 주는지 AI가 전파한다.
- 같은 결정에서 파생된 기능마다 다시 승인받지 않는다.
- 새 충돌이 발견되면 기존 답을 인용한 자연어 설명과 달라진 조건을 함께 제시한다.
- 사용자 부재나 시간 경과를 답으로 해석하지 않는다.

## 9. 반복 승인과 단계 통과 질문 줄이기

### 9.1. 제거하거나 통합할 질문

| 현재 발생할 수 있는 확인 | 제안하는 처리 |
|---|---|
| 더 물을 게 없으니 문서를 써도 되는가 | 구체적인 초안을 먼저 만들고 미결정과 함께 제시 |
| 이미 답한 내용을 계획에 적었는데 맞는가 | 결정 내용이 그대로면 반영 사실만 보고 |
| 계획을 다음 문서에 옮겼으니 다시 승인해 달라 | 원래 결정 근거를 연결하고 AI가 반영 여부 확인 |
| 같은 정책이 적용되는 다른 Story의 권한 승인 | 정책 적용 범위가 같으면 재사용 |
| 리포트를 만들었으니 열어봤는가 | 실제 판단할 결과·결정이 있는지에 따라 요청 |

제품의 새 선택, 중요한 변경, 실제 수동 검수, 외부 행동 승인은 단순한 단계 진행 확인과 다르다.
계획 내용에 동의했다는 사실을 배포·발송·결제 등 외부 행동의 실행 승인으로 확대하지 않는다.
기존 커밋 승인과 독립 리뷰 정책도 이 계획만으로 변경하지 않는다.

### 9.2. 결정 재사용에 필요한 최소 정보

- 사람이 읽는 결정명.
- 선택된 제품 동작.
- 적용 대상과 조건.
- 결정 근거와 사용자의 확인 위치.
- 다시 검토해야 하는 조건.

기존 정본·ADR·승인 근거에 이 정보가 있으면 새로운 의사결정 문서를 추가하지 않는다.
부족한 필드만 기존 기록에 보완하는 것을 먼저 선택한다.

### 9.3. 준비도 승인의 변경 방향

기존 `/mdm-ready`는 초안 전체를 사용자에게 확인받는 흐름이다.
제안은 기존 승인 내용의 단순 재현과 새로운 판단을 구분하는 것이다.

- 기존 승인과 일치하고 입력이 유효함: 연결·일관성 검증 후 사용.
- 승인된 동작을 구현하기 위한 위임 범위 안의 선택: AI가 판단.
- 새 제품 동작·정책 변경·충돌: 그 부분만 사용자에게 제시.
- 테스트나 기술 실험 결과가 원래 가정을 깨뜨림: 영향과 대안을 설명하고 재결정.

이 변경은 가이드 문구만 고쳐서는 안 된다. 커맨드·양식·준비 증거가 같은 구분을 사용하도록 함께 수정해야 한다.

## 10. 학습 설명과 빠른 결정의 균형

새 기술이 등장했다는 이유만으로 긴 학습 대화를 자동 시작하면 계획 시간이 늘어난다.
제안하는 기본은 **결정에 필요한 설명을 먼저, 더 깊은 설명은 필요할 때**다.

- 먼저 사용자의 제품에 생기는 차이를 설명한다.
- 선택을 바꾸는 핵심 제약과 추천 근거를 포함한다.
- 사용자가 원하거나 이해 부족이 잘못된 결정으로 이어질 때 상세 설명을 제공한다.
- 이미 배운 기본 결정은 적용 조건을 확인하고 재사용한다.
- 되돌리기 어렵거나 권한·비용 영향이 큰 결정을 단순한 추천 한 줄로 숨기지 않는다.

학습·실행 모드를 매번 새로 선택하게 하는 추가 질문은 만들지 않는다.
사용자가 이미 밝힌 설명 선호와 현재 결정의 성격으로 AI가 설명 깊이를 조절한다.

## 11. 사용자 언어 규칙

### 11.1. 내부 식별자와 사용자 표현

내부 ID는 요구사항·사양·테스트·결정을 추적하기 위해 유지한다.
사용자 화면과 대화에서는 기능명·행동·결과를 기본 표현으로 사용한다.
사용자가 `D-10`, `ST-012`, `AC-3`의 뜻을 기억해야만 답할 수 있는 문장은 피한다.

| 대상 | 기본 표현 | ID가 필요한 경우 |
|---|---|---|
| 질문 제목 | 팀 관리자의 녹음 조회 범위 | 상세 근거 링크나 사용자 요청 시 |
| 진행 항목 | 녹음 파일 선택과 접근 권한 처리 | 개발 로그·내보내기·검색용 상세 정보 |
| 검수 안내 | 권한 거부 시 파일 목록이 열리지 않는지 확인 | 테스트 연결 상세 |
| 오류 설명 | 주문 삭제의 거부 경로에 확인 근거가 없습니다 | 상세 검사 결과에 원래 코드·ID 보존 |
| 링크 | 녹음 조회 권한 결정 | 링크 대상이 ID 기반 파일이어도 이름은 자연어 |

짧은 선택지 번호는 사용할 수 있다. 같은 메시지에서 선택지를 고르는 번호와, 과거 문서를 찾아야 하는 내부 ID는 다르다.
사용자가 특정 ID를 직접 물으면 그 ID와 의미를 함께 답한다.

### 11.2. 이름을 붙이는 기준

- “권한 처리”보다 “팀 관리자의 녹음 조회 범위”처럼 대상과 행동을 포함한다.
- 같은 이름이 여러 개면 기능·역할·상황을 덧붙여 구분한다.
- 제품에서 쓰는 용어를 유지한다. 대화마다 다른 별칭을 만들지 않는다.
- 이름이 바뀌어도 내부 ID는 유지하여 과거 기록과 연결한다.
- 설명할 이름이 없거나 모호하면 원본에서 찾는다. 추측한 이름으로 잘못된 항목을 설명하지 않는다.
- 엔진 출력에서 이름을 찾지 못하면 해당 항목의 설명이 없음을 명시하고 근거 위치를 제공한다.

### 11.3. 질문 예시

피할 표현:

> D-10은 A/B 중 어느 쪽으로 할까요?

개선된 표현:

> **팀 관리자의 녹음 조회 범위**
>
> 관리자가 같은 팀의 녹음 전체를 볼 수 있게 할지 결정이 필요합니다.
>
> 제안은 사용자가 공유한 녹음만 관리자가 볼 수 있도록 하는 것입니다. 녹음 내용을 불필요하게 공개하지 않으면서 공유 기능을 제공할 수 있습니다.
>
> 관리자가 모든 녹음을 확인해야 하는 업무라면 전체 조회가 필요하며, 그 접근 범위를 화면에도 알려야 합니다.

이 예시는 제품 정책 추천을 설명하기 위한 사례이며 실제 적용 승인으로 취급하지 않는다.

### 11.4. 기계 검사와 의미 검토의 경계

생성 리포트에서는 제목·표시명 존재, 링크 이름, ID 단독 제목 여부를 검사할 수 있다.
그러나 모든 대화에서 내부 ID가 보인다는 이유만으로 실패시키면 사용자의 ID 조회나 코드 설명도 오탐이 된다.

따라서 다음처럼 나눈다.

- 구조 검사: 생성 리포트의 사용자용 필드에 표시명이 존재하는가.
- 회귀 사례: 정상 출력, ID 조회 요청, 이름 중복·누락, 오류 경로를 확인한다.
- 의미 검토: 사용자가 앞선 문서 없이 실제 판단할 수 있는가.
- 절차 지침: 자유 대화에는 자연어 우선 규칙을 적용하되 완전한 기계 보장을 주장하지 않는다.

## 12. 진행 보고와 검수 요청의 형식

### 12.1. 진행 보고

기본 순서는 **달라진 점 → 확인한 결과 → 남은 일 또는 필요한 결정**이다.
사용자에게 의미 없는 내부 작업 내역을 나열하지 않는다.

피할 표현:

> ST-012 완료. J 통과. D-10 대기.

개선된 표현:

> 녹음 파일을 선택하고, 접근 권한이 없으면 안내하는 동작을 구현했습니다. 허용·거부·선택 취소의 자동 테스트를 통과했습니다. 실제 휴대전화에서 권한 안내가 보이는지는 아직 확인해야 합니다.

### 12.2. 질문이 필요한 진행 보고

> 공유 목록은 구현했지만, 팀 관리자가 볼 수 있는 녹음 범위가 아직 정해지지 않았습니다. 본인에게 공유된 녹음만 보여주는 구성을 제안합니다. 관리자가 팀 전체 녹음을 확인해야 한다면 조회 범위와 안내 문구가 함께 달라집니다.

보고와 실제 질문은 사용 환경의 채널 규칙에 맞춰 전달한다.
진행 상황을 보고하는 문장에 불명확한 승인 요청을 숨기지 않는다.

### 12.3. 검수 요청

검수 요청에는 준비 상태·조작 순서·기대 결과가 있어야 한다.

> 앱에서 ‘녹음 가져오기’를 누른 뒤 파일 접근 권한을 거부해 주세요. 권한이 필요한 이유가 나타나고 파일 목록은 열리지 않아야 합니다. 이후 권한을 허용하면 파일을 선택할 수 있어야 합니다.

“권한 거부 케이스 검수”처럼 테스트 이름만 전달하지 않는다.
자동 테스트 통과·실제 기기 확인·사용자 검수 완료를 서로 구분한다.

### 12.4. 리포트 첫 화면

첫 화면에는 다음을 둔다.

1. 이번에 무엇을 만들거나 바꿀지.
2. 기존 결정으로 확정된 내용의 짧은 요약.
3. 새로 결정할 내용과 추천안.
4. 결정에 따른 범위·사용 경험·비용·권한 차이.
5. 남은 미정과 그것이 현재 진행을 막는지.

정본 경로·ID·전체 표·검사 로그는 상세 정보로 제공한다.
이 리포트를 보기 위해 사용자가 여러 파일을 직접 조합해서 읽게 하지 않는다.
질문을 숨기거나 리포트 열람을 또 하나의 의무 승인 단계로 추가하지 않는다.

## 13. 동작 사례를 계획·구현·테스트의 공통 근거로 사용

### 13.1. 사례의 최소 구조

기능별 정책을 긴 산문으로 반복하기보다, 확인 가능한 동작 사례로 구체화한다.

| 항목 | 내용 |
|---|---|
| 사례 이름 | 사람이 읽고 이해할 수 있는 행동과 결과 |
| 조건 | 역할, 대상 데이터의 소유권·상태, 필요한 입력 |
| 행동 | 사용자 또는 시스템이 일으키는 사건 |
| 결과 | 허용·거부·오류, 데이터 변화, 사용자가 보는 결과 |
| 정책 근거 | 공통 권한·상태·데이터 규칙의 원래 위치 |
| 확인 방법 | 테스트 또는 수동 검수와의 연결 |

ID는 내부 연결용으로 유지한다. 사용자 보고는 사례 이름과 결과를 사용한다.
각 사례가 모든 가능한 조합을 열거할 필요는 없다. 동작이 달라지는 경계를 대표하도록 구성한다.
필요한 조합을 놓치지 않았는지는 의미 검토의 대상이다.

### 13.2. 주문 삭제 예시

다음은 설계 형식을 보여주기 위한 가상 정책이다.

| 사례 | 조건·행동 | 기대 결과 | 확인 대상 |
|---|---|---|---|
| 작성자의 미확정 주문 삭제 | 작성자가 자신의 미확정 주문을 삭제 | 삭제 상태로 바뀌고 목록에 반영 | 허용 경로·상태·표시 |
| 다른 사용자의 삭제 요청 | 타인이 같은 주문에 직접 삭제 요청 | 거부되고 데이터 유지 | 서버의 권한 거부 |
| 확정 주문 삭제 요청 | 작성자가 확정된 주문 삭제 요청 | 거부되고 이유 표시 | 업무 규칙·금지 전이 |
| 삭제 요청 반복 | 이미 삭제된 주문에 같은 요청 | 합의한 중복 처리 결과를 반환 | 중복 처리·데이터 일관성 |

“권한 표 작성”, “거부 테스트 작성”, “검수 시나리오 작성”을 별개로 시작하지 않고 이 사례를 공유 근거로 삼는다.
자동 테스트는 사례를 실제로 검증해야 한다. 사례 문장을 테스트 이름으로 복사한 것만으로 충분하지 않다.

### 13.3. 기존 12개 슬롯과 연결

| 기존 슬롯 | 주된 근거 |
|---|---|
| 선행조건·트리거·동작·결과 | 동작 사례와 연결된 사양 |
| 권한·비즈니스 규칙·데이터·상태 전이 | 공통 정본과 사례가 가리키는 해당 항목 |
| 예외·표시 | 거부·취소·실패 사례와 인터페이스 정의 |
| 검사 명령 | 프로젝트의 기존 검사 설정 |
| 검증 조건 | 수용 기준과 사례·실행 테스트 연결 |

기존 슬롯을 즉시 삭제하지 않는다. 먼저 같은 근거에서 기존 판정 형식을 만들 수 있게 하여 호환성을 유지한다.
사례만으로 판단할 수 없는 슬롯은 별도의 근거를 보완한다. 자동 생성이 의미 판정을 대체하지 않는다.

### 13.4. 정본과 생성물의 역할

- 공통 정책은 기존 도메인·제품·아키텍처 정본에 둔다.
- 기능별 동작은 기존 사양 또는 Story 중 이미 소유한 곳에 둔다.
- Manyfast 등 외부 계획이 충분한 내용을 담고 있으면 그 항목을 인용한다.
- 원본 위치를 확인할 수 없는 자유 산문·이미지는 검토 가능한 텍스트로 정리하는 비용을 따로 기록한다.
- 리포트·준비 슬롯 표시·테스트 연결 요약은 정본에서 파생되는 출력으로 다룬다.
- 새 사례 파일·정책 파일·결정 파일을 무조건 늘리지 않는다. 기존 문서 안의 구조화된 절부터 검토한다.
- 내용이 충돌하면 사본을 모두 수동 수정하는 대신 정본을 고치고 파생 출력을 갱신한다.

## 14. 불필요한 재판정과 재검증 줄이기

### 14.1. 먼저 다룰 문제: 계약과 진행 상태 분리

현재 Story 문서에는 동작 계약과 완료 체크박스·종료 기록이 함께 있다.
문서 전체가 준비 입력이면 진행 표시를 고친 뒤에도 준비·검증을 다시 해야 할 수 있다.

첫 개선은 다음 경계를 명시하는 것이다.

- 계약: 조건·행동·결과·정책·수용 기준·의존 관계.
- 운영 상태: 담당·진행 여부·완료 시각·검증 결과 요약.

검증 결과를 기록했다는 사실이 검증 입력을 바꾸는 순환을 줄인다.
단순히 특정 문구를 해시에서 지우는 방식은 계약 내용까지 누락할 수 있으므로 피한다.
계약 영역을 명시적으로 읽는 구조와 기존 문서 이관 방식을 함께 설계한다.

### 14.2. 바뀐 이유를 먼저 보여주기

범위를 좁히는 엔진 개편에 앞서, 재판정이 필요한 이유를 이해할 수 있게 한다.

예시:

> 녹음 조회 권한 정책이 바뀌어 공유 목록의 접근 검토가 필요합니다. 이전에는 본인에게 공유된 녹음만 조회했지만, 새 계획에는 팀 전체 조회가 포함되어 있습니다.

자동으로 의미 차이를 확정할 수 없으면 변경 파일·항목·연결 관계까지만 설명한다.
해시가 다르다는 사실만으로 위와 같은 정책 변화 내용을 지어내지 않는다.

### 14.3. 항목 단위 의존성은 후속 개선

파일 전체를 보는 비용이 실전에서 크다고 확인되면 정책·사양·사례에 안정적인 항목 ID를 연결한다.
Story가 의존하는 항목과 공통 정책이 바뀌었을 때 해당 준비 판정을 다시 하도록 범위를 좁힌다.

필요한 조건:

1. 참조 대상 삭제·이름 변경·ID 중복을 탐지할 수 있어야 한다.
2. 의존 관계를 제거해 오래된 판정을 통과시키지 못해야 한다.
3. 공통 권한·데이터 정책 변경은 연결된 모든 기능에 전달되어야 한다.
4. 분류되지 않은 새 항목이나 불명확한 연결은 보수적으로 재검토해야 한다.
5. 기존 파일 단위 기록을 새 방식의 승인 기록으로 자동 변환하지 않아야 한다.

처음부터 코드 전체의 영향 그래프를 구현하지 않는다. 준비 판정 범위와 테스트 실행 범위는 별도 문제다.
기능별 테스트를 실행한 결과와 프로젝트 전체 통합 검증 결과도 구분한다.

## 15. 녹음 파일 가져오기에 적용한 계획 대화 예시

이 절은 개선 전후를 비교하기 위한 리허설 시나리오다. 실제 제품 정책이나 승인 기록이 아니다.

### 15.1. 기존 방식에서 생길 수 있는 왕복

1. 파일을 하나씩 고르는지 여러 개 고르는지 질문한다.
2. 여러 개라면 진행률을 어떻게 보여줄지 다음 라운드에서 질문한다.
3. 일부 실패 시 전체를 중단할지 질문한다.
4. 실패한 파일만 재시도할 수 있어야 하는지 질문한다.
5. 권한 거부 시 어디까지 막는지를 도메인 설계에서 다시 질문한다.
6. 계획을 작성해도 되는지 확인한다.
7. 작성한 계획을 승인받는다.
8. 준비도 단계에서 같은 내용을 다른 표현으로 다시 확인한다.

실제 모든 프로젝트가 이 순서를 밟는다는 주장은 아니다. 현행 규칙에서 발생 가능한 비용을 보여주는 비교 사례다.

### 15.2. 개선 후 AI의 사전 작업

기존 계획과 코드를 읽어 다음을 구분한다.

- 이미 정해진 사용자·플랫폼·처리 범위.
- 파일 접근 권한과 처리 목적 동의의 차이.
- 파일 선택 후 검증·등록까지의 상태.
- 취소·권한 거부·파일 없음·일부 실패·중복 선택의 처리 후보.
- 외부 전송 여부와 비용에 영향을 주는 결정.

OS별 실제 권한 방식은 플랫폼 근거를 확인한다. 모든 OS가 같은 권한 모델이라고 가정하지 않는다.
확인 가능한 구현 제약은 먼저 조사하며, 정책 선택은 사용자에게 남긴다.

### 15.3. 사용자에게 제시하는 초안

> **녹음 파일 가져오기 방식**
>
> 여러 파일을 선택하고 파일별 진행 상태를 보여주는 구성을 제안합니다. 일부 파일이 실패해도 나머지는 처리하고, 실패한 파일만 다시 시도할 수 있게 합니다. 한 파일씩 처리하는 구성보다 구현 범위가 커지지만, 여러 녹음을 반복해서 가져오는 작업을 줄일 수 있습니다.
>
> **선택 취소와 권한 거부 처리**
>
> 파일 접근이 허용되지 않으면 필요한 이유를 안내하고 파일 목록을 열지 않습니다. 선택을 취소하면 처리 대상으로 등록하지 않습니다. 접근 권한과 별개로, 사용자가 선택하고 처리를 승인한 파일만 처리 대상으로 사용하는 구성을 제안합니다.

이 초안은 새로 결정할 내용이 있는 경우에만 질문으로 제시한다.
기존 계획에 이미 같은 정책이 확정되어 있으면 적용 사실과 차이 없음만 요약한다.
외부 전송·공유 등 독립적인 중요한 결정이 남아 있으면 위 묶음에 숨기지 않고 별도로 명시한다.

### 15.4. 사용자가 일부만 수정한 경우

사용자: “이번에는 한 파일씩만 하고, 실패하면 다시 선택하게 하자.”

AI의 처리:

1. 다중 선택·파일별 병렬 진행·일괄 재시도는 이번 범위에서 뺀다.
2. 파일 하나의 선택·검증·등록·실패 안내를 현재 범위로 정리한다.
3. 취소·권한 거부·원본 보존 등 독립된 기존 정책은 유지한다.
4. 관련 사양·화면·검증 조건·준비 근거에 답을 반영한다.
5. 새 선택이 필요하지 않으면 각 문서마다 같은 질문을 반복하지 않는다.

응답 예:

> 이번 범위를 파일 한 개 선택과 처리로 줄였습니다. 실패하면 이유를 안내하고 다시 선택할 수 있게 합니다. 여러 파일의 진행률과 일괄 재시도는 이번에 만들지 않습니다.

### 15.5. 구현 준비 때 확인할 것

권한 거부·선택 취소·정상 선택·잘못된 파일·등록 실패의 결과와 확인 방법이 있는지 대조한다.
이미 확인한 동작이면 추가 승인을 요구하지 않는다. 실제 API나 플랫폼 동작이 계획과 다르면 차이와 영향을 제시한다.

## 17. 구현 순서와 각 단계의 완료 기준

### 17.1. 첫 단계: 질문과 사용자 표현부터 개선

목적: 엔진을 크게 바꾸기 전에 계획 대화의 왕복과 이해 비용을 줄인다.

작업:

1. 공통 질문·보고 규칙의 정본 위치를 정한다. 우선 기존 공통 가이드 안에 둔다.
2. 계획·도입·준비·단계 커맨드의 상충 규칙을 찾아 함께 수정한다.
3. 구체적인 초안 작성 전에 받던 진행 동의를 없애고, 실제 선택 확인으로 통합한다.
4. 질문 예시·진행 보고·검수 안내·상태 양식에서 ID 단독 표현을 교체한다.
5. 계획 확정 시간과 질문 부담의 측정 항목을 정의한다.

완료 기준:

- 간단한 후속 분기를 이유로 불필요하게 다음 라운드를 요구하지 않는다.
- 같은 내용의 단계별 재승인이 남지 않는다.
- 제품의 새 결정·외부 실행 승인·실제 검수는 구분되어 있다.
- 대표 리허설에서 사용자가 내부 ID를 찾아보지 않고 결정할 수 있다.

### 17.2. 두 번째 단계: 기능별 동작 사례와 준비 근거 연결

목적: 다양한 개발 고려사항을 놓치지 않으면서 중복 작성 시간을 줄인다.

작업:

1. 기존 영향 분류를 기능별 계획 검토에 적용한다.
2. 현재 범위의 정상·거부·취소·실패 사례를 기존 정본에 기록한다.
3. 사례와 공통 정책을 기존 준비 슬롯·수용 기준·테스트에 연결한다.
4. 외부 계획이 같은 내용을 담은 경우 새 사본을 만들지 않는 경로를 만든다.
5. 사용자용 리포트에 이름과 결정 내용을 우선 표시한다.

완료 기준:

- 기능별 권한과 중요한 예외에 구현 가능한 답이 있다.
- 같은 동작을 문서·JSON·리포트에 독립적으로 다시 작성하지 않는다.
- 기존 테스트 실행 증거와 준비 판정의 추적성을 유지한다.
- 문서 생성 비용이 실제로 줄었는지 파일럿에서 관측할 수 있다.

### 17.3. 세 번째 단계: 진행 상태 변경으로 인한 재판정 제거

목적: 결과 기록이 기존 준비·검증 근거를 다시 무효화하는 순환을 줄인다.

작업:

1. 계약과 진행 상태의 입력 경계를 설계한다.
2. 기존 Story·사이클 문서의 이관·호환 방식을 정한다.
3. 무효화 이유를 사람이 읽을 수 있게 출력한다.
4. 실제 계약 변경은 계속 재판정을 요구하는지 확인한다.

완료 기준:

- 완료 표시·담당·운영 시각 변경만으로 동작 계약이 바뀌지 않는다.
- 권한·상태·수용 기준 변경은 기존 판정을 무효화한다.
- 오래된 승인·테스트 결과가 잘못 승계되지 않는다.

### 17.4. 네 번째 단계: 실전 적용과 비용 검토

실제 제품의 유사한 변경 2~3건을 시작 표본으로 삼는다. 통계적 입증이나 충분한 표본 수라고 주장하지 않는다.
질문 기록·작업 시간·재작업 원인을 비교하고 반복되는 비용을 찾는다.

결과에 따라:

- 계획 질문과 이해 부담이 줄었으면 새 방식을 유지한다.
- 계획 시간이 늘어도 재작업이 더 줄어 총시간이 줄었다면 유지 근거로 본다.
- 질문은 줄었지만 뒤늦은 결정이나 결함이 늘면 초안·검토 기준을 보완한다.
- 리포트·메타데이터 관리 비용이 크면 출력·기록을 통합하거나 줄인다.

### 17.5. 다섯 번째 단계: 필요할 때만 항목 단위 의존성 도입

무관한 변경에 따른 재판정 비용이 반복해서 크다는 증거가 있을 때 진행한다.
첫 단계부터 전체 엔진을 재설계하거나 새 계획 서비스를 만들지 않는다.
실제 기대 절감 시간, 이관 비용, 검사기 유지 비용을 함께 판단한다.

## 18. 검증 계획

이 절의 검증은 **향후 구현 변경에 필요한 계획**이다. 이번 문서 작성으로 아래 테스트가 추가되거나 실행된 것은 아니다.
새 자동 검사를 구현하면 실제 실패를 재현하는 fixture를 함께 추가한다.
자연어 절차 변경만 있는 부분에는 구현을 그대로 반복하는 형식적인 테스트를 만들지 않는다.

### 18.1. 질문 절차 리허설

| 상황 | 확인할 행동 | 실패 신호 |
|---|---|---|
| 자료에 이미 권한 정책이 있음 | 관련 기능에 재사용하고 질문 생략 | 같은 정책을 다시 질문 |
| 다중 파일의 단순 후속 분기 | 동작 구성으로 함께 제안 | 진행률·실패·재시도를 무조건 별도 라운드로 질문 |
| 복잡하고 중요한 독립 결정 | 사용자가 구분해 판단하도록 분리 | 외부 공유·결제를 한 묶음에 숨김 |
| 사용자가 일부만 수정 | 관련 근거와 사례에 일관되게 반영 | 다른 문서에서 원래 안이 남음 |
| 답변이 모호함 | 달라질 부분만 좁혀 확인 | 임의 승인 또는 전체 설문 재시작 |
| 사용자가 응답하지 않음 | 의존 작업은 미결정으로 유지 | 시간 경과로 자동 승인 |
| 단계만 이동 | 기존 결정과 입력이 같으면 재사용 | 같은 내용의 승인 반복 |
| 기존 가정과 실행 결과가 다름 | 차이·영향·대안을 설명 | 테스트에 맞춰 조용히 정책 변경 |

리허설은 실제 대화 품질을 검토하는 자료다. 대본만 통과했다고 다양한 실제 대화에서도 성립한다고 주장하지 않는다.

### 18.2. 사용자 표현과 리포트 검사

자동화 가능한 부분은 기존 [리포트 회귀](../scripts/test-report.sh)에 추가한다.

- 사용자용 제목과 링크에 기능명·결정명이 표시되는지.
- 동일한 이름의 기능이 조건·대상으로 구분되는지.
- 이름 누락 시 다른 항목의 이름을 잘못 가져오지 않는지.
- 내부 ID와 원본 연결이 상세 정보에 보존되는지.
- 사용자 문구의 HTML 특수문자와 링크가 안전하게 출력되는지.
- 기존 계획·준비·사이클 리포트가 계속 생성되는지.

질문과 보고의 충분함은 사람이 다음 기준으로 평가한다.

- 원문 문서를 추가로 열지 않아도 무엇을 결정해야 하는지 알 수 있는가.
- 추천안을 바꾸었을 때 달라지는 동작을 알 수 있는가.
- 완료·검증·검수 대기를 혼동하지 않는가.
- ID에 대한 설명을 다시 요청하지 않아도 되는가.

### 18.3. 계약·의존성 검사

필요한 회귀는 기존 [계약 테스트](../scripts/tests/test_contracts.py)와 [운영 테스트](../scripts/tests/test_operations.py)에 둔다.

| 변경 | 기대 결과 |
|---|---|
| Story의 완료 표시만 변경 | 분리한 동작 계약의 준비 판정 유지 |
| 담당자·운영 시각만 변경 | 동작 계약의 준비 판정 유지 |
| 허용 역할·대상 범위 변경 | 관련 판정 무효화 |
| 상태 전이·데이터 규칙 변경 | 관련 판정 무효화 |
| 수용 기준·테스트 연결 변경 | 기존 연결의 증거 재사용 차단 |
| 참조한 정책 삭제 | 누락 실패, 묵시적 해당 없음 처리 금지 |
| 공통 정책 변경 | 영향을 받는 연결 전체 재검토 |
| 입력 관계 제거 | 과거 판정 그대로 승계하지 않음 |
| 코드 변경 후 과거 실행 결과 사용 | 기존 현재성 검증 유지 |
| 실행 실패·skip·미보고 | 이전 성공으로 완료 처리하지 않음 |
| 검사 도중 입력 변경 | 변경된 입력으로 성공 근거를 남기지 않음 |

항목 단위 범위를 도입하기 전에는 파일 단위 범위의 한계를 그대로 문서화한다.

### 18.4. 호환성과 통합

- 문서 참조·절 제목·형식: `bash scripts/check-docs.sh`.
- 계획 구조를 바꾸면 정합성 fixture와 기존 외부 계획 수용 경로를 함께 확인한다.
- 저장 형식·파일 배포가 바뀌면 설치·업그레이드 회귀를 실행한다.
- 제품 소유 결정·계획·증거가 설치 과정에서 덮어써지지 않는지 확인한다.
- Lite의 사이클 문서와 Standard·Full의 Story 문서 경로를 모두 확인한다.
- 관련 변경에 필요한 회귀가 통과하면 근거 없이 전체 검사를 반복하지 않는다.
- 커밋 시점에는 저장소의 기존 독립 리뷰와 커밋 정책을 따른다.

계획 수정과 재작업 등 분류가 겹칠 수 있는 구간에는 주된 원인 하나를 정하고 상세 태그만 덧붙인다.

### 19.2. 뒤늦은 질문의 원인 분류

- 계획에서 놓친 결정.
- 계획에 답은 있었으나 AI가 읽지 못한 결정.
- 사용자가 새로 바꾼 요구사항.
- 계획 후 발견된 실제 기술 제약.
- 범위 확장으로 새로 필요한 결정.
- 질문이나 보고가 불명확해서 생긴 재확인.

모든 추가 질문을 실패로 취급하지 않는다. 발견할 수 없었던 제약과 계획 누락을 구분해야 개선 방향이 맞는다.

### 19.3. 비교 방법

1. 기능 규모·권한·상태·외부 연동·기존 코드 상태가 비슷한 실제 변경을 고른다.
2. 기존 기록에 시간 정보가 없으면 기준선 미측정으로 표시한다.
3. 새 방식의 최초 적용 비용과 반복 사용 비용을 나눠 본다.
4. 개선 전후의 계획 시간, 사용자 부담, 전체 시간, 재작업·결함을 함께 비교한다.
5. 표본이 적으면 방향과 사례를 보고하고 일반적인 절감률로 확대하지 않는다.

응답 시간을 측정한다고 사용자의 생활 패턴이나 민감한 대화 원문을 방법론 저장소에 수집하지 않는다.
제품 안에 증거를 보관하고 방법론 저장소에는 요약 지표와 개선 판단만 가져온다.

## 22. 전체 완료 조건과 인계

### 22.1. 개선 구현 완료 조건

- [ ] 현재 개발 범위의 기능별 검토 대상과 근거를 AI가 먼저 정리한다.
- [ ] 권한·데이터·상태·예외·외부 영향의 필요한 결정이 구현 전에 확보된다.
- [ ] 기존 답으로 해결할 수 있는 질문을 사용자에게 반복하지 않는다.
- [ ] 단순한 조건부 후속 질문을 동작 제안으로 묶는다.
- [ ] 사용자의 새 결정이 필요한 내용과 위임된 구현 선택이 구분된다.
- [ ] 단계 이동과 문서 작성만을 위한 반복 확인이 제거된다.
- [ ] 새 결정과 실제 검수·외부 실행 승인은 적절한 범위에서 유지된다.
- [ ] 질문·진행 보고·검수 요청을 내부 ID 조회 없이 이해할 수 있다.
- [ ] 사용자용 리포트가 새 결정과 실제 결과를 우선 보여준다.
- [ ] 사례와 기존 정본을 준비 판정·검증에 연결하고 독립 사본을 늘리지 않는다.
- [ ] 진행 상태 변경이 동작 계약 변경으로 잘못 취급되는 경로를 해결한다.
- [ ] 실제 계약 변경·실행 실패·입력 변경에 대한 기존 차단을 유지한다.
- [ ] 변경 범위에 필요한 회귀와 기존 호환성 검사가 통과한다.
- [ ] 계획 시간·사용자 부담·전체 시간·재작업을 함께 측정할 수 있다.
- [ ] 리허설과 실제 제품 효과를 구분해 보고한다.

항목 단위 의존성은 후속 선택 사항이다. 실전 근거 없이 이를 구현해야만 첫 개선이 완료된다고 보지 않는다.

### 22.2. 다음 작업자가 시작할 순서

1. 현재 작업 트리와 기존 미커밋 변경을 확인한다. 이 계획 이전의 변경을 덮어쓰지 않는다.
2. 이 문서의 17.1절을 첫 구현 범위로 잡고 공통 규칙과 관련 커맨드의 충돌을 정리한다.
3. 녹음 파일 가져오기 예시로 질문을 재구성해 왕복·설명 비용을 검토한다.
4. 새 규칙을 가이드·커맨드·양식에 일관되게 반영한다.
5. 사용자 표현과 계획 시간 측정이 가능해진 뒤 사례 연결과 재판정 개선으로 진행한다.

### 22.3. 이 문서 작성의 범위

이번 작업의 산출물은 상세 개선 설계와 현재 상태 문서의 탐색 링크다.
키트 운영 규칙·엔진·제품 계획은 이 문서 작성만으로 바뀌지 않는다.
향후 구현에서는 제안별 상태와 실제 검증 결과를 작업 기록에 남기고, 미구현 내용을 구현된 것으로 소개하지 않는다.

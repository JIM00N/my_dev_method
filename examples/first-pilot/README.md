# 첫 실전 파일럿

이 폴더는 방법론을 실제 제품에 처음 적용했을 때 **방법론 자체가 유용했는지** 검증하는 기록 양식입니다.

**증거는 제품 저장소에 남기고, 회고만 여기로 가져옵니다.** 제품 코드·비밀값·실행 로그·이슈 원문을 넣지 않습니다.

## 파일럿의 최소 범위

- 진입은 `/mdm-adopt` — 계획 문서 수집·계약 확인·매핑표 작성까지가 파일럿 범위다 (계획이 없으면 `/mdm-plan`)
- 실제 사용자 또는 운영자가 확인할 수 있는 기능 1개
- Story는 1~3개 (프로파일 Lite면 Story 문서 없이 사이클 문서로)
- 공유 계약이 없다면 Main 단독 실행
- 새 함수·행동은 TDD로 `RED → GREEN → REFACTOR`
- 자동 테스트 결과와 수동 검수 결과를 모두 남김

## 성공 기준

- `/mdm-adopt`가 계획 문서를 어느 경로로 찾았는가 (저장소 안 / 밖 / `/mdm-plan`) — 계약 확인 판정에 예상 밖이 있었는가
- `/mdm-ready`가 올린 질문이 실제로 갈리는 것이었는가 — 빈칸 노동이 된 칸은 없는가
- 정합성 검사(9종)가 실제로 잡은 것과 오탐이 구분되어 기록됐는가
- 목적·성공 기준·비목표가 구현 전 명시됐는가
- 사분면에서 프로파일이 판정됐고, 그 프로파일이 실제로 절차량을 줄이거나 늘렸는가
- 중요한 기술·권한·구조 결정이 기록됐는가
- Story별 영향 범위·허용 행동·거부 행동·검증 방법이 있었는가
- 서비스 페르소나 권한과 개발 에이전트 작업 권한이 구분되어 있었는가
- 테스트가 구현 전 실패했고, 구현 후 통과했는가
- **검증을 약화시켜 통과시킨 곳이 없는가** (테스트 삭제·단언 완화·타입 무시·예외 삼킴)
- 구현 덩어리마다 `/mdm-review` 코드리뷰(서브에이전트)가 돌았는가? 리뷰가 실제로 잡은 것이 있는가
- 버그를 잡은 검수 시나리오가 자동 테스트로 승격됐는가
- 오류가 생기면 기록 → 재검수 → 학습 인제스트까지 이어졌는가
- 훅이 실제로 막은 적이 있는가? 그때 우회하지 않고 해결했는가
- 사이클 종료 시 스펙과 구현의 드리프트를 대조했는가
- STATUS와 폴더별 index가 서로의 역할을 침범하지 않았는가
- 절차가 실제 작업을 지연시킨 부분과 지켜 준 부분을 구분할 수 있는가

## 회고 양식

```markdown
## <프로젝트> — <기능> / YYYY-MM-DD

- 목적:
- 성공 기준:
- 비목표:
- 진입 경로: 저장소 안 | 밖 | /mdm-plan / 상류 문서 수:
- 계약 확인: 상류 보유 __ · 갭 __ · 해당 없음 __ / 예상과 달랐던 판정:
- /mdm-ready: 질문 수 / 그중 실제로 갈린 것:
- 정합성 검사: 적발 (A~I 검사와 내용) / 오탐과 조치:
- 프로파일: Lite | Standard | Full / 판정 근거:
- Story 수:
- 학습 모드로 처리한 결정:
- 실행 모드로 적용한 기본값:
- TDD 증거: RED 명령·결과 / GREEN 명령·결과
- 품질 검사 명령과 결과:
- 수동 검수: 횟수 / 잡은 문제 수 / 자동 테스트로 승격한 시나리오 수
- 발견한 오류와 인제스트 결과:
- /mdm-review 리뷰 횟수 / 잡은 문제 수:
- 훅이 막은 사례와 대응:
- 스펙 드리프트: 발견 여부 / 어디서
- 방법론이 방지한 문제:
- 불필요하거나 느렸던 절차:
- 다음 템플릿 수정 제안:
```

## 회고 다음에 할 일

"불필요하거나 느렸던 절차"에 적힌 것은 **읽고 넘어가지 않는다.**
두 번의 파일럿에서 같은 절차가 지목되면 그 절차를 잘라내거나 프로파일로 내리고, `CHANGELOG.md`에 이유와 함께 남긴다.
방법론도 `rules-learned.md`와 같은 규칙으로 산다 — **2회차면 승격, 여기서는 2회차면 삭제 검토.**

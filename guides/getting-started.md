# 시작 가이드 — 처음 쓰는 사람을 위해

이 문서는 my_dev_method를 **처음 접하는 사람**이 30분 안에 첫 프로젝트를 시작하게 하는 안내다.
절차의 단일 기준은 키트 안의 문서들이다 — 이 가이드는 규칙을 복제하지 않고, 무엇이 어디 있고 왜 그런지만 안내한다.

---

## 1. 이게 무엇인가

**AI 에이전트와의 개발을 규율하는 "실행 가능한 방법론"이다.** 제품 저장소에 복사해 넣는 파일 한 벌로,
규칙은 산문으로, 절차는 가이드로, 산출물은 양식으로 적혀 있고 — **지켜지는지는 사람이 아니라 기계가 본다.**

일반 방법론 문서와 다른 점 세 가지:

| 층 | 무엇 | 일반 문서였다면 |
|---|---|---|
| **훅** | 비밀값 커밋, 스택에 없는 패키지 설치, STATUS 미갱신 종료를 **실제로 차단** | "주의하세요"라는 산문 |
| **서브에이전트** | 코드리뷰(`/review`)와 에러 학습(`/ingest-errors`)을 구현과 **분리된 컨텍스트**가 수행 | 구현한 에이전트가 스스로 검토 (자기 우회를 못 본다) |
| **배포물** | 버전 스탬프·설치/업그레이드 절차·CI 검사를 갖춘 복사본 | 읽고 잊는 위키 페이지 |

풀려는 문제는 하나다: **AI는 빠르게 만들지만, 검증을 약화시켜 초록불을 만들고, 세션이 끊기면 맥락을 잃고, 같은 실수를 반복한다.**
이 키트는 그 세 가지를 각각 리뷰 서브에이전트, STATUS 스냅샷, 학습 루프로 막는다.

## 2. 전제

- **Claude Code** — 훅·커맨드·서브에이전트가 여기서 동작한다.
  (Codex 등 다른 에이전트도 `AGENTS.md`를 통해 같은 규칙을 읽지만, **기계적 강제는 없다** — 스스로 지켜야 한다.)
- **git** — 대상 프로젝트는 git 저장소여야 한다 (비밀값·STATUS 훅이 git을 근거로 판단한다).
- **jq** — guard 훅 2개가 쓴다. 없으면 훅이 경고만 남기고 통과한다. `brew install jq`
- 개발 지식이 깊지 않아도 된다 — 설계 단계(S1~S4)는 AI가 **사용자를 인터뷰**해서 채우는 구조다.

## 3. 5분 설치

```bash
git clone https://github.com/JIM00N/my_dev_method.git
my_dev_method/scripts/install-kit.sh <제품 저장소 경로>
```

스크립트가 `CLAUDE.md`·`AGENTS.md`·`docs/`·`.claude/`를 복사하고, 이어서 할 일 5가지를 출력한다.
기존 `.claude/`가 있으면 통째로 덮지 않고 병합한다(`settings.json` 보존). 손으로 하는 절차와
파일 소유권 규칙은 `templates/dev-kit/README.md`에 있다.

설치 후 Claude Code를 열고:

```
/stage 1
```

이 한 줄로 방법론이 시작된다.

## 4. 처음 한 바퀴 — 무엇이 일어나는가

| 단계 | AI가 하는 일 | **사람이 하는 일** |
|---|---|---|
| S1 문제·범위 | 인터뷰 질문, `product.md` 작성 | 질문에 답한다. "만들지 않을 것"을 정한다 |
| (프로파일) | 사분면으로 Lite/Standard/Full 판정 | 판정 확인 — **개인 도구면 절차가 자동으로 줄어든다** |
| S2 도메인·상태 | 데이터·상태 전이표 설계 | 업무가 실제로 어떻게 흐르는지 답한다 |
| S3 인터페이스 | 화면/API/CLI 표면 설계 | 뭐가 보여야 하는지 답한다 |
| S4 구조·스택 | 기술 선택지를 장단점과 함께 제시 | **고른다** (모르면 추천안 채택 — 이 인터뷰가 안목을 만든다) |
| S5 시각 (화면 있을 때) | 목업 생성 | 눌러 보고 어색한 곳을 지적한다 |
| S6 구축 | TDD 구현 → `/review` → 수정 | **검수 시나리오를 직접 누른다**, 리뷰 판정의 반영을 정한다 |

핵심 역할 분담: **문서는 에이전트가 쓴다. 사람은 답하고, 누르고, 판정한다.**
문서 정합성(정본·경로·양식·아카이브)은 구조와 훅이 지키므로 사람이 신경 쓸 일이 아니다.

## 5. 매일의 리듬

- **세션 시작**: `/stage` — STATUS를 읽고 현재 단계 가이드 하나만 읽는다. 어제 어디까지 했는지 설명할 필요가 없다.
- **구현 한 덩어리 끝**: `/review` — 리뷰 서브에이전트가 검증 우회·스펙 위반을 잡는다.
- **세션 끝**: STATUS 갱신 — 잊으면 훅이 종료를 막으며 갱신할 목록을 알려준다.
- **사이클 끝**: `/cycle-close` — 리뷰·검사·드리프트 대조·학습 인제스트·아카이브를 순서대로 수행한다.

| 커맨드 | 언제 | 하는 일 |
|---|---|---|
| `/stage [n]` | 세션 시작, 단계 진입 | STATUS → 현재 가이드 → 모드 세팅 |
| `/review` | 구현 덩어리 끝, 사이클 닫기 전 | `code-review` 서브에이전트 리뷰 |
| `/ingest-errors` | 에러 기록이 쌓였을 때 | `error-learning` 서브에이전트가 규칙 승격 |
| `/cycle-close` | 사이클 종료 | 종료 점검 11단계 일괄 수행 |

## 6. 훅이 막았을 때

**우회하지 않는다.** 막힌 데는 이유가 있고, 우회 금지가 이 방법론의 존재 이유다.

| 막힌 것 | 요구하는 것 |
|---|---|
| 패키지 설치 / 매니페스트 편집 | `docs/spec/stack.md` 결정 표에 선택·근거를 먼저 기록 (사용자 승인) |
| `git commit` / 파일 쓰기 | 비밀값을 환경 변수로 옮기고 `.gitignore` 확인. 유출됐으면 키 재발급 |
| 세션 종료 | `docs/status/STATUS.md`의 최종 갱신·다음 3가지 갱신 |

진짜 오탐이면 끄지 말고 좁힌다 — `docs/spec/code-conventions.md` 5-1의 예외 표에 그 한 건만 기록하고 진행한다.

## 7. 업그레이드

배포본의 버전은 `CLAUDE.md` 첫 줄의 `<!-- dev-kit v… -->` 스탬프로 확인한다.

```bash
my_dev_method/scripts/install-kit.sh <제품 저장소 경로> --upgrade
```

키트 소유 파일만 교체되고, 프로젝트가 채운 spec·이슈·STATUS·ADR은 건드리지 않는다.
바뀐 내용은 원본 저장소의 `CHANGELOG.md`에서 확인한다.

## 8. 써 보고 나서

- **방법론이 유용했는지 회고**를 `examples/first-pilot/README.md` 양식으로 남긴다 (증거는 제품 저장소에, 회고만 여기에).
- 키트 자체의 결함·개선 제안은 GitHub 이슈로. 이 방법론도 자기 규칙대로 산다 —
  같은 절차가 두 번의 파일럿에서 "불필요하다"고 지목되면 잘라낸다.

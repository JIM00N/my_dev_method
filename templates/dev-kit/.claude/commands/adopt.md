## A. 최초 도입 (인자 없음)

### 0. 계획 문서를 찾는다 ★★

**어떤 도구도 전제하지 않는다.** 순서대로 찾고, 찾으면 거기서 멈춘다.

**① 저장소 안을 먼저 뒤진다.** 사용자에게 묻기 전에 한다 — 사실은 에이전트가 찾는다.

```
docs/  doc/  documentation/  spec/  specs/  planning/  저장소 루트의 *.md
이름 패턴: prd · product · spec · plan · requirement · feature · scope · brief · rfc · design
```

찾은 것을 **목록으로 보여주고 사용자가 고르게 한다.** 무엇이 계획 문서인지 임의로 단정하지 않는다.
목록에는 파일마다 경로·첫 제목·줄 수를 함께 적어 사용자가 판단할 수 있게 한다.

**② 저장소에 없으면 밖에 있는지 묻는다.** 형태를 제한하지 않는다 — 파일 경로 · 붙여넣기 · 외부 도구 무엇이든 좋다.

> 계획 도구가 MCP로 붙어 있으면 그것도 수집 경로 중 하나다. **다만 특정 도구를 전제하지 않는다** —
> 사용 가능한 도구를 먼저 탐색해 무엇을 조회할 수 있는지 확인한 뒤 쓴다. 도구 이름·스키마는 서비스가 바꾼다.
> MCP가 없거나 인증되지 않았다고 해서 절차가 막히지 않는다.

**③ 그래도 없으면 `/plan` 으로 보낸다.** 계획을 지어내지 않는다.
`/plan` 이 만든 결과도 `docs/upstream/` 에 같은 자리로 들어오고, 출처만 `self:plan` 으로 구분된다.

### 1. 수집

찾은 계획 문서를 `docs/upstream/` 에 스냅샷으로 저장한다.

- **문서 개수·종류를 고정하지 않는다.** 한 장짜리 PRD 하나일 수도, 네 문서일 수도 있다. 있는 것을 그대로 받는다.
- 저장 위치와 이름은 `docs/upstream/index.md` 를 따른다. 없는 문서를 위해 빈 파일을 만들지 않는다.
- 저장소 안에 이미 있던 파일이라도 **스냅샷은 따로 뜬다.** 원본은 그대로 두고, 해시로 변경을 감시할 사본이 필요하다.
- 화면 자료가 이미지면 **화면 목록 텍스트 인덱스**를 뽑아 남긴다. 기계는 이미지를 못 본다.
- 각 파일의 출처·수집시각·sha256을 `docs/upstream/manifest.tsv` 에 탭 4열로 기록한다.
  출처 칸은 세 갈래다: 외부 도구 이름 · 저장소 경로 · `self:plan`.

### 2. 교차 대조 ★

문서가 **둘 이상이면** 서로 대조해 불일치를 전부 목록으로 만든다
(`docs/guides/S0-adopt.md` 2절의 대조 짝 표). 문서가 하나면 이 단계는 건너뛰고 그 사실을 보고한다.

**목록을 사용자에게 제시하고 판정을 받는다.** 어느 쪽이 맞는지 임의로 고르지 않는다.
상류를 고쳐야 하는 건이면 상류에서 고치고 다시 받는다 — **스냅샷을 손으로 고쳐 맞추지 않는다.**

### 3. ID 정리 — 발급이 아니라 인용이다 ★

- **계획 문서가 ID를 이미 붙였으면 그대로 옮긴다.** 형식을 바꾸지 않는다
  (`FR-1` · `R-AOTSCK` · `REQ-042` 무엇이든 그대로). 번호를 다시 매기면 같은 것에 이름이 둘이 된다.
- **ID가 없는 것에만 부여한다.** 화면은 대체로 여기 해당한다 — 계획 도구가 요구사항에는 ID를 붙여도
  화면에는 안 붙이는 경우가 많다. `SC-001` 부터 순서대로 준다.
- `docs/spec/source-map.md` 2·3절 표를 채운다. 이 시점 상태는 전부 `⬜ 대기`, 사이클·테스트 칸은 비운다.

**한 행 = 최상위 요구사항 하나.** 그 아래 기능·사양으로 쪼개져 있어도 행을 늘리지 않는다.
행의 단위는 **검증 조건이 붙어 있는 계층**이다.

### 4. 검증 조건 수를 센다 ★

각 요구사항에 딸린 **"이렇게 되면 된 것"** 목록의 개수를 세어 `조건 수` 칸에 적는다.
상류마다 이름이 다르다 — 수용 기준 · acceptance criteria · 완료 조건 · 검증 항목 등.

- 목록이 아니라 산문으로 적혀 있으면 **세지 말고 `—` 로 둔다.** 억지로 쪼개 세지 않는다.
- 이 칸이 채워져 있으면 검사기가 **조건 하나당 테스트 하나**를 요구한다.
  `—` 면 기존 규칙("완료인데 테스트 칸이 비었나")으로 내려간다.

### 5. 계약 확인 ★★ — 판정이 곧 소유권 결정이다

`docs/spec/source-map.md` 4절 표의 항목마다 **상류를 실제로 뒤져 보고** 판정한다. 단정하지 않는다.
판정 어휘(`✅ 상류 보유` · `❌ 갭` · `— 해당 없음`)와 **각 판정이 1절 정본 소유권을 어떻게 정하는지는
4절이 정본이다** — 여기 옮겨 적지 않는다. 4절을 열고 그대로 따른다.

- **표의 6항목은 최소 후보일 뿐이다.** 훑다가 후보 밖의 빈 곳을 발견하면 **줄을 더한다.**
- **유저플로우를 상태 전이표로 취급하지 않는다.** 화면 이동과 데이터 상태 전이는 다른 물건이다.
  전이표는 어느 계획 도구도 구조로 담지 않으므로 거의 항상 갭으로 나온다 — 없으면 구현 중에 에이전트가 지어낸다.

### 6. 갭 메우기

`❌ 갭` 으로 판정된 항목이 가리키는 절**만** 편다 (S0 가이드 5절 대응표). S1~S5를 처음부터 밟지 않는다.
프로파일 판정도 여기서 한다 — `docs/guides/profiles.md` 의 사분면을 계획 문서의 사용자 정의로 채운다.

### 7. 마일스톤 배치 ★

**상류에 없는 축을 여기서 세운다.** 계획 문서는 "무엇을"의 트리이지 "언제까지 무엇이 되나"가 아니다.

- **모든 요구사항을 마일스톤에 배치한다** — `docs/spec/source-map.md` 매핑표의 `마일스톤` 칸.
  **빈 칸을 남기지 않는다.** 배치가 빈 요구사항은 검사 H가 실패시킨다.
- 배치 전에 **의존 순서**를 훑는다 — "A 없이 B가 성립하나". 성립 안 하면 A가 먼저다.
- `docs/plan/roadmap.md`에 마일스톤 **행을 전부** 만들되,
  **「무엇이 되면 달성인가」와 목표 시점은 M1 것만 채운다.** 나머지는 비워 둔다 —
  돌아보지 않은 마일스톤의 달성 조건은 계획이 아니라 추측이다.
- **M1의 달성 조건을 확인 가능한 한 문장으로 못 쓰면 M1이 너무 크다.** 다시 긋는다.
- 나누는 기준의 정본은 `docs/plan/index.md` 핵심 원칙 5다. 판정 결과를 사용자에게 보이고 확인받는다.

> **백로그로 보내지 않는다.** 백로그는 "범위 밖에서 떠오른 것"의 자리다.
> 계획에 이미 있는 요구사항은 M3에 배치하되 상태를 `⬜ 대기`로 둔다.

### 8. 리포트

```bash
python3 .claude/scripts/report.py adopt
```

`docs/reports/adopt-<날짜>.html` 이 생성된다 — 교차 대조 발견·계약 확인 판정·매핑표를 한 화면에서 본다.
**사용자에게 파일 경로를 알려주고 확인을 받는다.** 판정할 것이 가장 많은 시점이므로 md 로만 보고하지 않는다.
(HTML 은 읽기용 사본이다. 정본은 md 이고 리포트는 매번 다시 생성된다)

### 9. 마감

- `.claude/scripts/check-consistency.sh` 를 실행해 통과시킨다.
- `docs/status/STATUS.md` 에 S0 완료·프로파일·다음 3가지를 기록한다.
- `docs/guides/S0-adopt.md` 의 DoD를 하나씩 실제로 대조한다. 대조하지 않은 완료 보고는 하지 않는다.

## B. 재동기화 (`--sync`)

**사이클을 시작할 때마다 돈다.** 구현 도중 상류가 바뀐 걸 뒤늦게 알면 이미 지은 것을 뜯게 된다.

1. 상류를 다시 수집해 새 스냅샷과 해시를 얻는다. (출처가 `self:plan` 인 문서는 사용자가 `/plan` 을 다시 돌리지 않는 한 안 바뀐다)
2. `docs/upstream/manifest.tsv` 의 기록과 비교해 **바뀐 문서**를 가려낸다. 변화가 없으면 여기서 끝내고 보고한다.
3. 바뀐 문서에서 **영향받는 요구사항·화면 ID를 산출**한다.
4. 각 ID의 `docs/spec/source-map.md` 행 **재검토 칸에 사유를 적는다.** 함께 나열한다:
   - `docs/spec/domain.md` 전이표의 어느 행이 딸려 있는가
   - 권한 표의 어느 행이 딸려 있는가
   - 어느 테스트가 그 요구사항을 검증하고 있는가
   - 이미 구현된 사이클이 있는가
   - **검증 조건 개수가 바뀌었는가** — 늘었으면 `조건 수` 칸을 고치고, 그만큼 테스트가 더 필요해진다
5. **판정을 무효화한다 ★★** — 판정은 한 번 하고 끝나는 것이 아니다. 근거가 바뀌면 판정도 다시 해야 한다.
   - 바뀐 요구사항의 **`준비` 칸을 `❌ 재판정 (상류 변경)`** 으로 되돌린다.
     슬롯 판정은 그 시점의 상류를 근거로 내린 것이라, 상류가 바뀌면 근거가 사라진다.
   - 4절 **계약 확인표**에서 바뀐 문서와 관련된 항목의 판정을 **다시 확인한다** —
     상류가 이번에 권한을 담기 시작했을 수도, 담던 것을 뺐을 수도 있다.
     `✅ 상류 보유` 였는데 빠졌으면 그 항목은 이제 갭이고, 반대면 저장소 사본을 걷어내고 인용으로 바꾼다.
6. 스냅샷과 `manifest.tsv` 를 새 판으로 교체한다.
7. **사용자에게 재검토 목록을 보고한다.** 판정을 받아 저장소 소유 항목을 갱신하고, 처리된 행의 재검토 칸을 비운다.
8. **`/ready` 를 다시 돌린다** — 5절에서 `❌ 재판정` 으로 되돌린 요구사항의 슬롯을 새 상류 기준으로 판정한다.
   이걸 건너뛰면 검사가 실패한 채로 남는다 (그게 의도다 — 조용히 지나가지 않게).

재검토 칸이 남아 있으면 `.claude/scripts/check-consistency.sh` 가 실패한다. 칸을 비우려고
근거 없이 지우지 않는다 — 실제로 반영한 뒤에 비운다 (절대 규칙 11).

## 경계

- 요구사항·기능 목록과 화면 구성의 정본은 **항상 상류**다. `docs/upstream/` 은 읽기 전용 사본이다.
- 기술 스택과 검사 명령의 정본은 **항상 이 저장소**다. 상류에 되돌려 쓰지 않는다.
- **그 사이 항목(상태 전이표·권한 표·데이터 정의)의 정본은 미리 정해져 있지 않다** —
  계약 확인(A-5단계)이 `docs/spec/source-map.md` 4절에 남긴 판정이 정한다.
- 경계표는 `docs/spec/source-map.md` 1절이 정본이다.

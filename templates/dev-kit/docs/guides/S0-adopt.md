# S0 — 도입 (기존 계획 문서 받아들이기)

**읽어야 할 때**: 프로젝트를 시작할 때. **모든 프로젝트의 진입점이다.**
**입력**: 계획 문서 (저장소 안 · 밖 · `/mdm-plan`이 만든 것 — 어디서 왔든 상관없다)
**산출물**: `docs/upstream/` 스냅샷, `docs/spec/source-map.md`
**모드**: 찾기 → 수집 → 대조 → **갭만** 인터뷰
**다음**: 갭이 가리키는 S2·S4의 해당 절 → `docs/guides/S6-build.md`

> **계획 문서가 아예 없으면** `/mdm-adopt`가 `docs/guides/plan.md`(`/mdm-plan`)로 보낸다.
> 거기서 만든 계획도 여기로 돌아온다 — 자리는 같고 취급도 같다.

---

## 왜 이 단계인가

계획을 뽑아내는 일은 이미 상류가 한다 (외부 도구든, `/mdm-plan`이든). 이 키트가 맡는 것은 **그다음** —
구현 중에 문서가 서로 어긋나서 생기는 오류와 일탈을 막는 것이다.
그러려면 상류가 준 것을 **기계가 볼 수 있는 형태로 한 번 앉혀야** 한다.

여기서 하는 일은 넷이다.

1. 계획 문서를 **찾는다** — 저장소 안을 먼저 뒤진다
2. 문서가 여럿이면 **서로** 맞는지 본다 (따로 생성된 문서는 반드시 어긋나 있다)
3. 요구사항과 화면에 **ID를 앉힌다** — 상류가 붙였으면 그대로, 없으면 부여
4. 상류가 **무엇을 담고 무엇을 안 담는지 확인**해서, 안 담긴 것만 채운다

**용어**: 이 문서에서 **상류**는 요구사항이 태어난 곳이다. 외부 기획 도구일 수도,
저장소에 이미 있던 PRD 파일일 수도, `/mdm-plan`이 만든 계획일 수도 있다.

---

## 1. 찾기와 수집 ★

```
/mdm-adopt
```

**어떤 도구도 전제하지 않는다.** `/mdm-adopt`가 순서대로 찾는다.

1. **저장소 안을 먼저 뒤진다** — `docs/` · `doc/` · `spec/` · 루트의 `*.md`,
   이름 패턴 `prd · product · spec · plan · requirement · feature · scope · brief · rfc · design`.
   찾은 것을 목록으로 보여주고 **사용자가 고른다.** 무엇이 계획 문서인지 임의로 단정하지 않는다.
2. **없으면 밖에 있는지 묻는다** — 파일 경로 · 붙여넣기 · 외부 도구 무엇이든.
   계획 도구가 MCP로 붙어 있으면 그것도 수집 경로 중 하나다. **다만 특정 도구를 전제하지 않는다.**
3. **그래도 없으면 `/mdm-plan`으로 간다.** 계획을 지어내지 않는다.

찾은 것을 `docs/upstream/`에 스냅샷으로 저장하고 `docs/upstream/manifest.tsv`에 출처·수집시각·해시를 기록한다.

- **문서 개수·종류를 고정하지 않는다.** 한 장짜리 하나일 수도, 넷일 수도 있다. 억지로 넷으로 쪼개지 않는다.
- 저장소 안에 이미 있던 파일이라도 **스냅샷은 따로 뜬다.** 원본은 그대로 두고, 해시로 변경을 감시할 사본이 필요하다.
- 스냅샷은 **읽기 전용**이다. 손으로 고치면 검사가 해시로 잡는다 (`docs/upstream/index.md`).
- 화면 자료가 이미지면 **화면 ID 텍스트 인덱스**를 뽑는다. 기계는 이미지를 못 본다.

## 2. 교차 대조 — 문서가 여럿일 때 ★★

상류가 문서를 **따로** 생성했다면 서로 안 맞는 곳이 반드시 있다. 그걸 지금 잡지 않으면
구현 중에 *"어느 문서가 맞나"*로 매번 멈춘다. **문서가 하나면 이 절은 건너뛰고 그 사실을 보고한다.**

대조할 짝 (해당하는 것만):

| 대조 | 흔한 불일치 |
|---|---|
| 요구사항 목록 ↔ 기능 명세 | 명세에만 있는 기능 (범위 확장) · 요구사항만 있고 명세가 없는 것 |
| 기능 명세 ↔ 사용자 흐름 | 명세에 있는데 도달 경로가 없는 기능 |
| 사용자 흐름 ↔ 화면 자료 | 흐름에 등장하는데 화면이 없음 · 화면은 있는데 흐름에 없음 |
| **비목표 ↔ 나머지 전부** | **"안 만들 것"에 있는데 다른 문서가 만들고 있음** |

발견을 **목록으로 보고하고 사용자가 판정한다.** 에이전트가 임의로 한쪽을 고르지 않는다.
판정 결과는 상류를 고칠 일이면 상류에서 고치고 다시 받는다 — 스냅샷을 손으로 고쳐 맞추지 않는다.

## 3. ID — 발급이 아니라 인용이다 ★

**키트는 ID 형식을 강요하지 않는다.**

- **상류가 이미 붙였으면 그대로 쓴다.** `FR-1` · `R-AOTSCK` · `REQ-042` 무엇이든 그대로 옮긴다.
  번호를 다시 매기면 **같은 것에 이름이 둘**이 되고, 그때부터 어느 쪽을 인용할지 매번 갈린다.
- **없는 것에만 부여한다.** 화면은 대체로 여기 해당한다 — 계획 도구가 요구사항에는 ID를 붙여도
  화면에는 안 붙이는 경우가 많다 (여정을 산문이나 다이어그램으로만 주기 때문). `SC-001`부터 순서대로 준다.

`docs/spec/source-map.md` 2절·3절 표에 기록한다. 이후 **사이클·Story·테스트·이슈가 이 ID를 인용**하고,
`.claude/scripts/check-consistency.sh`가 인용을 기계로 대조한다.
검사기는 고정 형식을 쓰지 않는다 — **매핑표에 실제로 쓰인 ID에서 접두사를 유도**해 대조한다.

- **한 행 = 최상위 요구사항 하나.** 그 아래 기능·사양으로 쪼개져 있어도 행을 늘리지 않는다.
  행의 단위는 **검증 조건이 붙어 있는 계층**이다. 그보다 잔 단위의 진척은 사이클·Story가 맡는다.
- ID는 재사용하지 않는다. 요구사항이 사라져도 행을 지우지 않고 상태를 `취소`로 적는다.
- 이 시점의 상태는 전부 `⬜ 대기`다. 사이클·테스트 칸은 비워 둔다.

## 4. 검증 조건 세기 ★

각 요구사항에 딸린 **"이렇게 되면 된 것"** 목록의 개수를 세어 매핑표 `조건 수` 칸에 적는다.
상류마다 이름이 다르다 — 수용 기준 · acceptance criteria · 완료 조건 · 검증 항목.

**왜 세나**: 조건이 5개인데 테스트가 1개면 나머지 4개는 **검증되지 않은 채 완료가 된다.**
검사기가 "테스트 칸이 비었나"만 보면 이걸 못 잡는다. 조건 수를 적어 두면 **테스트 5개를 기계가 요구한다.**

- 목록이 아니라 산문으로 적혀 있으면 **세지 말고 `—`로 둔다.** 억지로 쪼개 세지 않는다.
- `—`면 기존 규칙("완료인데 테스트 칸이 비었나")으로 내려간다. 검사가 약해지는 것이지 꺼지는 게 아니다.

## 5. 계약 확인 ★★ — 단정이 아니라 확인이다

**상류가 무엇을 담는지 미리 단정하지 않는다.** 도구마다 다르다 — 권한과 데이터 정의를 기능마다
채워 주는 상류도 있고, 요구사항 목록만 주는 상류도 있다. **실제로 뒤져 보고** 판정한다.

`docs/spec/source-map.md` 4절 표의 항목마다 보유·갭·해당없음을 판정한다.
**판정 어휘와, 판정이 1절 정본 소유권을 어떻게 정하는지는 4절이 정본이다** — 이 가이드는 다시 적지 않는다.
요지만: 상류가 담고 있으면 **베끼지 않고 인용**하고(정본이 상류로 간다), 없으면 그 절만 펴서 저장소가 채운다(저장소 소유).

**그 표의 항목은 "반드시 확인할 최소 후보"일 뿐이다.** 훑다가 후보 밖의 빈 곳을 발견하면 **줄을 더한다**
(예: 오류 메시지 규칙, 보존 기간, 동시 편집 처리). **개수를 여기서 다시 세지 않는다** — 세는 순간 갈라진다.

> **상류가 `self:plan`이면 권한과 사양별 영향 영역·선행은 대체로 `✅ 상류 보유`다.**
> `/mdm-plan`이 그 둘을 담도록 검사 J가 강제하기 때문이다 (`docs/guides/plan.md` P3).
> **그래도 열어 보고 판정한다** — 미리 단정하지 않는 원칙은 여기서도 같다.

> **같은 것을 두 벌로 만들지 않는다 ★**
> 상류가 이미 담은 것을 저장소에 옮겨 적으면, 상류가 바뀌는 순간 두 벌이 갈라지고
> 어느 쪽이 맞는지 사람이 매번 판정하게 된다. 갈라짐을 막으려고 만든 표가 갈라짐을 만드는 셈이다.

**갭으로 나오는 것이 정확히 훅과 코드리뷰의 연료다.** 항목별로 없으면 무슨 일이 생기는지:

| 확인할 것 | 없으면 무슨 일이 |
|---|---|
| **상태 전이표** | *"여기서 뒤로 가면 데이터는 무슨 상태?"*에 답이 없어 에이전트가 지어낸다 |
| 권한 표 | 거부 경로 테스트가 아예 안 생긴다 |
| 데이터 항목·관계·기준 장소 | 같은 값이 두 화면에서 다르게 보인다 |
| 사양별 영향 영역·선행 | 무엇을 병렬로 돌릴 수 있는지 계산할 근거가 없어, 병렬 작업이 같은 파일을 덮어쓴다 |
| 스택 결정표 | `guard-dependency.sh`가 근거 없이 통과만 한다 |
| 검사 명령·금지된 우회 | 코드리뷰가 기준 없이 감으로 본다 |
| 안정성 대비 | 배포 후 조용히 어긋난다 |

> **상태 전이표만은 거의 항상 갭이다.** 어느 계획 도구도 데이터 상태 전이를 구조로 담지 않는다 —
> 사용자 흐름은 "화면 A → 화면 B"이고 전이표는 "주문: 접수 → 진행중"이다. 다른 물건이다.

## 6. 갭만 메운다

**S1~S5를 처음부터 밟지 않는다.** `❌ 갭`으로 판정된 항목이 가리키는 절만 편다.

| 갭 | 펼 절 |
|---|---|
| 상태 전이표 | `docs/guides/S2-domain.md` ③ |
| 권한 표 | `docs/guides/S2-domain.md` ④ |
| 데이터 정의 | `docs/guides/S2-domain.md` ② |
| 사양별 영향 영역·선행 | Story 문서 2절 (`docs/plan/stories/ST-000-template.md`) — **Lite 는 사이클 문서**(`docs/plan/cycles/C00-template.md`). 사이클을 열 때 |
| 스택·검사 명령 | `docs/guides/S4-architecture.md` 2부 |
| 안정성 | `docs/guides/S4-architecture.md` 4부 |

프로파일(Lite/Standard/Full) 판정은 여기서 한다 — 계획 문서의 사용자 정의를 근거로
`docs/guides/profiles.md`의 사분면을 채우고 `docs/status/STATUS.md`에 적는다.
계획 문서가 사분면을 주지 않으면 이것도 갭이다.

## 7. 마일스톤에 배치한다 ★

**여기가 상류에 없는 축을 세우는 자리다.** 계획 문서는 *"무엇을 만드나"*의 트리이지
*"언제까지 무엇이 되나"*를 담지 않는다 — 어느 계획 도구도 이 축을 주지 않으므로 여기서 만든다.

### 무엇을 지금 하고, 무엇을 미루나

| 지금 확정한다 | 열 때 채운다 |
|---|---|
| 마일스톤 행 (M1, M2 …) — 이름과 순서 | 각 마일스톤의 **「무엇이 되면 달성인가」** |
| **모든 요구사항의 배치** — 매핑표 `마일스톤` 칸 | 각 마일스톤의 **목표 시점** |
| **M1의 달성 조건과 목표 시점** | (M2 이후는 `/mdm-cycle-close`가 앞 마일스톤을 닫을 때) |

**배치를 남기지 않는다.** 매핑표의 모든 행에 마일스톤이 적혀야 한다 — 배치가 빈 요구사항은
"언제 만들지 아무도 모르는 것"이고, 검사 H가 실패시킨다.

**배치와 착수는 다른 일이다.** M3에 배치된 요구사항도 상태는 `⬜ 대기`로 남는다.
그리고 **백로그로 보내지 않는다** — 백로그는 *"범위 밖에서 떠오른 것"*의 자리이지
계획에 이미 있는 요구사항의 자리가 아니다. 백로그로 보내면 꺼낼 때 S1부터 다시 밟게 된다.

### 어떻게 나누나

**나누는 기준의 정본은 `docs/plan/index.md` 핵심 원칙 5다** — 여기 옮겨 적지 않는다.
한 줄로는 *"여기까지 되면 사람이 실제로 써 볼 수 있다"* 는 선이다.

배치 전에 **의존 순서**를 먼저 훑는다. 상류 요구사항을 서로 대 보며 *"A 없이 B가 성립하나"* 를 묻는다.
성립하지 않으면 A가 먼저다. 이 순서가 M1을 고르는 근거가 된다.

### 산출

- `docs/spec/source-map.md` 매핑표의 `마일스톤` 칸 — 전부
- `docs/plan/roadmap.md` 마일스톤 표 — 행 전부 + M1의 달성 조건·시점
- `docs/plan/roadmap.md` 「사이클 배치」 표 — M1의 첫 사이클만

**M1의 달성 조건을 확인 가능한 한 문장으로 못 쓰면 M1이 너무 크다.** 다시 긋는다.

## 상류가 바뀌면 — `/mdm-adopt --sync`

상류와 이 저장소는 **둘 다 갱신된다.** 갈라지지 않는 이유는 항목 단위로 소유가 갈리기 때문이다
(`docs/spec/source-map.md` 1절). `--sync`가 하는 일:

```
상류 재수집 → 스냅샷 해시 비교 → 바뀐 문서의 요구사항·화면 ID 산출
→ 그 ID의 source-map 행 "재검토" 칸에 사유 기입
→ 딸린 상태 전이 행·권한 행·테스트를 함께 나열
→ 검증 조건 개수가 바뀌었으면 "조건 수" 칸도 고친다
```

재검토 칸이 비어 있지 않으면 **검사가 실패한다.** 사람이 판정해 저장소 소유 항목을 갱신하고 칸을 비워야 통과한다.
요구사항이 바뀌면 전이표도 바뀌어야 하는데, 그건 갈라짐이 아니라 **파생 갱신**이고 ID 추적이 그걸 잡는 장치다.

**언제 도나**: 사이클을 시작할 때마다. 구현 도중 상류가 바뀐 걸 뒤늦게 알면 이미 지은 것을 뜯는다.
(`self:plan` 출처 문서는 `/mdm-plan`을 다시 돌리지 않는 한 안 바뀐다)

## 자주 빠지는 함정

| 함정 | 증상 | 처방 |
|---|---|---|
| 사용자에게 먼저 물음 | 저장소에 이미 있는 PRD를 놓치고 새로 만듦 | 1절 — 저장소 안을 먼저 뒤진다. 사실은 에이전트가 찾는다 |
| 교차 대조 생략 | 구현 중 "어느 문서가 맞나"로 매번 멈춤 | 2절 — 도입 시점에 한 번에 판정한다 |
| ID를 다시 매김 | 같은 것에 번호가 둘이 되어 인용이 갈림 | 3절 — 상류가 붙였으면 그대로 쓴다 |
| 검증 조건을 안 셈 | 조건 5개에 테스트 1개인데 완료로 통과 | 4절 — 조건 수 칸을 채운다 |
| 상류에 있는 걸 또 씀 | 두 벌이 되어 상류가 바뀔 때 갈라짐 | 5절 — `✅ 상류 보유`면 인용만 한다 |
| 사용자 흐름을 전이표로 착각 | 취소·뒤로가기에서 데이터 상태가 제각각 | 5절 — 전이표는 별도 갭이다 |
| 갭을 비워 둔 채 구현 | 훅은 통과만 하고 리뷰는 감으로 봄 | 6절 — 갭이 채워지기 전에 사이클을 열지 않는다 |
| 스냅샷을 손으로 고침 | 다음 `--sync`에서 조용히 사라짐 | 상류에서 고치고 다시 받는다 |
| 상류 갱신 방치 | 다 만든 뒤 요구사항이 달랐음을 앎 | 사이클 시작마다 `--sync` |

## 완료 조건 (DoD)

> 표식 규칙: `(Standard+)`는 Standard·Full만, `(Full)`은 Full만 본다 — 표식 없는 항목은 모든 프로파일이 본다.
> `(사람 확인)`은 에이전트가 대신 체크하지 않는다 — 사용자에게 요청하고 받은 답을 기록한다.

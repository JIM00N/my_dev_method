# S3 — 인터페이스 설계

**읽어야 할 때**: S2의 DoD를 전부 통과한 직후.
**입력**: `docs/spec/product.md`, `docs/spec/domain.md`
**산출물**: `docs/spec/interface.md`
**모드**: 인터뷰 · 높은 추론 설정
**다음**: S4 구조·스택·안정성

---

## 왜 이 단계인가

인터페이스는 **사용자·외부 세계와 만나는 표면**이다. 여기서 표면의 모양을 먼저 정하지 않으면
내부 구조가 먼저 굳어 버리고, 나중에 표면을 고칠 때 내부까지 끌려 나온다.

여기서 정하는 건 "어떻게 보이나"(그건 S5)가 아니라 **"무엇이 있고 어떻게 도달하나"**다.

## 프로젝트 형태를 먼저 고른다

S1의 사용자 정의를 보고 해당하는 갈래만 수행한다. 둘 이상 해당하면 둘 다 한다.

| 형태 | 표면 | 수행할 절 |
|---|---|---|
| 사람이 화면으로 쓴다 | 화면·메뉴 | **A. 화면 IA** |
| 다른 프로그램이 호출한다 | API | **B. API 표면** |
| 터미널에서 명령으로 쓴다 | 명령·옵션 | **C. CLI 표면** |
| 코드에서 불러 쓴다 | 함수·클래스 | **C. 공개 API 표면** (같은 절) |

공통 절(D)은 모든 형태가 수행한다.

---

## A. 화면 IA (화면이 있는 경우)

### A-1. 정보 구조
- 최상위 메뉴는 몇 개인가? **5개 이하로 맞춘다.** 넘으면 묶는다.
- 각 메뉴의 이름은 사용자의 언어인가, 개발자의 언어인가? (사용자 언어로)
- 주 사용 환경은? 데스크톱 / 모바일 / 둘 다 — 어느 쪽을 우선 설계할지 정한다.

### A-2. 로그인 직후 화면 ★
사용자가 들어오자마자 보는 것이 이 시스템의 성격을 정한다.

- 로그인 직후 무엇이 보여야 하나?
- 거기 뭐가 **우선순위 순으로** 배치되나? (1위부터 5위까지 나열)
- 아무것도 할 일이 없을 때는 뭐가 보이나?

### A-3. 화면별 핵심 목표 ★
**화면마다 "사용자가 여기서 달성해야 하는 것" 한 문장을 먼저 박는다.**
이 문장이 있어야 나중에 UI 결정을 그 목표에 맞춰 판단할 수 있다. 없으면 취향 싸움이 된다.

| 화면 | 핵심 목표 (한 문장) | 여기서 할 수 있는 행동 |
|---|---|---|
| | | |

### A-4. 상태별 화면
S2에서 정의한 상태마다 화면에서 할 수 있는 일이 달라진다.

- 각 상태에서 **가장 중요한 행동 하나**는 무엇인가? (빠른 버튼으로 뺀다)
- 각 상태에서 **막아야 하는 행동**은 무엇인가?
- 다음 단계로 넘어가려면 반드시 입력해야 하는 값이 있나? (통제 장치)

### A-5. 진입 경로
- 알림·메일에서 클릭하면 어디로 가나? 상세로? 목록으로?
  (해당하는 건이 여러 개일 수 있으면 **목록으로 보낸다**)
- 외부에서 직접 주소로 들어올 수 있는 화면은 어디까지인가?

---

## B. API 표면 (다른 프로그램이 호출하는 경우)

### B-1. 이용자 구분
- 누가 호출하나? 우리 화면 / 파트너 시스템 / **미래의 AI 에이전트** / 사용자 스크립트
- 각각 권한이 같은가 다른가?

> 외부 API를 설계할 때는 **첫 사용자를 AI 에이전트라고 가정**하면 설계가 좋아진다.
> 사람이 화면으로 하던 일을 프로그램이 하려면 무엇이 필요한지가 드러나기 때문이다.

### B-2. 리소스와 동작
S2의 데이터 목록을 그대로 리소스로 놓고 각각에 대해:
- 조회 / 생성 / 수정 / 삭제 중 무엇을 열 것인가?
- 목록 조회에 필터·정렬·페이지 나눔이 필요한가?
- 여러 건을 한 번에 처리하는 동작이 필요한가?

### B-3. 즉시 반영 vs 승인 필요 ★
모든 동작을 두 부류로 나눈다.
- **즉시 반영해도 되는 것** — 기록·조회·상태 갱신 등
- **사람 승인 후 반영할 것** — 돈이 오가는 것, 외부로 나가는 것, 되돌릴 수 없는 것

이 구분이 없으면 자동화가 사고를 낸다.

### B-4. 통보 (필요한 경우)
- 우리 쪽 변화를 상대에게 알려야 하나? (웹훅)
- 어떤 사건을 알리나? 실패하면 몇 번 재시도하나?

### B-5. 계약 유지
- 호출 한도는? (분당 몇 회)
- 버전을 어떻게 표기하고 얼마나 유지하나?
- 오류는 어떤 형태로 돌려주나? (형식을 하나로 고정한다)

---

## C. CLI · 공개 코드 표면

- 명령(또는 공개 함수)을 전부 나열한다. **10개를 넘으면 하위 명령으로 묶는다.**
- 각각: 무엇을 받고 무엇을 돌려주나? 부작용이 있나?
- 되돌릴 수 없는 동작에 확인 절차가 있나? 자동화용 강제 실행 옵션이 있나?
- 출력 형태: 사람이 읽는 형태와 프로그램이 읽는 형태를 모두 제공하나?
- 오류 시 종료 코드와 메시지 규칙은?
- 이름은 일관적인가? (같은 개념에 같은 단어를 쓰는가)

---

## D. 공통 — 모든 형태가 수행

### D-1. 외부 연동 목록
- 이 시스템이 의존하는 외부 서비스를 전부 나열한다 (결제·메일·저장소·인증·데이터 제공)
- 각각 없으면 무엇이 안 되나?

### D-2. 어댑터 층 ★
**외부 서비스는 반드시 바뀐다.** 상대가 주는 형태를 그대로 내부까지 흘려보내면
상대가 바뀔 때 내부 데이터 정의까지 흔들린다.

→ "무엇이 오든 우리 형태로 바꿔 받는" 변환 층을 두기로 명시한다. 어디에 둘지는 S4에서 정한다.

### D-3. 무엇을 안 열 것인가
- 내부 전용으로 남길 것
- 이번 범위에서 제외할 것

## 자주 빠지는 함정

| 함정 | 증상 | 처방 |
|---|---|---|
| 화면별 목표 없이 시작 | UI 논의가 취향 싸움이 됨 | A-3의 한 문장을 먼저 박는다 |
| 메뉴 과다 | 최상위 8개 이상 | 5개 이하로 묶는다 |
| 승인 구분 없음 | 자동화가 잘못된 돈을 보냄 | B-3을 반드시 채운다 |
| 외부 형태가 내부까지 침투 | 상대 변경에 내부가 끌려감 | D-2 어댑터 층을 명시 |
| 오류 형태 제각각 | 호출 측이 매번 다르게 처리 | 오류 형식을 하나로 고정 |
| S5를 미리 함 | 색·폰트 이야기가 나옴 | 여기서는 "무엇이 있나"만. 모양은 S5 |

## 완료 조건 (DoD)

해당하는 갈래의 항목만 본다. 공통(D)은 항상.

- [ ] 프로젝트 형태(화면/API/CLI)가 확정되어 해당 절을 수행했다
- [ ] (A) 최상위 메뉴가 5개 이하로 정해져 있다
- [ ] (A) **모든 화면에 핵심 목표 한 문장**이 붙어 있다
- [ ] (A) S2의 각 상태에 대해 화면에서의 행동이 정의되어 있다
- [ ] (B) 모든 동작이 즉시반영/승인필요로 분류되어 있다
- [ ] (B) 오류 형식이 하나로 고정되어 있다
- [ ] (C) 명령·함수 목록과 각각의 입출력이 적혀 있다
- [ ] (D) 외부 연동 목록이 있고 각각의 장애 영향이 적혀 있다
- [ ] (D) 어댑터 층을 두기로 명시되어 있다
- [ ] (D) 이번에 안 여는 것이 적혀 있다
- [ ] `docs/status/STATUS.md`의 S3가 ✅ 로 갱신되었다

# S4 — 시스템 구조·기술 스택·안정성

**읽어야 할 때**: S3의 DoD를 전부 통과한 직후. **코드를 쓰기 전 마지막 단계.**
**입력**: `docs/spec/product.md`, `docs/spec/domain.md`, `docs/spec/interface.md`, `docs/guides/profiles.md`(범위 확인 — Lite는 `stack.md`+`code-conventions.md` 1절+안정성 1·4·5번)
**산출물**: `docs/spec/stack.md`, `docs/spec/architecture.md`, `docs/spec/code-conventions.md`
**모드**: 인터뷰 · 높은 추론 설정
**다음**: S5 시각 설계 (화면 없으면 S6)

> **S0로 들어왔어도 이 단계는 통째로 갭이다.** 상류 계획 도구는 기술을 정하지 않는다.
> 그리고 여기 산출물이 정확히 기계 장치의 연료다 — `stack.md`가 없으면 `guard-dependency.sh`가
> 근거 없이 통과만 하고, `code-conventions.md` 1절·5-1이 없으면 코드리뷰가 기준 없이 감으로 본다.
> **비워 둔 채 사이클을 열지 않는다.**

## 왜 이 단계인가

개발 지식이 없으면 가장 넘기고 싶은 단계이고, 그래서 가장 큰 차이가 벌어지는 단계다.
여기를 건너뛰면 **AI가 알아서 고른 기술로, 안정성 장치 없이 서비스가 나온다.**
문제는 그 사실 자체를 모른 채 나온다는 것이다. 무너질 때까지는 멀쩡해 보인다.

**이 단계는 네 부분이다**: 구조 → 기술 스택 → 배치·자동 실행 → 안정성.

## 1부. 시스템 구조

### 1-1. 통합인가 분리인가
- 화면과 서버를 한 프로젝트로 둘 것인가, 나눌 것인가?
- 판단 기준: **단일 목적의 시스템이면 통합**, 여러 시스템이 공용으로 쓸 허브면 **분리**.
- 나중에 커질 가능성이 있으면 AI에게 이렇게 요청한다:
  `"기능 단위와 규모가 커질 수 있으니 확장성이 보장되는 구성으로 다시 제안해 줘."`

> AI의 첫 제안은 대체로 **가장 단순한 통합 구성**이다. 그게 맞는 경우가 많지만,
> 맞는지 한 번은 되물어야 한다. 되묻지 않으면 확장이 필요할 때 통째로 옮기게 된다.

### 1-2. 구성 요소
필요한 것만 고른다. 없어도 되는 걸 넣는 게 과설계다.

| 요소 | 언제 필요한가 |
|---|---|
| 화면(프론트) | 사람이 브라우저로 쓸 때 |
| API 서버 | 화면 외의 것이 호출할 때, 또는 분리 구성일 때 |
| 데이터베이스 | 저장할 상태가 있을 때 (거의 항상) |
| 작업 대기열 | 오래 걸리는 일을 요청과 분리해야 할 때 |
| 워커 | 대기열의 일을 처리할 주체가 필요할 때 |
| 스케줄러(크론) | 시간에 맞춰 자동 실행할 일이 있을 때 |
| 캐시 | 같은 조회가 반복되고 느릴 때 (**측정 전엔 넣지 않는다**) |
| 파일 저장소 | 사용자 업로드 파일이 있을 때 |

### 1-3. 데이터 흐름
S2의 핵심 시나리오를 구성 요소 위에 그린다.
"사용자 행동 → 어디를 거쳐 → 어디에 저장되고 → 무엇이 반응하나"를 문장으로 적는다.

### 1-4. 환경 분리
- 로컬 / 스테이징 / 프로덕션 — 몇 개를 둘 것인가? (**최소 로컬 + 프로덕션**)
- 각 환경이 무슨 데이터를 쓰나? (프로덕션 데이터를 로컬에 내려받지 않는다)
- 어떤 브랜치가 어떤 환경으로 가나?

## 2부. 기술 스택 결정 ★

### 진행 방법 — 학습 또는 실행 모드 선택

먼저 `docs/guides/decision-modes.md`를 읽는다. 새로운·되돌리기 어려운·보안/권한 영향이 큰·다음 프로젝트에도 반복될 선택은 **학습 모드**로 진행한다. 이미 기록된 기본값에 예외가 없으면 **실행 모드**로 적용하고 예외만 보고한다.

학습 모드에서는 한 기술씩이 아니라 **한 결정 묶음씩** 결정한다. 예를 들어 인증과 권한 접근 모델은 한 묶음이다. 답이 선택을 바꾸지 않는 질문은 하지 않는다.

> **여기는 "묶어 묻기"의 예외다** (`docs/guides/index.md`). 기술 결정은 서로 얽혀 있어서
> 지금 답할 수 있는 질문 자체가 적고, 사용자가 **배우면서 결정해야** 하므로 깊이가 왕복 수보다 중요하다.
> 다만 **서로 의존하지 않는 묶음끼리는 묶어도 된다** — 예를 들어 로깅 방식과 테스트 러너는 서로 무관하다.
> 실행 모드(이미 기록된 기본값 적용)에서는 묶어 내고 예외만 보고한다.

```
기술 스택을 결정하겠다. 지금은 구현이 아니라 기술 조합을 정하는 단계다.
docs/spec/ 의 S1~S3 산출물을 먼저 읽어라.

나는 이 영역의 전문가가 아니다. 의사결정을 할 수 있도록,
결정 묶음을 하나씩 순차적으로 물어봐 줘. 각 항목마다:
  ① 이건 어떤 기술 영역인가
  ② 주요 장점
  ③ 단점과 주의점 (특히 종속성)
  ④ 검토한 대체제와, 그중 이것을 추천하는 이유
을 제시하고 내 선택을 기다려라. 한 질문에 여러 개를 묶지 마.
```

궁금한 항목은 계속 파고들어도 된다. **이 인터뷰 자체가 산출물을 읽을 수 있는 눈을 만든다.**

### 결정할 항목 (프로젝트에 해당하는 것만)

언어·런타임 / 프레임워크 / 패키지 매니저 / UI 라이브러리 / 스타일 / 컴포넌트
데이터베이스 / 마이그레이션 도구 / 인증 방식 / 파일 저장 / 결제 / 메일·알림
작업 대기열 / 캐시 / 배포 대상 / CI 도구 / 테스트 도구 / 오류 추적 / 분석
코드 품질 도구 / 형상 관리 / 비밀값 관리

각 결정은 `docs/spec/stack.md`에 **[영역 | 선택 | 탈락 대체제 | 선택 이유 | 결정일]** 표로 기록한다. 기록하지 않으면 `.claude/hooks/guard-dependency.sh`가 그 패키지 설치를 막는다 — 훅은 stack.md를 근거로 판단하기 때문이다. 다음 프로젝트에도 쓸 기본값이면 적용 조건·재검토 조건을 추가로 남긴다. 기록하지 않으면 나중에 왜 그걸 골랐는지 아무도 모른다.

스택을 확정한 뒤 `docs/spec/code-conventions.md`를 채운다. formatter·linter·type checker·테스트의 **실행 명령**, 모듈 경계, 명명, 오류·로그·비밀값, 금지된 우회, PR 전 검사를 해당 프로젝트에서 실제로 실행 가능한 규칙으로 정한다.

**명령은 적기만 하지 말고 그 자리에서 한 번 실행한다.** 실행되지 않는 명령은 규칙이 아니라 희망이다. S6의 모든 완료 판정이 이 명령들에 걸려 있다.

### 판단 기준

- **보안 관련 선택은 웬만하면 안전한 쪽으로.** 단 명백히 과한 것(개인 프로젝트의 다중 인증 등)은 뺀다.
- **종속성을 확인한다.** 편한 통합 서비스는 나중에 걷어내기 어렵다. "규모가 작고 민감정보가 없으면 유지, 대외비·전용망이면 처음부터 배제"가 기본선.
- **유료 플랜은 개발 중 무료, 출시 직전 전환.**
- **테스트 도구는 넣는다.** 사람이 안 쓰던 이유는 작성 비용이었는데, AI가 작성하므로 그 이유가 사라졌다.
  프로파일이 Lite여도 넣는다. S6는 RED를 먼저 확인하는 것을 전제로 진행한다.
- **AI가 임의로 고른 것을 그대로 두지 않는다.** 특히 화면 기술은 지정하지 않으면 임의 선택된다.

### 되돌리기 어려운 결정은 ADR로

데이터베이스 종류, 통합/분리 구조, 인증 방식, 호스팅 등은
`docs/decisions/`에 ADR로 남긴다. 나중에 "왜 이렇게 했지"가 반드시 나온다.

## 3부. 배치·자동 실행

시간이나 사건에 맞춰 스스로 도는 일을 전부 나열한다.

각 항목마다:
- 언제 도나? (주기 또는 조건)
- 무엇을 하나?
- 실패하면? (재시도 횟수, 알릴 대상)
- **중복 실행되면?** (같은 일이 두 번 처리되면 안 되는 것을 식별한다)
- 한동안 멈춰 있었다면 밀린 것을 소급 처리하나, 건너뛰나?
- 휴일·업무시간 기준이 필요한가?

| 작업 | 주기 | 하는 일 | 실패 시 | 중복 방지 | 소급 처리 |
|---|---|---|---|---|---|
| | | | | | |

## 4부. 안정성 대비 7종 ★★

**이 절을 건너뛰면 안 된다.** 아래는 겪기 전엔 존재조차 모르는 항목들이다.
각각에 대해 "이 프로젝트에서는 이렇게 대비한다" 또는 "해당 없음(이유)"을 적는다.

| # | 항목 | 물어야 할 것 | 대비 |
|---|---|---|---|
| 1 | **사용자·권한** | 권한 없는 사람이 주소를 직접 치면? 남의 데이터에 접근되나? | |
| 2 | **외부 API 변경** | 연동 서비스가 형태를 바꾸면? 어댑터 층이 막아 주나? | |
| 3 | **인증 만료** | 토큰·키가 만료되면 무슨 일이 생기나? 만료를 감지하나? | |
| 4 | **데이터 오류** | 형태가 어긋난 값이 들어오면? 검증은 어디서 하나? | |
| 5 | **중복 실행** | 같은 요청이 두 번 오면 두 건이 생기나? 무엇을 기준으로 같다고 보나? | |
| 6 | **호출 한도** | 외부 서비스 한도를 넘으면? 우리를 향한 과다 호출은? | |
| 7 | **실행 실패** | 작업이 실패하면 누가 아나? 재시도하나? 몇 번? | |

추가로 반드시 확인:

- **비밀값 관리** — 키·비밀번호가 코드나 저장소에 들어가지 않는가? 환경 변수 파일이 형상 관리에서 제외되어 있는가?
  (`.claude/hooks/guard-secrets.sh`가 커밋 시점에 한 번 더 막지만, 훅은 마지막 방어선이지 설계가 아니다)
- **알림 채널의 이중화** — 알림 수단(메일 등) 자체가 고장 나면 아무도 모른다. 보조 채널을 둔다.
- **백업** — 무엇을, 얼마나 자주, 어디에? **복구를 실제로 해 봤는가?**
- **변경 이력** — 누가 언제 무엇을 바꿨는지 남는가?
- **입력 검증 위치** — 화면에서만 검증하면 소용없다. **서버가 다시 검증한다.**
- **값 재계산** — 금액처럼 중요한 값은 클라이언트가 보낸 것을 믿지 않고 **서버가 다시 계산한다.**

## 과설계 잘라내기

AI의 제안이 요구사항보다 크면 축소한다. 판단 기준:

- 이 항목을 뺐을 때 **당장** 무슨 문제가 생기나? "언젠가 필요할 것 같다"면 뺀다.
- 사용자가 몇 명인가? 규모에 안 맞는 장치는 뺀다.
- 뺐다가 나중에 넣기 어려운가? 쉽게 넣을 수 있으면 지금은 뺀다.
  (반대로 나중에 넣기 어려운 것 — 데이터 구조, 권한 모델, 이력 보관 — 은 지금 넣는다)

## 자주 빠지는 함정

| 함정 | 증상 | 처방 |
|---|---|---|
| 스택 결정 생략 | AI가 고른 기술로 반쯤 지어져 있음 | 2부를 반드시 수행 |
| 안정성 절 생략 | 배포 후 조용히 데이터가 어긋남 | 7종 표를 전부 채운다 |
| 비밀값 커밋 | 키가 저장소에 남음 | 첫 커밋 전에 제외 설정 확인 |
| 중복 실행 미대비 | 알림이 두 번 가고 건이 두 개 생김 | 5번 항목에 판별 기준 명시 |
| 캐시 선넣기 | 복잡도만 늘고 값이 어긋남 | 느린 걸 측정한 뒤에 넣는다 |
| 과설계 방치 | 권한 5단계, 실사용자 2명 | 축소안을 함께 제시받는다 |

## 완료 조건 (DoD)

> 표식 규칙: `(Standard+)`는 Standard·Full만, `(Full)`은 Full만 본다 — 표식 없는 항목은 모든 프로파일이 본다.
> `(사람 확인)`은 에이전트가 대신 체크하지 않는다 — 사용자에게 요청하고 받은 답을 기록한다. 근거: `docs/guides/profiles.md`.

- [ ] 통합/분리 구조가 근거와 함께 정해져 있다 (Standard+)
- [ ] 구성 요소 목록이 있고, 각각 왜 필요한지 적혀 있다 (Standard+)
- [ ] 환경 분리와 브랜치 대응이 정해져 있다 (Standard+)
- [ ] `docs/spec/stack.md`에 모든 기술 결정이 **[영역 | 선택 | 탈락 대체제 | 선택 이유 | 결정일]** 표로 있다
- [ ] `docs/spec/code-conventions.md` 1절의 검사 명령이 실행 가능한 형태로 있다
- [ ] 1절의 검사 명령을 **실제로 한 번 실행**해 결과를 확인했다
- [ ] `docs/spec/code-conventions.md`의 경계·오류·테스트·금지된 우회(스택 문법으로 구체화)·리뷰 규칙이 채워져 있다 (Standard+)
- [ ] 되돌리기 어려운 결정이 ADR로 기록되어 있다
- [ ] 자동 실행 작업이 표로 정리되어 있다 (중복 방지·실패 처리 포함) (Standard+)
- [ ] **프로파일 범위의 안정성 항목이 전부 "대비" 또는 "해당 없음(이유)"으로 채워져 있다** —
      Lite는 1·4·5번, Standard·Full은 7종 전부. 범위 밖 항목은 `해당 없음(프로파일)`로 표기한다
- [ ] 백업 복구를 실제로 실연해 봤다 (Full) (사람 확인)
- [ ] 비밀값이 형상 관리에서 제외되도록 설정되어 있다

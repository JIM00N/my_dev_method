# S5 — 시각 설계

**읽어야 할 때**: S4의 DoD 통과 후, **화면이 있는 프로젝트일 때만.**
**화면이 없으면 이 단계를 건너뛰고** `docs/guides/S6-build.md`로 간다. 프로파일 Lite는 화면이 있어도 스킵할 수 있다 — 기본 테마로 S6에서 함께 다룬다.
**입력**: `docs/spec/interface.md`, `docs/spec/stack.md`, `docs/guides/profiles.md`(범위 확인)
**산출물**: `docs/spec/ui.md`
**모드**: 여기서부터 **검수 루프 모드** — 인터뷰는 끝났다
**다음**: S6 구축·검수·배포

---

## 왜 이 단계인가

**UI 결정은 취향이 아니라 논리다.** 어울리는 걸 짝지어 고르는 게 아니라, S3에서 박아 둔
"화면별 핵심 목표"에 비추어 답이 정해지는 영역이다.

다만 현재 모델들은 이 영역에서 첫 제안이 거의 맞는다. **초기 구축에서는 개입할 일이 많지 않다.**
개입이 필요해지는 건 실사용 후 고도화할 때다. 그러니 여기서 시간을 오래 쓰지 않는다.

## 시작 전 반드시 지정

**기술을 미리 지정하지 않으면 AI가 임의로 고른다.** S4에서 정한 것을 명시적으로 전달한다.

- 스타일 체계와 컴포넌트 라이브러리 (`docs/spec/stack.md`에서)
- 기본 테마로 시작할지, 테마를 입힐지
- 우선 대상: 데스크톱 우선 / 모바일 우선

그리고 **지금까지의 결정을 전부 문서로 정리한 뒤** 화면 작업을 시작한다.
S1~S4 산출물이 컨텍스트에 없으면 AI는 화면을 상상해서 만든다.

## 1. 프레임 목업

- S3의 화면 목록을 전부 뽑아 뼈대만 만든다. 색·이미지 없이 배치와 요소만.
- **예상보다 화면 수가 3~5배 늘어나는 게 정상이다.** 목록·상세·편집·빈 상태·오류 상태가 각각 화면이다.
- 만들었으면 로컬에서 **직접 눌러 본다.** 보는 것과 누르는 것은 다르다.

빠지기 쉬운 화면:
- 데이터가 하나도 없을 때 (빈 상태)
- 불러오는 중
- 오류가 났을 때
- 권한이 없을 때
- 결과가 아주 많을 때

## 2. UI 의사결정 — 논리 규칙

취향으로 다투지 말고 아래 규칙으로 판단한다.

| 상황 | 규칙 |
|---|---|
| 여러 개 중 고르게 할 때 | 나열형 데이터는 체크박스·선택 목록. 자유 입력을 쓰지 않는다 |
| 한 화면의 버튼 위계 | **핵심 행동은 화면당 하나.** 나머지는 시각적으로 낮춘다 |
| 빨간색 | **지연·오류·위험에만.** 강조 용도로 쓰지 않는다 |
| 되돌릴 수 없는 행동 | 확인 절차를 붙인다. 다른 버튼과 나란히 두지 않는다 |
| 목록 | 무엇으로 정렬되는지 보이게 한다. 기본 정렬을 정한다 |
| 상태 표시 | S2의 상태 어휘를 그대로 쓴다. 화면마다 다른 말로 바꾸지 않는다 |
| 클릭했는데 반응 없음 | 누를 수 있는 것과 없는 것이 구별되어야 한다 ← **가장 흔한 혼동** |

## 3. 테마 선택

쇼핑하듯 고르지 말고 조건에서 도출한다.

- 어떤 인상을 줘야 하나? (전문성 / 친근함 / 속도감)
- 지켜야 할 브랜드가 있나? 있으면 참고 이미지를 제공한다
- 어떤 환경에서 보나? (이동 중 모바일이면 대비를 높인다)
- 글꼴은? 업무용이면 단정·중립적인 것

> **테마 이름만 던지지 않는다.** "글래스모피즘으로 해 줘"라고만 하면 기본 형태에 색만 입혀 나온다.
> 먼저 **"네가 생각하는 그 테마의 정의와 구현 전략을 설명해 줘"**로 받아 보고,
> 합의한 다음 적용한다.

> 업무용 화면은 **데이터 가독성이 최우선**이다. 화려한 효과를 전면에 쓰면 오히려 해롭다.
> 쓰더라도 머리말·메뉴·요약 영역에만 절제해서 쓰고, 데이터가 놓이는 곳은 불투명하게 둔다.

## 4. 검수

- 로컬에서 화면을 하나씩 눌러 본다.
- 어색한 곳은 **위치와 현상을 구체적으로** 지적한다 (`S6-build.md` 5-3의 리포트 형식).
- 이 단계의 문제도 `docs/quality/issues.md`에 기록한다.
- 빈 상태·오류·권한없음 화면은 **자동 테스트로도 덮는다.** 사람이 매번 확인하기 가장 쉽게 빠지는 화면들이다.

## 자주 빠지는 함정

| 함정 | 증상 | 처방 |
|---|---|---|
| 기술 미지정 | 스택에 없는 라이브러리가 들어옴 | 시작 전에 명시적으로 전달 |
| 맥락 없이 시작 | 스펙과 다른 화면이 나옴 | S1~S4 산출물을 문서로 정리한 뒤 시작 |
| 빈 상태 누락 | 데이터 없을 때 화면이 깨짐 | 1절의 5가지 상태를 목록에 넣는다 |
| 누를 수 있는지 불분명 | 사용자가 눌렀는데 무반응이라 여김 | 시각적 구별을 명확히 |
| 색 남용 | 빨강이 강조로 쓰여 위험 신호가 묻힘 | 2절 규칙 적용 |
| 여기서 시간 과다 | 화면만 다듬다가 기능이 안 나옴 | 초기 구축에서는 빠르게 통과시킨다 |

## 완료 조건 (DoD)

> 표식 규칙: `(Standard+)`는 Standard·Full만, `(Full)`은 Full만 본다 — 표식 없는 항목은 모든 프로파일이 본다.
> `(사람 확인)`은 에이전트가 대신 체크하지 않는다 — 사용자에게 요청하고 받은 답을 기록한다. 근거: `docs/guides/profiles.md`.

- [ ] 스타일·컴포넌트 기술이 `docs/spec/stack.md`대로 지정된 상태로 작업했다
- [ ] S3의 모든 화면에 대해 목업이 존재한다
- [ ] 빈 상태·로딩·오류·권한없음 화면이 각각 있다
- [ ] 화면마다 핵심 행동이 하나로 정해져 있다
- [ ] 상태 표시 어휘가 S2와 일치한다
- [ ] 테마가 조건에서 도출된 근거와 함께 정해져 있다 (Standard+)
- [ ] 사용자가 로컬에서 직접 눌러 보며 확인했다 (사람 확인)
- [ ] 발견한 문제가 `docs/quality/issues.md`에 기록되었다
- [ ] 산출물에 양식 플레이스홀더(`YYYY-MM-DD`·`미작성`·예시 텍스트)가 남아 있지 않다
- [ ] `docs/status/STATUS.md`의 S5가 ✅ 로 갱신되었다

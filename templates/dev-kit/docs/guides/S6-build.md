# S6 — 구축·검수·배포

**읽어야 할 때**: S4(화면 있으면 S5)의 DoD 통과 후. 그리고 **모든 사이클마다 반복해서.**
**입력**: `docs/spec/*` 전부, `docs/plan/cycles/C<nn>-*.md`, `docs/quality/rules-learned.md`
**산출물**: 코드, **자동 테스트**, `docs/quality/issues.md`, `docs/quality/test-scenarios.md`
**모드**: 검수 루프 — 구현 → 검수 요청 → 사람 확인 → 피드백 → 수정

## 왜 이 단계가 가장 실패하기 쉬운가

설계가 아무리 좋아도 여기서 **한 번에 끝까지 만들려고 하면** 무너진다.
문제 하나를 잡으면 다른 게 튀어나오는 상태가 되고, 그때부터는 무엇을 고치고 있는지도 모르게 된다.

방어 장치는 세 개다: **작게 자르기**, **테스트를 먼저 쓰기**, **기록하며 검수하기**.

## 1. 사이클로 자른다 ★

한 사이클 = 「구축 → 검수 → 안정화 → 배포」 한 바퀴.

- 첫 사이클은 **가장 좁은 동작 경로 하나**만 담는다. 처음부터 끝까지 이어지되 얇은 것.
- 한 사이클의 목표는 **"사람이 직접 눌러서 끝까지 통과시킬 수 있는 상태"**다.
- `docs/plan/cycles/C<nn>-<이름>.md`를 만들고 이번 사이클에 담을 것을 적는다.
- 권한 영향이 있거나 병렬로 돌릴 작업은 `docs/plan/stories/ST-<nnn>-*.md`로 쪼갠다.
  Story 문서가 그 에이전트의 **영향 범위·권한 계약·검증 방법**이다. (프로파일 Lite는 생략하고 사이클 문서에 흡수)
- **사이클에 없는 것은 만들지 않는다.** 하고 싶은 게 생기면 `docs/plan/roadmap.md` 백로그로.

한 사이클이 너무 크다는 신호:
- 완료 조건이 10개를 넘는다
- 손대는 화면이 5개를 넘는다
- "이것도 있어야 저게 되는데"가 세 번 이상 나온다

→ 이 중 하나라도 해당하면 자른다.

## 3. 구현 — 작은 TDD 사이클 ★★

**AI가 코드를 쓰므로 테스트 작성 비용은 더 이상 테스트를 안 쓸 이유가 되지 못한다.**
사람이 테스트를 건너뛰던 유일한 이유가 사라졌는데도 건너뛰면, 그건 방법론이 아니라 습관이다.

### 3-1. 한 덩어리 = RED → GREEN → REFACTOR

새 함수·새 행동마다:

```
① RED    — 원하는 행동의 테스트를 먼저 쓰고, 실제로 실패하는 것을 확인한다
② GREEN  — 그 테스트를 통과시키는 최소 구현을 한다
③ REFACTOR — 테스트를 초록으로 유지한 채 정리한다
```

**RED를 눈으로 확인하지 않은 테스트는 테스트가 아니다.** 처음부터 통과하는 테스트는
아무것도 검증하지 않고 있을 가능성이 높다. RED 명령과 그 출력을 보고에 남긴다.

- 권한 영향이 있으면 **허용 경로와 거부 경로를 둘 다** 테스트한다. 거부 경로가 없는 권한 테스트는 절반이다.
- 버그 수정은 **재현 테스트를 먼저** 추가한다. 재현되지 않는 수정은 수정이 아니다.
- 테스트는 내부 호출 횟수가 아니라 **사용자·도메인 행동**을 검증한다. mock은 불가피한 경계에만.

### 3-2. 검증을 약화시켜 통과시키지 않는다 ★★

**이것이 에이전트에게 가장 흔한 실패다.** 사람 개발자에게는 드물고 AI에게는 자주 일어난다.
막혔을 때 나오는 자연스러운 다음 수가 전부 여기 해당하기 때문이다.

| 금지 | 대신 |
|---|---|
| 실패하는 테스트를 지우거나 `skip` 처리 | 왜 실패하는지 `issues.md`에 적고 멈춘다 |
| 단언(assert)을 느슨하게 바꿔 통과시킴 | 기대값이 틀렸다면 **스펙을 먼저** 고친다 |
| `any` · `as` · `# type: ignore`로 타입 오류를 덮음 | 타입이 안 맞으면 경계 설계를 다시 본다 |
| 예외를 잡아서 삼킴 (`catch {}`, `except: pass`) | 처리하거나, 올리거나, 로그를 남긴다 |
| 린트를 `disable` 주석으로 끔 | 규칙이 틀렸으면 `code-conventions.md`를 고치고 이유를 남긴다 |
| 안 쓰는 것 같아 보이는 기존 코드를 지움 | 참조를 확인하기 전에는 지우지 않는다 |
| 스펙 항목을 조용히 빼고 "완료" 보고 | 못 한 것을 **못 했다고 말한다** |

`CLAUDE.md` 절대 규칙 11이 이것이다. **초록불은 목표가 아니라 증거다.**
증거를 만들 수 없으면 증거를 위조하는 게 아니라 막혔다고 보고한다.

### 3-3. 한 덩어리가 끝나면

- `code-conventions.md` 1절의 검사 명령을 **실제로 실행**한다. "통과할 것이다"는 실행이 아니다.
- 구현이 `spec/`과 어긋났으면 **코드가 아니라 스펙을 먼저** 고치고 최근 결정에 한 줄 남긴다.
- `docs/status/STATUS.md`의 "지금 하고 있는 일"과 "다음 3가지"를 갱신한다.

## 4. 진행 상태 표시 규칙

작업 중 **다음 시점마다** `docs/status/STATUS.md`를 갱신한다:

| 시점 | 갱신 내용 |
|---|---|
| 사이클 시작 | 현재 사이클 · 단계를 🔵 진행 중으로 |
| 구현 한 덩어리를 끝냈을 때 | "지금 하고 있는 일" · "다음 3가지" |
| 검수로 넘길 때 | 🟡 검수 대기로 |
| 막혔을 때 | ⛔ 막힘 + 무엇에 막혔는지 + 사용자 결정이 필요한지 |
| 사이클 종료 | ✅ 완료 + DoD 통과일 |
| **세션 종료 시 (항상)** | 위 전부 |

상태 어휘는 `⬜ 대기 / 🔵 진행 중 / 🟡 검수 대기 / ✅ 완료 / ⛔ 막힘` 5개만 쓴다.

> **"완료했습니다"라고 보고하기 전에** 사이클 문서의 완료 조건을 실제로 하나씩 대조한다.
> 대조하지 않은 완료 보고는 하지 않는다.
> 세션 종료 시 STATUS를 갱신하지 않으면 `.claude/hooks/status-updated.sh`가 종료를 막는다.

## 5. 검수 — 사람이 직접 누른다 ★★

**"동작합니다"는 검수가 아니다.** 자동 테스트가 초록인 것도 검수가 아니다.
자동 테스트는 **내가 예상한 것**만 본다. 사람이 누르는 이유는 예상 밖을 보기 위해서다.

### 5-1. 검수 시나리오를 먼저 받는다

```
이번 사이클에 대해 내가 직접 확인할 검수 시나리오를 만들어 docs/quality/test-scenarios.md 에 적어 줘.
각 항목마다: 무엇을 누르는지 / 정상이면 어떻게 보여야 하는지 / 어떤 데이터 상태를 전제하는지.
이미 자동 테스트가 덮고 있는 것은 그렇다고 표시해 줘 — 사람은 덮이지 않은 것부터 본다.
정상 경로뿐 아니라 아래도 포함해라.
  - 필수 값을 비우고 진행
  - 같은 동작을 두 번 반복
  - 권한 없는 상태에서 접근
  - 데이터가 하나도 없을 때
  - 아주 많을 때
  - 중간에 취소
```

### 5-2. 직접 누른다

- 시나리오를 순서대로 실행한다.
- 횟수는 프로파일을 따른다 (`guides/profiles.md`) — **Full은 15~20회, Standard는 5~10회, Lite는 핵심 경로 1회.**
- 정상 경로만 밟지 않는다. 사용자는 아무 순서로나 누른다.

### 5-3. 문제를 리포트한다

**위치와 현상을 구체적으로** 적는다. "안 돼요"는 리포트가 아니다.

```
<어느 화면/기능>의 <어느 단계>에서, <무엇을 하면>,
<이 현상>이 나타난다. 전제 조건은 <이런 상태>다.
기대한 동작은 <이것>이다. 원인 확인 및 해결하라.
```

### 5-4. 버그를 잡은 시나리오는 자동 테스트로 승격한다 ★★

이 절이 없으면 수동 검수는 **사이클이 늘수록 조용히 죽는다.**
사이클 5에서 사이클 2의 시나리오를 다시 클릭하는 사람은 없다. 안 하게 되고, 그때부터 장치는 없는 것과 같다.

```
사람이 처음 보는 것을 본다 → 버그를 잡는다 → 그 시나리오는 자동이 본다
```

- 검수에서 **문제를 하나라도 잡아낸 시나리오**는 자동 테스트로 옮긴다. 예외 없다.
- `test-scenarios.md`의 각 항목에 `자동화` 칸을 채운다: `⬜ 수동만` / `✅ 자동화됨(테스트 이름)` / `➖ 자동화 불가(이유)`.
- 자동화 불가는 진짜 불가일 때만 쓴다 — 시각적 인상, 실제 메일 수신, 외부 결제 승인 같은 것.
- 다음 사이클의 수동 검수는 **자동화되지 않은 항목부터** 본다.

이건 `rules-learned.md` 승격 장치의 테스트판이다. 같은 구조다 — **두 번째부터는 사람이 하지 않는다.**

## 6. 문제 기록 ★★

### 6-1. 기록 먼저, 수정은 그다음

발견한 모든 문제를 `docs/quality/issues.md`에 **먼저 적고** 고친다.
기록 없이 고치면 그 순간은 편하지만 **재발 패턴이 보이지 않게 된다.**

기록 대상:
- 검수에서 나온 버그
- 자동 테스트가 잡은 회귀
- 코드리뷰 지적
- 배포 중 실패
- "이상한데 일단 넘어간" 것 (특히 이것)

### 6-2. 이슈 닫는 절차

```
기록 → 재현 테스트 추가(RED) → 원인 분석 → 수정 → 같은 시나리오로 재검수 → 통과하면 닫음
```

**재검수 없이 닫지 않는다.** 수정했다는 것과 고쳐졌다는 것은 다르다.
검증된 이슈는 `docs/quality/archive/<유형>/`로 옮기고 열린 목록에서 제거한다.

### 6-3. 재발하면 규칙으로 승격 ★

같은 유형의 문제가 **2번째** 발생하면 `docs/quality/rules-learned.md`에 규칙으로 올린다.

이게 이 키트의 핵심 장치다. 이슈 로그만 있으면 문제는 쌓이기만 하고 AI는 같은 실수를 반복한다.
규칙으로 올라가야 다음 사이클의 구축 전 확인에서 걸린다.

종합·승격은 **구현 담당이 아니라 `error-learning` 서브에이전트**가 한다 (`/ingest-errors`).
구현 관점과 학습 관점을 같은 작업으로 섞지 않는다. 절차는 `guides/error-learning-ingest.md`.

규칙이 10개를 넘으면 해당 단계 가이드 본문으로 이관한다.

## 7. 배포

### 7-1. 배포 전 확인

- [ ] `code-conventions.md` 1절의 검사 명령이 전부 통과했다 (실행 결과가 남아 있다)
- [ ] 검수 시나리오를 전부 통과했다
- [ ] 열린 치명·높음 이슈가 없다
- [ ] 비밀값이 저장소에 들어가 있지 않다 (훅이 막지만 diff를 눈으로도 본다)
- [ ] `docs/spec/architecture.md`의 안정성 대비가 **말이 아니라 코드로** 존재한다
- [ ] 되돌리는 방법이 있다 (이전 버전으로 돌아갈 수 있는가)

### 7-2. 환경 순서

```
로컬 → 스테이징 → 프로덕션
```

프로파일이 정한다 (`guides/profiles.md`) — Lite는 로컬만, Standard는 로컬+프로덕션, **Full은 스테이징을 생략하지 않는다.**

- 브랜치가 곧 환경이다. 작업 브랜치 → 스테이징, 주 브랜치 → 프로덕션.
- **스테이징 검수를 생략하지 않는다.** 로컬에 없던 오류가 스테이징에서 나온다 —
  로컬에만 있던 데이터, 로컬에만 있던 설정 때문이다. 그걸 잡으라고 스테이징이 있다.
- 환경이 똑같이 생겼으면 **환경 표시를 화면에 넣는다** (색이 다른 배지 등).
  어느 환경을 보고 있는지 착각해서 생기는 사고가 실제로 많다.

### 7-3. 배포 후

- 실제 주소로 들어가 핵심 경로 한 바퀴를 다시 돈다.
- 오류 추적·로그가 실제로 들어오는지 확인한다.
- **인증·권한이 완성되기 전에는 실제 데이터를 넣지 않는다.**
  임시 공개 상태에 진짜 데이터를 넣는 것이 가장 흔한 사고다.
- `docs/status/STATUS.md`에 배포 사실과 버전을 기록한다.

## 8. 사이클 종료

`/cycle-close`가 이 순서를 그대로 수행한다.

- [ ] 사이클 문서의 완료 조건 전부 대조 완료 (가정하지 않고 실제로)
- [ ] 품질 검사 명령이 전부 통과 — 결과를 붙인다
- [ ] **스펙 드리프트 대조** — 이번 사이클이 `spec/domain.md` 전이표·`spec/interface.md` 표면과 어긋나지 않는가?
      어긋났으면 스펙을 고치고 `STATUS.md` 최근 결정에 남긴다
- [ ] 버그를 잡은 검수 시나리오가 자동 테스트로 승격됨
- [ ] 열린 이슈를 다음 사이클로 넘기거나 백로그로 이동 (치명·높음이 열려 있으면 닫지 않는다)
- [ ] `/ingest-errors`로 학습 인제스트 → `rules-learned.md`에 이번에 배운 것이 반영됨
- [ ] 사이클·Story 문서를 `docs/plan/archive/`로 이동
- [ ] `docs/status/STATUS.md` 갱신
- [ ] 다음 사이클 문서 생성

### 스펙 드리프트를 왜 매번 보나

"코드가 스펙을 앞서가지 않는다"는 규칙만 있고 **어긋났는지 확인하는 절차가 없으면**,
사이클 3~4쯤에 `spec/`은 읽으면 오히려 해로운 문서가 된다. 그 시점부터 AI는 틀린 문서를 근거로 코딩한다.
드리프트는 한 사이클 안에서는 몇 줄이고, 다섯 사이클 뒤에는 다시 쓰는 일이 된다.

## 자주 빠지는 함정

| 함정 | 증상 | 처방 |
|---|---|---|
| 한 번에 다 만들기 | 두더지 잡기 시작 | 1절로 돌아가 사이클을 자른다 |
| 테스트 없이 구현 | 사이클 3에서 사이클 1이 깨진 걸 모름 | 3-1 — RED를 먼저 본다 |
| **초록불을 위해 검증을 약화** | 테스트는 통과하는데 기능이 안 됨 | 3-2 — 막혔으면 막혔다고 보고한다 |
| 수동 검수만 쌓임 | 시나리오 40개, 실제로는 아무도 안 돌림 | 5-4 — 버그 잡은 것은 자동으로 |
| 검수 없이 완료 선언 | 배포 후 기본 동작이 안 됨 | 5절 — 사람이 직접 |
| 기록 없이 수정 | 같은 버그가 계속 재발 | 6-1 — 기록 먼저 |
| 재검수 없이 닫기 | 고쳤다던 게 그대로 | 6-2 — 같은 시나리오로 재확인 |
| 스펙 드리프트 방치 | spec/이 현실과 다른 소설이 됨 | 8절 — 사이클마다 대조 |
| 스테이징 생략 | 프로덕션에서 처음 터짐 | 7-2 — 순서를 지킨다 |
| 상태 미갱신 | 다음 세션이 맥락 없이 시작 | 4절 — 세션 종료 시 항상 |
| 범위 슬금슬금 확장 | 사이클이 안 끝남 | 백로그로 보낸다 |

## 완료 조건 (DoD) — 사이클마다

- [ ] 새 행동마다 테스트가 **먼저 실패한 것(RED)을 확인**한 뒤 구현했다
- [ ] `code-conventions.md` 1절의 검사 명령이 전부 통과했고 결과가 남아 있다
- [ ] 검증을 약화시켜(테스트 삭제·단언 완화·타입 무시·예외 삼킴·린트 비활성화) 통과시킨 곳이 없다
- [ ] 권한 영향이 있는 곳은 허용·거부 경로를 둘 다 테스트했다
- [ ] 사이클 문서의 완료 조건을 하나씩 대조했다
- [ ] 검수 시나리오가 존재하고 전부 통과했다 (횟수는 프로파일 기준)
- [ ] 버그를 잡은 시나리오가 자동 테스트로 승격되었다
- [ ] 발견된 모든 문제가 `issues.md`에 기록되어 있다
- [ ] 열린 치명·높음 이슈가 없다
- [ ] 재발한 문제가 `rules-learned.md`에 규칙으로 올라갔다
- [ ] 구현과 `spec/`의 드리프트를 대조했고, 어긋난 곳은 스펙을 먼저 고쳤다
- [ ] 스테이징을 거쳐 배포되었다 (또는 프로파일상 대상이 아님이 명시됨)
- [ ] 배포 후 핵심 경로를 실제 환경에서 확인했다
- [ ] `docs/status/STATUS.md`가 갱신되었다

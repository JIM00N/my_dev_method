# 에러 학습 인제스트

**읽어야 할 때**: 새 에러·버그·검수 실패·운영 장애를 기록했거나, 누적된 에러에서 재발 방지 지식을 뽑을 때.
**역할 분리**: 구현 에이전트는 에러를 기록·수정·재검수한다. **Error Learning Agent**는 새 기록을 종합·인제스트해 규칙·검수·설계 문서에 반영한다. 둘을 같은 작업으로 취급하지 않는다.
**실행**: `/ingest-errors` — `.claude/agents/error-learning.md`로 정의된 서브에이전트가 이 절차를 수행한다. 그 에이전트는 코드를 고칠 수 없다.

## 1. 즉시 기록 — 구현 담당

에러가 생길 때마다 `docs/quality/issues.md`에 즉시 기록한다. 수정 전이어야 하며, 최소 항목은 그 파일 양식의 발견·심각도·재현 절차·전제 조건·기대/실제 동작·유형이다 — 양식이 정본이다.

새 기록의 `학습 인제스트` 상태는 `대기`로 둔다. 기록 없이 수정만 하는 것은 금지한다.

## 2. 별도 에이전트의 인제스트 — Error Learning Agent

새로운 또는 갱신된 이슈가 있으면 별도 에이전트가 다음만 수행한다. 코드 구현·배포·기술 선택을 임의로 바꾸지 않는다.

1. `issues.md`에서 `학습 인제스트: 대기`인 항목을 찾는다.
2. 원인·조치·재검수 근거가 충분한지 확인한다. 부족하면 `보류`로 표시하고 구현 담당에게 필요한 사실만 요청한다.
3. `learning-log.md`의 이전 종합을 읽어 중복을 확인하고, 여러 에러를 유형·공통 원인·영향 Story/사이클별로 종합한다. 유형은 `docs/quality/index.md`의 유형 표에서 고른다.
4. 아래 산출물을 갱신한다.
   - `rules-learned.md`: 재발 방지 규칙이 될 일반화된 학습
   - `test-scenarios.md`: 앞으로 반복할 검수 시나리오. **버그를 잡아낸 시나리오는 자동 테스트 승격 후보로 표시한다** (`S6-build.md` 5-4)
   - 관련 guide/spec/ADR: 실제로 변경이 필요한 경우만, 영향 목록을 남겨 Main에 통합 요청
   - `learning-log.md`: 원본 이슈 ID, 종합 결과, 수정한 문서, 남은 질문
5. 이슈에 `학습 인제스트: 완료`와 learning-log 링크를 남긴다.

같은 유형이 2번째면 규칙 승격은 필수다. 한 번의 예외를 과도한 전역 규칙으로 일반화하지 않는다.

## 3. Main의 통합 책임

Main은 Error Learning Agent가 제안한 guide/spec/ADR 변경의 영향 범위를 검토하고, 다른 Story·문서와 충돌하지 않는지 확인한 뒤 최종 반영한다. 학습 에이전트의 “인제스트 완료”는 코드·제품 변경의 승인이나 전역 정합성 완료를 뜻하지 않는다.

## 학습 로그 형식

```markdown
## YYYY-MM-DD — <유형> 종합
- 원본 이슈: #012, #019
- 공통 원인:
- 영향 Story/사이클:
- 일반화 가능한 규칙 / 규칙 아님:
- 추가·수정한 검수 시나리오:
- 자동 테스트로 승격한 것 / 승격 불가(이유):
- 영향을 받는 문서와 Main 통합 상태:
- 남은 질문:
```

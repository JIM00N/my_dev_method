# guides — 단계별 실행 지시서

각 단계를 **어떻게** 수행하는지의 절차서. 프로젝트가 달라져도 거의 그대로 쓴다.

**한 번에 하나만 읽는다.** 지금 단계가 아닌 가이드는 읽지 않는다 — 컨텍스트 낭비이고, 앞선 단계의 결정을 뒤집게 만든다.

**진입점은 S0 하나다.** `/mdm-adopt`가 계획 문서를 **저장소 안에서 먼저 찾고**, 없으면 밖에 있는지 묻고,
그래도 없으면 `/mdm-plan`으로 보낸다 — `/mdm-plan`이 만든 계획도 S0로 돌아온다.
어느 경로든 S1~S5를 처음부터 밟지 않는다. S0의 **계약 확인이 `❌ 갭`으로 판정한 절만** 편다.
갭은 대체로 S2 ②③④(데이터·상태 전이표·권한 표)와 S4 2·4부(스택·검사 명령·안정성)다.
**단 `/mdm-plan`이 만든 계획이면 권한은 대체로 갭이 아니다** — 계획 2절이 담는다 (`docs/spec/source-map.md` 4절).
**무엇이 갭인지는 상류마다 다르다** — 권한과 데이터를 담아 주는 상류도 있다. 단정하지 않고 확인한다.

## 단계 목록

| 단계 | 파일 | 무엇을 정하나 | 스킵 조건 |
|---|---|---|---|
| **S0** | `S0-adopt.md` | 계획 문서를 찾아 대조·ID 정리·**계약 확인** | 없음 — 모든 프로젝트의 진입점 |
| S1 | `S1-problem.md` | 누가 쓰고, 무슨 문제를 풀고, 어디까지 만드나 | 없음 |
| S2 | `S2-domain.md` | 어떤 데이터가 있고 어떤 상태를 오가나 | 저장할 데이터가 없으면 축약 |
| S3 | `S3-interface.md` | 사용자·외부와 만나는 표면(화면/API/CLI) | 없음 |

## 전 단계 공통 (단계가 아니라 판단 기준)

| 파일 | 언제 읽나 | 무엇을 정하나 |
|---|---|---|
| `plan.md` | S0에서 계획 문서를 못 찾았을 때 (`/mdm-plan`) | 요구사항·검증 조건·화면을 ID 붙여 만든다. 압박 → 묶어 묻기 → 작성 → 검증 |
| `ready.md` | Story 를 열기 직전 (`/mdm-ready`) | **개발 준비 슬롯 12칸 + Story 크기 판정** — AI 가 초안을 채우고, 크기를 판정한 뒤, 갈리는 것만 묶어 묻는다. **슬롯은 모호함을, 크기 판정은 크기와 응집도를 본다.** **계층이 다르면 묻는 것도 다르다**: 요구사항은 *무엇이 되면 됐나*, Story 는 *어떻게 동작하나* |
| `profiles.md` | S1에서 사분면을 확정한 직후, 각 단계 진입 시, 절차가 무겁게 느껴질 때 | 절차량 — Lite / Standard / Full (각 가이드 DoD의 프로파일 표식이 실제 게이트) |
| `commit-policy.md` | S1에서 프로파일과 함께, 그리고 커밋 방식을 바꾸고 싶을 때 | **승인 모드 / 보고 모드** — 커밋 버튼을 누가 누르는가. 판정이 아니라 사용자 선택. `/mdm-review` 통과 요구와 「어느 쪽이든 반드시 묻는 것」 표는 모드와 무관하게 유지 |
| `decision-modes.md` | 기술·권한·구조를 새로 선택하거나 기본값을 적용할 때 | 학습 모드와 실행 모드 전환, 재사용 가능한 기본 결정 |
| `error-learning-ingest.md` | 새 에러 기록이 생겼을 때 (`/mdm-ingest-errors`) | 별도 에이전트의 종합·인제스트 절차 |

**문서 정합성은 스크립트가, 판단은 서브에이전트가** 맡는다.
`/mdm-review`는 1단계 `.claude/scripts/check-consistency.sh`(기계 — 고아 ID·커버리지·참조 깨짐)와
2단계 `mdm-code-review` 서브에이전트(판단 — 검증 우회·드리프트·권한 경로)로 나뉜다.
에러 학습은 `/mdm-ingest-errors`(`mdm-error-learning`)가 맡는다. 구현한 컨텍스트는 자기 우회를 보지 못하기 때문에 분리한다.
정의는 `.claude/agents/`에 있다.

## 모드 전환 ★

- **S1~S4 = 설계 단계 → 인터뷰 모드.**
  AI가 사용자를 인터뷰해서 정의를 완성한다. 사용자가 답을 미리 알고 있을 필요가 없다 — 질문이 답을 끌어낸다.
  **추론을 가장 높게 쓴다** — Claude Code는 `ultrathink`(또는 `/model`에서 상위 모델), Codex는 reasoning effort `high` 이상.
  여기 품질이 전체 결과를 결정하므로 토큰을 아끼지 않는다.

- **S5~S6 = 구현 단계 → 검수 루프 모드.**
  "구현 → 검수 요청 → 사람이 직접 확인 → 피드백 → 수정"의 반복. 인터뷰는 끝났다.
  추론은 보통으로 내리되, **원인 불명 버그·설계 변경 판단에서는 다시 올린다.**

## 인터뷰 방식 — 묶어 묻기 ★

**S1~S4 전체에 적용되는 정본이다.** 각 가이드가 이 절을 참조한다.

**① 지금 답할 수 있는 질문을 한꺼번에 낸다.** 한 절(①②③…)의 질문은 서로 독립적인 경우가 많다.
하나씩 던지면 왕복이 열 번 넘게 늘어나고 사용자가 지친다.

**② 질문마다 추천 답과 한 줄 근거를 붙인다.** 사용자가 *"3번만 빼고 다 좋다"*로 답할 수 있어야 한다.
사용자가 답을 미리 알고 있을 필요가 없다 — **추천안이 답을 끌어낸다.**
"잘 모르겠다"는 답이 나오면 그건 추천안을 안 붙였다는 뜻이다.

**③ 앞선 답이 정해져야 물을 수 있는 질문은 다음 차례로 미룬다.**

> 예: *"파일을 한 번에 하나만 고르나, 여러 개 고르나?"* 는 지금 물을 수 있다.
> *"여러 개면 진행률을 파일별로 보나 합계로 보나?"* 는 위 답이 '여러 개'라야 뜻이 있다 → 다음 차례.
>
> 둘을 같이 물으면 무의미한 질문을 섞게 되고, 하나씩만 물으면 왕복이 늘어난다.

**④ 사실은 에이전트가 찾는다.** 파일시스템·도구로 알 수 있는 것을 사용자에게 묻지 않는다.
탐색이 필요하면 서브에이전트를 띄우되 **그것 때문에 라운드를 막지 않는다.**
**결정은 사용자의 것이다** — 사실은 찾고, 결정은 묻는다.

**⑤ 답이 실제 선택을 바꾸는 질문만 한다.** 채워야 할 칸이 있다는 이유로 묻지 않는다.

> **예외 — 학습 모드**: 사용자가 그 영역의 전문가가 아니어서 **배우면서 결정해야** 할 때는
> 묶지 말고 한 묶음씩 깊이 다룬다 (`decision-modes.md`). S4 2부 기술 스택이 대표적이다.
> 기술 결정은 서로 얽혀 있어서 지금 답할 수 있는 질문 자체가 적다.

## 인터뷰 모드 기본 프롬프트

새 기술·권한·구조 선택이 있으면 먼저 `decision-modes.md`를 읽는다. **모든 질문을 없애지 않는다.** 새로운·되돌리기 어려운·반복될 선택은 학습 모드로, 이미 기록된 기본값은 실행 모드로 처리한다.

`/mdm-stage [n]`이 이 진입 절차를 대신 수행한다.

```
docs/guides/S<n>-*.md 를 읽고, 그 단계를 완성하기 위해 나를 인터뷰해 줘.
- 지금 답할 수 있는 질문은 한꺼번에 내 줘. 하나씩 묻지 마.
- 질문마다 네 추천안과 한 줄 근거를 붙여 줘.
- 앞선 답이 정해져야 물을 수 있는 질문은 다음 차례로 미뤄 줘.
- 파일이나 도구로 알 수 있는 건 나한테 묻지 말고 네가 찾아 줘.
- 답이 실제 선택을 바꾸는 질문만 해 줘.
- 내가 놓치고 있는 게 보이면 지적해 줘.
- 인터뷰가 끝나면 docs/spec/<산출물>.md 에 정리하고 DoD 체크리스트를 대조해 줘.
```

## 검수 루프 모드 기본 프롬프트

```
구현된 부분을 내가 직접 확인하겠다.
먼저 /mdm-review 로 mdm-code-review 서브에이전트 리뷰를 통과시켜 줘.
그다음 docs/quality/test-scenarios.md 기준으로 내가 눌러볼 순서를 알려 줘.
확인해야 할 것과 정상이라면 어떻게 보여야 하는지를 각 항목에 적어 줘.
```

## 공통 원칙

1. **단계를 외우지 말고 구조만 안다.** 실제 수행은 AI와의 대화로 한다.
2. **각 단계는 산출물 파일 하나로 끝난다.** 산출물이 없으면 그 단계는 끝난 게 아니다.
3. **DoD 전부 통과해야 다음 단계로 간다.** 하나라도 비면 그 자리에서 채운다.
4. **이 6단계는 기능을 추가할 때마다 다시 밟는다.** 최초 구축 전용이 아니다. 두 번째부터는 범위가 작아 훨씬 빠르다.
5. **절차량은 프로파일이 정한다.** 무겁게 느껴지면 프로파일을 확인한다 — 다만 테스트·기록·학습 루프·코드리뷰는 어느 프로파일에서도 줄이지 않는다.
6. **구현 한 덩어리마다 `/mdm-review`.** 리뷰는 서브에이전트가 하고, 사람은 결과의 반영 판단만 한다.

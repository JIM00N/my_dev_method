# 계획 만들기 — 상류가 없을 때 (`/mdm-plan`)

**읽어야 할 때**: 저장소에도 밖에도 계획 문서가 없을 때. `/mdm-adopt`가 여기로 보낸다.
**입력**: 사용자의 아이디어 (한 문장이어도 된다)
**산출물**: `docs/upstream/plan.md`
**모드**: 압박 → 묶어 묻기 → 작성 → 검증
**다음**: `/mdm-adopt` (이 계획을 매핑표로 앉힌다) → `docs/guides/S0-adopt.md`

---

## 왜 이 경로인가

계획을 뽑아 주는 도구는 이미 많다. 하지만 **없는 사람이 더 많다.**
키트가 특정 도구를 전제하면 그 도구가 없는 프로젝트에서는 첫 단계부터 막힌다.

그래서 여기서 만든다. 다만 **키트가 쓸 수 있는 형태**로 만든다 — 그게 외부 도구와 다른 점이다.

| 만드는 것 | 왜 |
|---|---|
| 요구사항마다 **ID** | 이게 없으면 정합성 검사가 아예 불가능하다 |
| 요구사항마다 **검증 조건 목록** | 조건 하나가 테스트 하나다. 검사기가 개수를 센다 |
| **화면 목록** | 화면 정합 검사의 근거 |
| **비목표** | 안 적으면 AI도 사람도 계속 범위를 넓힌다 |
| **부작용 지표** | 주지표만 있으면 그것만 밀어붙이다 다른 걸 망가뜨린다 |

이 다섯 개가 하류(구현·검사)의 연료다. 산문으로만 잘 쓰인 계획서는 이 중 어느 것도 주지 않는다.

**산출 위치는 `docs/upstream/`이다.** 키트가 스스로 만들었어도 "요구사항이 태어난 곳"의 자리는 같다.
`manifest.tsv`의 출처만 `self:plan`으로 적어 외부 수집과 구분한다.

## P1. 압박 — 아이디어가 버티는가 ★

**바로 계획을 쓰지 않는다.** 안 버티는 아이디어를 잘 정리해 봐야 잘 정리된 채로 실패한다.

- **동의하지 않는다. 칭찬하지 않는다.** "좋은 생각이네요"는 잡음이다. 여기서는 아이디어를 공격하는 것이 일이다.
- 공격 각도를 **둘 이상** 잡는다. 예: *이 문제를 실제로 겪는 사람이 있나* · *이미 있는 것으로 되지 않나* ·
  *가장 비싼 부분을 빼면 남는 게 있나* · *한 달 뒤에도 쓸까*.
- 사용자가 **방향을 뒤집을 수 있다.** "이번엔 네가 옹호해 봐" / "역할을 바꾸자"고 하면 따른다.

**끝날 때는 셋 중 하나를 명시한다:**

| 결과 | 뜻 | 그다음 |
|---|---|---|
| **강해졌다** | 공격을 견뎠고 구체적이 됐다 | P2로 간다 |
| **기각** | 안 버틴다 | **여기서 끝낸다.** 이걸 지금 아는 것도 성과다. 이유를 적는다 |
| **이해만 깊어졌다** | 더 잘 알게 됐지만 아직 만들 것이 아니다 | 알게 된 것을 적고 멈춘다. 억지로 P2로 밀지 않는다 |

> **"기각"이라는 출구가 있어야 압박이 진짜가 된다.** 어차피 통과시킬 거면 P1은 연극이다.

## P2. 묶어 묻기 — 정보를 모은다 ★★

**무엇을 물을지의 정본은 `docs/guides/S1-problem.md` ①~⑤다.** 여기서 다시 나열하지 않는다.
S1이 정한 것: 사용자 정의(+난이도 사분면) · 문제 정의 · 범위 경계 · 성공 기준 · 제약.
그 위에 요구사항과 화면을 뽑는 질문이 더 붙는다.

여기서 다른 것은 **묻는 방식**이다.

**① 지금 답할 수 있는 질문을 한꺼번에 낸다.** 하나씩 던지면 왕복이 열 번 넘게 늘어난다.

**② 질문마다 추천 답을 붙인다.** 사용자가 "3번만 빼고 다 좋다"로 답할 수 있어야 한다.
사용자가 답을 미리 알고 있을 필요가 없다 — 추천안이 답을 끌어낸다.

**③ 앞선 답이 정해져야 물을 수 있는 질문은 다음 차례로 미룬다.**

> 예: *"파일을 한 번에 하나만 고르나, 여러 개 고르나?"* 는 지금 물을 수 있다.
> *"여러 개면 진행률을 파일별로 보나 합계로 보나?"* 는 위 답이 '여러 개'라야 뜻이 있다 → 다음 차례.
>
> 둘을 같이 물으면 무의미한 질문을 섞게 되고, 하나씩만 물으면 왕복이 늘어난다.

**④ 사실은 에이전트가 찾는다.** 파일시스템·도구로 알 수 있는 것을 사용자에게 묻지 않는다.
탐색이 필요하면 서브에이전트를 띄우되 **그것 때문에 라운드를 막지 않는다** — 그 탐색에 의존하는 질문만 기다린다.
**결정은 사용자의 것이다.** 사실은 찾고, 결정은 묻는다.

**⑤ 더 물을 게 없으면 끝난다.** 남은 질문이 없다고 선언하고, 사용자가 "됐다"고 하기 전에는 P3으로 넘어가지 않는다.

라운드 형식:

```
❓ Q1 — <제목>
<질문. 선택지가 있으면 함께>
➡️ 추천: <추천 답과 한 줄 근거>

❓ Q2 — <제목>
...
```

## P3. 작성 — `docs/upstream/plan.md`

아래 골격으로 쓴다. **체크리스트가 아니라 판단의 결과다** — 해당 없는 절은 빼되 **왜 뺐는지 한 줄 남긴다.**
골격이 담지 못한 것이 있으면 **절을 새로 만든다.**

```markdown
# <제품명> — 계획

**출처**: self:plan · **작성**: <날짜> · **상태**: 초안 | 확정

## 1. 한 문장
<누가> 가 <어떤 상황>에서 <무슨 문제>를 겪는다.
<무엇>을 만들어 <어떻게> 해결하고, <지표>를 <현재값>에서 <목표값>으로 만든다.

## 2. 사용자
역할별로 나눠 적는다. 권한이 다르면 다른 사용자다.
**난이도 사분면**: 나만/남도 × 로컬/원격 → <칸> (`docs/guides/S1-problem.md` ①)

## 3. 낱말 정의
이 문서가 쓰는 도메인 명사를 **한 번씩만** 정의한다. 같은 것을 두 이름으로 부르지 않는다.
(뒤에서 상태 전이표·데이터 정의가 이 낱말 위에 세워진다)

## 4. 요구사항 ★★
### FR-1: <짧은 능력 이름>
<누가> 는 <어떤 조건에서> <무엇을> 할 수 있다.

**검증 조건**
- <구체적이고 확인 가능한 것>
- <또 하나>

**이번에 안 하는 것** *(있으면)*
- <경계>

### FR-2: ...

## 5. 화면
| ID | 이름 | 무엇을 하는 곳 | 관련 요구사항 |
|---|---|---|---|
| SC-001 | <이름> | <한 줄> | FR-1 |

화면이 없는 프로젝트(라이브러리·CLI·백엔드 전용)는 이 절을 빼고 표면 목록을 S3에서 정한다.

## 6. 이번에 만들지 않을 것 ★
목록으로. **여기가 요구사항 목록보다 중요하다.**
애매한 것은 전부 여기로 보낸다. 필요해지면 그때 다시 계획한다.

## 7. 지표
**주지표**
- <지표> — <정의>, 현재 <값> → 목표 <값>. 검증 대상: FR-1, FR-3

**부작용 지표** ★
- <이걸 밀어붙이다 나빠질 수 있는 것> — <왜 이건 최적화하면 안 되는가>

## 8. 아직 모르는 것
번호를 붙여 적는다. 나중에 다시 볼 거리이지 조용한 구멍이 아니다.

## 9. 가정
본문에 `[가정]`으로 표시한 것을 여기 모아 사용자에게 **명시적으로 확인받는다.**
확인 안 된 가정은 요구사항이 아니라 위험이다.
```

**규율 셋:**

1. **분량은 걸린 것에 비례한다.** 개인 도구면 두 쪽, 남이 쓰는 서비스면 요구사항이 요구하는 만큼.
   (`docs/guides/profiles.md`의 프로파일과 같은 발상이다)
2. **능력을 적고 구현을 적지 않는다.** *"무엇을 할 수 있다"*까지가 여기다.
   *"어떤 라이브러리로"*는 `docs/spec/stack.md`(S4)의 것이다. 여기서 기술을 고르면 S4가 뒤집을 수 없게 된다.
3. **ID는 여기서 태어난다.** `FR-1`은 예시일 뿐 형식은 자유다. 다만 **한 번 붙이면 바꾸지 않는다** —
   사이클·테스트·이슈가 이 번호를 인용하고 검사기가 그 인용을 대조한다.

## P4. 검증 — 체크리스트가 아니라 판정이다 ★

**칸을 채우는 게 아니라 이 계획이 쓸 만한지를 판정한다.** 각 항목에 `튼튼함 / 쓸 만함 / 얇음 / 깨짐` 중 하나를 매기고,
**얇음·깨짐에는 구체적인 위치와 고칠 것을 적는다.** "추상적인 지적은 용기 없음이다."

| 볼 것 | 무엇을 묻나 | 나쁜 신호 |
|---|---|---|
| **결정이 되어 있나** | 읽고 나서 만들기 시작할 수 있나. 무엇을 포기했는지가 적혀 있나 | 모든 선택이 "균형을 맞췄"고 모든 것이 "중요하다" |
| **내용이 실물인가** | 이 문장이 무언가를 결정하나, 아니면 문서를 두껍게 만드나 | 아무 결정도 바꾸지 않는 사용자 정의·차별점·비기능 요구 |
| **앞뒤가 맞나** | 요구사항이 1절 한 문장을 실제로 푸나. 지표가 요구사항을 재나 | 문제와 상관없는 요구사항이 섞여 있다 |
| **완료를 알 수 있나** | 각 요구사항의 검증 조건이 **확인 가능한가** | "빠르다" "편하다" 같은 잴 수 없는 조건 |
| **범위가 정직한가** | 6절이 비어 있지 않나. 애매한 것을 슬쩍 안에 두지 않았나 | "이번에 안 함"이 한 줄뿐이거나 없다 |
| **하류가 쓸 수 있나** | ID가 있나 · 조건을 셀 수 있나 · 화면이 목록인가 | 산문만 훌륭하고 셀 것이 없다 |
| **크기가 맞나** | 걸린 것에 비해 너무 두껍거나 너무 얇지 않나 | 개인 도구에 20쪽 |

**깨짐이 하나라도 남아 있으면 끝내지 않는다.** 얇음은 사용자가 알고 넘어가겠다고 하면 넘어가되, 9절 가정이나 8절에 남긴다.

## P5. 넘기기

1. `docs/upstream/plan.md`로 저장하고 `manifest.tsv`에 `self:plan` 출처와 해시를 기록한다.
2. `/mdm-adopt`를 실행한다 — 매핑표를 만들고 계약 확인을 한다.
   `/mdm-adopt`가 검증 조건 개수를 세어 `조건 수` 칸에 넣는다.
3. 이때 **상태 전이표는 거의 항상 갭으로 나온다.** 계획 문서는 "무엇을 할 수 있다"를 적지
   "데이터가 어떤 상태를 오가나"를 적지 않기 때문이다 → `docs/guides/S2-domain.md` ③에서 채운다.

## 경계 — 무엇을 여기서 하지 않나

| 여기서 안 하는 것 | 어디서 하나 | 왜 |
|---|---|---|
| 기술 스택 선택 | `docs/guides/S4-architecture.md` 2부 | 계획이 기술을 고르면 S4가 뒤집을 수 없다 |
| 상태 전이표 · 권한 표 · 데이터 정의 | `docs/guides/S2-domain.md` ②③④ | 계획의 언어가 아니다. 그리고 여기가 훅·코드리뷰의 연료다 |
| 화면 배치·시각 설계 | `docs/guides/S5-ui.md` | 화면 **목록**까지가 계획이다 |
| 사이클 쪼개기 | `docs/guides/S6-build.md` | 요구사항 단위와 구현 단위는 다르다 |

## 자주 빠지는 함정

| 함정 | 증상 | 처방 |
|---|---|---|
| 압박을 건너뜀 | 잘 정리된 채로 실패한다 | P1에 "기각" 출구를 실제로 열어 둔다 |
| 하나씩 묻기 | 왕복이 열 번 넘어가고 사용자가 지친다 | P2 ① — 지금 답할 수 있는 것을 묶는다 |
| 추천안 없는 질문 | "잘 모르겠다"에서 멈춘다 | P2 ② — 모든 질문에 추천과 근거를 붙인다 |
| 검증 조건이 산문 | 조건을 셀 수 없어 검사가 반쪽이 된다 | P3 4절 — 반드시 **목록**으로 쪼갠다 |
| 비목표가 빔 | 구현 중에 범위가 계속 는다 | P3 6절 — 애매한 건 전부 여기로 |
| 계획에 기술이 섞임 | S4가 결정을 못 뒤집는다 | 경계표 — 능력까지만 적는다 |
| 검증을 칸 채우기로 | 형식은 맞는데 쓸 수 없는 계획이 통과한다 | P4 — 위치를 인용하며 판정한다 |

## 완료 조건 (DoD)

> 표식 규칙: `(Standard+)`는 Standard·Full만, `(Full)`은 Full만 본다.
> `(사람 확인)`은 에이전트가 대신 체크하지 않는다 — 사용자에게 요청하고 받은 답을 기록한다.

- [ ] P1의 결과가 **강해졌다 / 기각 / 이해만 깊어졌다** 중 하나로 명시되었다 (사람 확인)
- [ ] P2에서 더 물을 것이 없음을 선언했고 사용자가 동의했다 (사람 확인)
- [ ] 모든 요구사항에 **ID**가 있다
- [ ] 모든 요구사항에 **검증 조건이 목록으로** 있다 (산문이 아니다)
- [ ] **"이번에 만들지 않을 것"** 목록이 비어 있지 않다
- [ ] 주지표에 숫자와 단위가 있다
- [ ] **부작용 지표가 1개 이상** 있다 (Standard+)
- [ ] 화면이 있는 프로젝트라면 화면 목록에 ID가 붙어 있다
- [ ] 본문의 `[가정]`이 9절에 모여 있고 사용자가 확인했다 (사람 확인)
- [ ] P4 판정에서 **깨짐이 남아 있지 않다**
- [ ] `docs/upstream/manifest.tsv`에 `self:plan` 출처와 해시가 기록되었다
- [ ] `docs/status/STATUS.md`가 갱신되었다

# plan — 계획

**어떤 순서로 만드는가.**

## 파일

| 파일 | 내용 | 언제 |
|---|---|---|
| `roadmap.md` | 마일스톤 + **백로그** | 범위 밖 아이디어가 나올 때마다 |
| `cycles/C<nn>-<이름>.md` | 사이클별 실행 계획 | 사이클 시작 시 생성 |
| `stories/ST-<nnn>-<이름>.md` | Story의 영향 범위·권한 계약·검증 방법 | `docs/guides/profiles.md` 「Story 문서」 행이 정하는 대상일 때 |
| `archive/index.md` | 완료된 사이클·Story 기록의 카탈로그·탐색 | 종료된 계획을 현재 계획에서 뺄 때 |

## 핵심 원칙

1. **사이클에 없는 것은 만들지 않는다.** 좋은 아이디어가 떠오르면 구현하지 말고 `roadmap.md` 백로그로.
2. **한 사이클 = 「구축 → 검수 → 안정화 → 배포」 한 바퀴.**
3. 첫 사이클은 **가장 좁은 동작 경로 하나**. 처음부터 끝까지 이어지되 얇게.
4. **사이클이 크다는 신호의 정본은 이 줄이다** — 완료 조건 10개 초과 / 화면 5개 초과 / "이것도 있어야"가 3회 이상.
   하나라도 걸리면 자른다. 가이드는 이 줄을 **가리키기만** 한다 (`docs/guides/S6-build.md` 1절).
5. **마일스톤은 「여기까지 되면 사람이 실제로 써 볼 수 있다」는 선에서 끊는다. ★**
   요구사항 개수로 나누지 않는다 — 개인 도구는 M1 하나로 끝나고, 큰 제품은 그만큼 늘어난다.
   **너무 크다는 신호** (하나라도 걸리면 다시 긋는다):

   | 신호 | 뜻 | 누가 잡나 |
   |---|---|---|
   | 「무엇이 되면 달성인가」를 확인 가능한 한 문장으로 못 쓴다 | 너무 크다 | **사람** — 기계가 못 본다 |
   | 한 마일스톤에 사이클이 5바퀴를 넘는다 | 너무 크다 | `check-consistency.sh` 검사 H (경고) |
   | 한 마일스톤에 요구사항이 1개다 | 너무 잘다 — 사이클의 다른 이름이 됐다 | `check-consistency.sh` 검사 H (경고) |
   | 마일스톤 안에 배포 없이 끝난 사이클이 있다 | 선이 잘못 그어졌다 | **사람** — 검사 없음 (권고) |

   달성 조건을 못 쓰는 것이 가장 강한 신호다. 그 칸이 마일스톤 표의 필수 칸이므로,
   **안 써진다는 사실 자체가 분할이 틀렸다는 뜻이다.** 별도 규칙을 발명하지 않는다.
6. **Story는 하나의 사용자·도메인 결과를 독립적으로 구현하고 검증할 수 있는 가장 작은 행동 단위다. ★**
   기술 계층(UI·API·DB)으로 자르지 않고 **세로로 관통**하며, 한 에이전트가 그 단위를 끝까지 책임진다.
   **어디까지 쪼개고 어디서 멈추는지의 정본은 `docs/guides/ready.md` 「Story 크기 — 어디서 멈추나」다** —
   여기서 신호를 다시 세지 않는다. 판정 시점은 `/ready`가 슬롯 초안을 채운 **직후**다.
   병렬로 돌릴 작업은 Story 문서에서 영향 범위(손대는 파일)와 권한 계약을 먼저 확정한다.
   같은 파일을 손대는 Story는 병렬로 돌리지 않는다.
7. 완료된 사이클·Story의 상세는 archive로 옮긴다. `roadmap.md`와 STATUS에는 현재·다음 작업만 남긴다.
8. 계획의 계층은 **마일스톤 → 사이클 → Story** 세 층뿐이다. 다른 층(Epic 등)을 만들지 않는다.
   **상류 계획 도구가 몇 층으로 나누든 그 층을 옮겨 오지 않는다** — 상류의 최하위 항목이 곧 Story인 것도 아니다.
   상류는 요구사항 트리를 주고, 어디서 멈출지는 원칙 6의 크기 판정이 정한다.
9. 절차량은 프로파일이 정한다 (`docs/guides/profiles.md`). **Lite는 Story 문서를 만들지 않고 사이클 문서에 흡수한다.**

## 1. 무엇을

한 문장으로. **트리거 하나·종료 상태 하나**로 써진다.

> `<누가>가 <트리거>하면, 시스템이 <핵심 동작>하여 <확인 가능한 결과>가 된다.`

>

**이 문장이 한 트리거·한 종료 상태로 안 써지면 Story가 너무 크다** — 여기서 고민하지 말고
`docs/guides/ready.md` 「Story 크기 — 어디서 멈추나」로 가서 나눈다. 신호와 반례가 거기 있다.
(반대로, "및"이 들어가도 흐름 하나에 종료 상태 하나면 그대로 둔다)

**근거 스펙**: `docs/spec/domain.md#<절>`, `docs/spec/interface.md#<절>`

## 1-1. 개발 준비 슬롯 ★★ — `/ready`가 채운다

**구현을 시작해도 되는지가 여기서 갈린다.** 답이 없는 칸은 구현 중에 에이전트가 묻지 않고 지어낸다.
`/ready`가 **초안을 채우고 갈리는 것만 질문**한다. 사람이 확인·승인한 뒤 이 표가 확정된다.

판정: `✅` 답 있음 · `❌` 답 없고 갈림 · `—` 해당 없음(**이유 필수**)

**A. 정본을 가리키는 칸** — 여러 Story가 공유하므로 **내용을 여기 베껴 쓰지 않는다.** 어느 행인지만 적는다.

| 칸 | 판정 | 정본의 어디 |
|---|---|---|
| 상태 전이 | | `domain.md` 3절 — |
| 권한 & 접근 | | `domain.md` 4절 — |
| 비즈니스 규칙 | | `domain.md` 5절 — |
| 데이터 | | `domain.md` 2절 — |
| 예외 | | `domain.md` 1절 — |
| 표시 | | `interface.md` — |
| 검사 명령 | | `code-conventions.md` 1절 — |

**B. 이 Story만의 칸** — 여기에 직접 쓴다.

| 칸 | 판정 | 내용 |
|---|---|---|
| 선행조건 | | 이 작업을 시작하려면 무엇이 이미 되어 있어야 하나 |
| 트리거 | | 무엇이 이 동작을 시작시키나 |
| 동작 | | 시스템이 무엇을 하나 (순서대로) |
| 결과 | | 끝나면 무엇이 달라져 있나 |

**C. 검증 조건** — 상류의 수용 기준 중 이 Story가 책임지는 것. 실행 형태는 아래 4절에 적는다.

| 판정 | 이 Story가 닫는 수용 기준 |
|---|---|
| | |

> **전부 `✅`가 목표가 아니다.** 화면 없는 Story의 표시 칸, 상태를 갖지 않는 데이터의 전이 칸은
> `—`(+이유)가 정답이다. 칸 채우기가 아니라 **답이 필요한데 없는 곳을 찾는 것**이 목적이다.
>
> **`❌`가 남은 채 구현을 시작하지 않는다.** 매핑표 `준비` 칸이 롤업으로 이 상태를 물고 있고,
> 진행 중인데 `❌`가 남아 있으면 `.claude/scripts/check-consistency.sh`가 실패시킨다.

## 2. 영향 범위 ★

이 Story가 **실제로 손대는 곳**을 미리 적는다. 병렬 작업 시 파일 소유권 충돌을 여기서 막는다.

| 구분 | 대상 |
|---|---|
| 손대는 파일·모듈 | |
| 바뀌는 데이터·스키마 | |

| 바뀌는 상태 전이 | (`domain.md` 전이표의 어느 행) |

> 다른 Story와 **같은 파일**을 손대야 하면 병렬로 돌리지 않는다.
> 데이터·권한·API·코드 컨벤션·파일 소유권이 확정된 뒤에만 병렬 구현한다.

### 3-2. 개발 에이전트 (이 Story를 구현하는 에이전트가 무엇을 해도 되나)

(작성 예 — 허용: "`src/orders/**` 수정, 테스트 추가" / 거부: "스키마 파괴적 변경, 프로덕션 접근, 실데이터 조회, 다른 Story 파일 수정, 새 패키지 도입".

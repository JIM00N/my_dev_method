# 재발 방지 규칙

> 규칙 승격의 단위는 **공통 원인·실패한 통제·적용 조건**이다. 유형 이름만 같다고 합치지 않는다.
> 같은 원인·조건의 두 번째 발생이면 통제를 보완한다. 기존 규칙 수정·회귀 테스트·구조 변경을 먼저 검토한다.
> 첫 발생이어도 영향이 큰 결함은 즉시 재현 테스트와 구조 보완을 검토한다.
>
> 구축 전에 이번 변경에 적용되는 활성 규칙을 읽는다. 사건 원문은 issues/archive, 종합 근거는 learning-log가 소유한다.

## 규칙 목록

| ID | 행동 규칙 | 적용 조건 | 공통 원인·실패 통제 | 근거 이슈 | 검사 장치 또는 수동 확인 | 상태 | 마지막 효과 확인 |
|---|---|---|---|---|---|---|---|
| — | (아직 없음) | | | | | | |

### 작성 규칙

- 행동 지시문으로 쓰고 언제 적용하는지 명시한다. 모호한 주의 문구를 추가하지 않는다.
- 검사 장치가 있으면 경로·테스트를 연결한다. 없으면 수동 리뷰라고 적는다.
- 상태는 active / merged / retired. merged에는 대체 규칙 ID를, retired에는 필요 없어진 근거를 남긴다.
- 마지막 효과 확인에는 적용 사례·잡은 결함 또는 오탐과 날짜를 기록한다. 빈 값은 효과 미측정이다.
- 의미적 원인 분류와 규칙의 유용성 판정은 `/mdm-ingest-errors`의 리뷰 절차다. 자동 판정으로 설명하지 않는다.

## 이관

활성 규칙이 10개를 넘으면 **먼저 통합·폐기를 검토**한다. 파일만 옮겨 총량을 숨기지 않는다.
사이클 종료 시 새 이슈와 관련된 규칙을 확인한다. 관련 없는 규칙 전체를 매번 다시 리뷰하지 않는다.

| 판단 | 처리 |
|---|---|
| 같은 조건·원인을 다루는 중복 | 하나로 통합하고 이전 ID에 대체 링크 유지 |
| 회귀 테스트나 구조 변경이 같은 실패를 막음 | 수동 행동 규칙을 폐기할 수 있는지 검토하고 장치 링크 유지 |
| 적용 대상 기능이 삭제됨 | retired와 삭제 근거 |
| 오탐·질문만 늘고 예방 효과가 없음 | 조건을 좁히거나 폐기 제안, 안전 영향이 있으면 사용자 판단 |
| 여러 제품에 적용할 근거가 있음 | 방법론 저장소에 수정 제안 |

프로젝트 고유의 상세 규칙은 필요하면 `CLAUDE.md` 6절 또는 `docs/spec/code-conventions.md`로 이관하되,
이 파일에 소유 위치·대체 ID를 남긴다. `docs/guides/`는 제품 사고 기록의 이관처가 아니다.

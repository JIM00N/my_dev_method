**상태**: ⬜ 미작성 · **최종 갱신**: YYYY-MM-DD
**전제**: 이 문서는 `stack.md`와 `architecture.md`가 확정된 뒤, **코드를 쓰기 전에** 프로젝트에 맞게 채운다.

> 범용 취향을 나열하는 문서가 아니다. formatter·linter·테스트 명령과 코드 경계처럼, 이 프로젝트에서 자동으로 검증하거나 일관되게 판단할 수 있는 규칙만 확정한다.

## 2. 디렉터리·모듈 경계

| 영역 | 소유 책임 | 다른 영역이 직접 하면 안 되는 것 |
|---|---|---|
| | | |

- 도메인·권한 판단은 UI에만 두지 않고 서버 또는 도메인 경계에서 다시 수행한다.
- 외부 I/O, 데이터 접근, 도메인 규칙, 화면 표현을 한 파일에 섞지 않는다.
- 순환 의존이 생기면 import 우회가 아니라 경계 설계를 다시 검토한다.

## 3. 이름·함수·주석

- 파일·디렉터리·타입·함수·변수의 명명 형식: `(스택 결정 후 기입)`
- 이름은 구현 수단이 아니라 역할·도메인 의미를 드러낸다.
- 함수는 한 가지 책임과 검증 가능한 입력·출력에 집중한다. 테스트 이름에 `and`가 반복되면 행동을 나눈다.
- 주석은 문법을 반복하지 않는다. **왜 필요한가, 어떤 제약·권한·트레이드오프가 있는가**만 설명한다.

## 4. 오류·로그·민감정보

- 외부 입력은 경계에서 검증하고, 내부 로직에는 검증된 타입·값만 전달한다.
- 사용자에게는 해결 가능한 메시지를, 운영 로그에는 원인 추적 정보를 남긴다.
- 로그에 토큰·비밀번호·개인정보·원문 민감 데이터·인증 헤더를 남기지 않는다.
- 재시도 가능 여부, 사용자 조치 필요 여부, 관측 방법을 오류 유형별로 명시한다.

| 권한 거부 | | | |

## 5. 테스트 규칙

- 새 행동은 **테스트가 먼저 실패한 것(RED)**을 확인한 뒤 최소 구현으로 통과시킨다(GREEN).
- 테스트는 내부 호출 횟수보다 사용자·도메인 행동을 검증한다. mock은 불가피한 경계에만 쓴다.
- 권한 영향이 있으면 허용 경로와 거부 경로를 모두 테스트한다.
- 버그 수정은 재현 테스트를 먼저 추가한다. 발견한 오류는 `quality/issues.md`에 기록한 뒤 수정한다.

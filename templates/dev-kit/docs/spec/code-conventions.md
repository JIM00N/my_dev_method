## 2. 디렉터리·모듈 경계

| 영역 | 소유 책임 | 다른 영역이 직접 하면 안 되는 것 |
|---|---|---|
| | | |

- 도메인·권한 판단은 UI에만 두지 않고 서버 또는 도메인 경계에서 다시 수행한다.
- 외부 I/O, 데이터 접근, 도메인 규칙, 화면 표현을 한 파일에 섞지 않는다.
- 순환 의존이 생기면 import 우회가 아니라 경계 설계를 다시 검토한다.

## 3. 이름·함수·주석

- 파일·디렉터리·타입·함수·변수의 명명 형식: `(스택 결정 후 기입)`
- 이름은 구현 수단이 아니라 역할·도메인 의미를 드러낸다.
- 함수는 한 가지 책임과 검증 가능한 입력·출력에 집중한다. 테스트 이름에 `and`가 반복되면 행동을 나눈다.
- 주석은 문법을 반복하지 않는다. **왜 필요한가, 어떤 제약·권한·트레이드오프가 있는가**만 설명한다.

## 4. 오류·로그·민감정보

- 외부 입력은 경계에서 검증하고, 내부 로직에는 검증된 타입·값만 전달한다.
- 사용자에게는 해결 가능한 메시지를, 운영 로그에는 원인 추적 정보를 남긴다.
- 로그에 토큰·비밀번호·개인정보·원문 민감 데이터·인증 헤더를 남기지 않는다.
- 재시도 가능 여부, 사용자 조치 필요 여부, 관측 방법을 오류 유형별로 명시한다.

## 5. 테스트 규칙

- 새 행동은 **테스트가 먼저 실패한 것(RED)**을 확인한 뒤 최소 구현으로 통과시킨다(GREEN).
  RED를 눈으로 확인하지 않은 테스트는 아무것도 검증하지 않고 있을 수 있다. RED 명령과 출력을 보고에 남긴다.
- 테스트는 내부 호출 횟수보다 사용자·도메인 행동을 검증한다. mock은 불가피한 경계에만 쓴다.
- 권한 영향이 있으면 허용 경로와 거부 경로를 모두 테스트한다. **거부 경로가 없는 권한 테스트는 절반이다.**
- 버그 수정은 재현 테스트를 먼저 추가한다. 발견한 오류는 `quality/issues.md`에 기록한 뒤 수정한다.
- 수동 검수에서 **버그를 잡아낸 시나리오는 자동 테스트로 승격한다** (`guides/S6-build.md` 5-4).

## 5-1. 금지된 우회 ★★

에이전트가 막혔을 때 나오는 자연스러운 다음 수가 전부 여기 해당한다. **사람보다 AI에게 훨씬 흔한 실패다.**
`CLAUDE.md` 절대 규칙 11이 이것이고, 리뷰에서 반드시 본다.

| 금지 | 대신 |
|---|---|
| 실패하는 테스트를 삭제하거나 `skip`·`xfail` 처리 | 왜 실패하는지 `quality/issues.md`에 적고 멈춘다 |
| 단언(assert)을 느슨하게 바꿔 통과시킴 | 기대값이 틀렸다면 **스펙을 먼저** 고친다 |
| `any` · `as` · `# type: ignore` · `@ts-ignore`로 타입 오류를 덮음 | 타입이 안 맞으면 경계 설계를 다시 본다 |
| 예외를 잡아 삼킴 (`catch {}`, `except: pass`) | 처리하거나, 올리거나, 최소한 로그를 남긴다 |
| 린트를 `disable` 주석으로 끔 | 규칙이 틀렸으면 이 문서를 고치고 이유를 남긴다 |
| 참조 확인 없이 기존 코드·테스트를 지움 | 지우기 전에 사용처를 찾는다 |
| 스펙 항목을 조용히 빼고 "완료" 보고 | 못 한 것을 못 했다고 말한다 |
| 훅이 막았다고 우회 경로를 찾음 | 막힌 이유를 해결하거나 사용자에게 보고한다 |

**초록불은 목표가 아니라 증거다.** 증거를 만들 수 없으면 위조하지 말고 막혔다고 보고한다.

# spec — 설계 산출물

**무엇을 만드는가**의 확정된 답. S1~S5의 산출물이 여기 쌓인다.

## 파일

| 파일 | 단계 | 내용 | 상태 |
|---|---|---|---|
| `product.md` | S1 | 사용자·문제·범위·성공 기준 | ⬜ |
| `domain.md` | S2 | 데이터·상태 전이·권한 | ⬜ |
| `interface.md` | S3 | 화면 IA / API 표면 / CLI 표면 | ⬜ |
| `stack.md` | S4 | 기술 결정 표 | ⬜ |
| `architecture.md` | S4 | 구조·배치·안정성 7종 | ⬜ |
| `code-conventions.md` | S4 | formatter·lint·테스트·경계·오류 처리·리뷰 규칙 | ⬜ |
| `ui.md` | S5 | 화면 목록·테마 (화면 없으면 스킵) | ⬜ |

## 코딩 전 필독

코드를 한 줄이라도 쓰기 전에 최소한 이 셋은 읽는다:

- `stack.md` — 여기 없는 라이브러리·서비스를 임의로 도입하지 않는다
- `architecture.md` — 안정성 대비가 실제로 구현되어야 한다
- `code-conventions.md` — 코드 품질 명령·모듈 경계·오류·테스트·리뷰 규칙을 따른다

## 규칙

1. **여기 적힌 것과 다르게 구현하지 않는다.** 다르게 해야 할 이유가 생기면
   먼저 이 문서를 고치고 사용자에게 알린 뒤 구현한다. 코드가 스펙을 앞서가지 않는다.
2. **추측으로 채우지 않는다.** 모르는 항목은 `(미정 — 사용자 확인 필요)`로 남기고
   `docs/status/STATUS.md`의 "막힌 것"에 올린다.
3. 스펙이 바뀌면 `docs/status/STATUS.md`의 최근 결정에 한 줄 남긴다.
4. 되돌리기 어려운 변경은 `docs/decisions/`에 ADR로 남긴다.

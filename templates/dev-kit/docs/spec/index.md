# spec — 설계 산출물

**무엇을 만드는가**의 확정된 답. S1~S5의 산출물이 여기 쌓인다.

## 파일

상태는 문서 상태 어휘(미작성 → 작성 중 → 확정)를 쓴다.

| 파일 | 단계 | 내용 | 상태 |
|---|---|---|---|
| `source-map.md` | **S0** | **요구사항·화면 정본 매핑표 · 정본 소유권 · 계약 확인표** | 미작성 |
| `product.md` | S1 | 사용자·문제·범위·성공 기준 | 미작성 |
| `domain.md` | S2 | 데이터·상태 전이·권한 | 미작성 |
| `interface.md` | S3 | 화면 IA / API 표면 / CLI 표면 | 미작성 |
| `stack.md` | S4 | 기술 결정 표 | 미작성 |
| `architecture.md` | S4 | 구조·배치·안정성 7종 | 미작성 |
| `code-conventions.md` | S4 | formatter·lint·테스트·경계·오류 처리·금지된 우회·리뷰 규칙 | 미작성 |
| `ui.md` | S5 | 화면 목록·테마 (화면 없으면 스킵) | 미작성 |

## 코딩 전 필독

코드를 한 줄이라도 쓰기 전에 최소한 이 셋은 읽는다:

- `stack.md` — 여기 없는 라이브러리·서비스를 임의로 도입하지 않는다
- `architecture.md` — 안정성 대비가 실제로 구현되어야 한다
- `code-conventions.md` — 코드 품질 명령·모듈 경계·오류·테스트·**금지된 우회**·리뷰 규칙을 따른다

## 규칙

0. **상류 소유 항목을 여기서 고치지 않는다.** 요구사항·기능 목록·화면 구성의 정본은 상류에 있다
   (외부 기획 도구든, 저장소의 PRD 파일이든, `/plan`이 만든 계획이든 — 어디서 왔든 취급은 같다).
   **어느 항목이 상류 소유인지는 미리 정해져 있지 않다** — `/adopt`의 계약 확인이 판정하고,
   경계표는 `docs/spec/source-map.md` 1절이 정본이다. 상류 소유 항목은 상류에서 고치고 `/adopt --sync`로 받는다.
1. **여기 적힌 것과 다르게 구현하지 않는다.** 다르게 해야 할 이유가 생기면
   먼저 이 문서를 고치고 사용자에게 알린 뒤 구현한다. 코드가 스펙을 앞서가지 않는다.
2. **사이클마다 드리프트를 대조한다.** 1번 규칙만 있고 확인 절차가 없으면 서너 사이클 뒤에
   `spec/`은 읽으면 오히려 해로운 문서가 된다. 그 시점부터 AI는 틀린 문서를 근거로 코딩한다.
   기계 검사는 `.claude/scripts/check-consistency.sh`, 판단이 필요한 대조는 `docs/guides/S6-build.md` 8절.
3. **추측으로 채우지 않는다.** 모르는 항목은 `(미정 — 사용자 확인 필요)`로 남기고
   `docs/status/STATUS.md`의 "막힌 것"에 올린다.
4. 스펙이 바뀌면 `docs/status/STATUS.md`의 최근 결정에 한 줄 남긴다.
5. 되돌리기 어려운 변경은 `docs/decisions/`에 ADR로 남긴다.
